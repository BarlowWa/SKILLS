# 通用计划审查

对技术方案 / 实施计划做**多轮独立 agent 审查**，判定阻塞问题（blocker），驱动修订与复审，最终给出三态结论（通过 / 有条件通过 / 不通过）。

本技能是**编排型**技能：自身不做审查，而是派发独立子 agent 审查、复审与终审。

编排者（主对话）**不直接采信**子 agent 的结论。初审 A 与终审 C 报出的每条 blocker 与 major，**先回计划原文独立核实**——「原话是否真的存在（按坐标能检索到）」「是否确实落入该规则的分界」「是否贴合本次审查的目标与范围」——只有核实为**确认**的条目才驱动修订与终审判据；核实为**驳回 / 待定**的条目**降级后仍如实列入报告**，不静默抹去（详见第 3、6 步）。**判定依据是计划原文，子 agent 的分级自述不是**。

## 适用范围

- **审查对象**：技术方案、实施计划、设计文档、步骤清单（领域无关，不绑定语言/技术栈）
- **使用时机**：计划刚产出、计划修订后、提交/实施前把关
- **调用前提**：本技能是编排型技能，**仅适用于主对话直接调用**（`/plan-review`）。被其它编排者当作子 agent 调用时整体不适用——只读子 agent 无法派发孙 agent，多轮审查模型塌缩
- **不适用**：生产代码规范审查（由 `cpp-rules` 负责）、模块架构审查（由 `cpp-arch-review` 负责）、测试代码审查（由 `cpp-test-review` 负责）、外部资料事实核查（由 `deep-research` 负责）
- **能力边界**：审查子 agent 是**只读**的，输入为**计划全文、计划所引用的代码/资料文件**（见硬性指令 3）与两个 references。因此本技能只做**计划内部一致性**审查——「需求与目标是否对得上」（`SCP-005`）、「事实前提是否标注了核验方式」（`FEAS-006`）、「所引文件是否确有该语句」。**「这个需求本身是否真实」超出本技能能力**（需要工单、用户反馈、线上数据等计划外证据），该判断须明说「需外部核验」并转 `deep-research`，不得凭计划文本臆断

## 严重级别

| 级别    | 含义                                              | 是否触发复审 |
| ------- | ------------------------------------------------- | ------------ |
| blocker | 照此执行无法完成或必错（方向错误 / 不可行 / 关键步骤缺失或矛盾 / 验收不可判定 / 依赖倒置 / 范围缺失 / 不可接受风险无缓解） | 强制修订后复核（正常路径派复审 B；降级路径由终审兼任） |
| major   | 会导致返工或重大风险的缺陷，应修复                  | 仅记录       |
| minor   | 优化建议，可逐步改进                               | 仅记录       |

**与其他 skill 的级别换算**（仅在审查涉及 C++ / 数据库实现，需引用他 skill 作依据时用）见 `references/severity-mapping.md`。

## 工作流程

**主流程（顺序执行、唯一的分叉在「有无已确认的 blocker」处）**：

```
解析输入 → 输入合法性预检 → 得到「计划」 → [初审] 派只读 agent A 全面审查
→ 得到分级问题清单 → [核实] 编排者回计划原文逐条核实 A 的 blocker 与 major（确认 / 驳回 / 待定）
→ 分支：
   · 无「确认」的 blocker ───────────────────────────────→ [终审]
   · 有「确认」的 blocker → 编排者修订 → 派只读 agent B 复审 →（仍有 blocker 则再修订、再复审，上限 3 轮；耗尽仍不通过者直接判「不通过」，不派 C）
                                                        ↓
                                                      [终审]
→ [核实终审] 编排者核实 C 的 blocker 与 major（只降不升）→ 定稿三态结论
```

- **修订与复审的循环**：B 的 prompt 含「上一轮清单（逐条标注采纳 / 驳回 / 未采纳）+ 修订说明 + 修订后计划全文 + 两 references 绝对路径」；B 核对 blocker 是否解决、是否引入新问题，并对「驳回 / 未采纳」项给「驳回有据 / 有保留地驳回」裁定；新 blocker 视同未解决，计入循环。
- **终审**：派全新只读 agent C 独立给结论（通过 / 有条件通过 / 不通过）；C 的输出再由编排者核实一次（见第 6 步），**不做循环回退**——终审是终止节点。

### 1. 获取审查对象（三种输入形态，按优先级解析）

1. **显式文件路径**：用户给出 `PLAN.md` / `docs/plan.md` 等 → 用 Read 读取。**文件不存在或读不到 → 报错并提示用户检查路径**，不猜测内容。
2. **粘贴文本**：用户直接附上方案文本 → 以该文本为审查对象。
3. **当前会话方案（默认，使用最多）**：用户仅输入 `/plan-review` 无参数 → 取当前会话中**最近一处**具备「目标 + 步骤」结构的方案/计划输出块。

> **前提声明**：形态 3 依赖主对话上下文，**仅在主对话直接调用本技能时生效**；当本技能被其它编排者当作子 agent 调用时拿不到父会话，此时**强制回退到形态 1/2**（显式路径或文本），找不到则提示调用方提供。

**输入合法性预检**（形态 1/2/3 均执行）：
- 内容为空、或**无「目标 + 步骤」结构**（是代码、提问、随机文本）→ 判定为「非计划输入」，输出提示并**终止**，不硬审。
  > 「极短但具备结构」**不在此列**——见「豁免」小节的降级规则。

### 2. 初审

派发独立只读 agent A，按 `references/review-dimensions.md` 全面审查，输出按 `references/blocking-criteria.md` 分级的问题清单。

### 3. 核实初审清单（编排者执行，先于任何修订）

子 agent 的分级是**待核实的意见**，不是结论。编排者拿到清单后，**逐条**对每个 blocker 与 major 做同一套核实（minor 仅记录，不核实）——**核实口径对 blocker 与 major 完全相同**，不存在「标成 major 就免检」的通道：

1. **读计划原文**：**按子 agent 给出的坐标（行号 / 小节名）检索**它引的那段**原话**（字面子串）。**检索不到 → 直接标「驳回（无原文依据）」**——这是机械比对，不是「通读一遍觉得有」。
2. **比对规则分界**：回到 `references/review-dimensions.md` 的分界条款，看这条是否真的落入该规则、而非相邻规则或误报。
3. **对照审查目标**：看该缺陷是否真的妨碍「这份计划达成它自己声明的目标」（见下方「目标契合性」）。

据此把每条标成一种：

| 标注 | 含义 | 是否进入循环 |
| --- | --- | --- |
| **确认** | 原话确实存在，且确落入该规则分界 | **仅当原条目是 blocker** ✅ 是；原条目是 major / minor ❌ 否（仅记录） |
| **驳回** | 无原文依据（原话不存在）；或**确证**落入相邻规则的分界，应改挂 | ❌ 否 |
| **待定** | 原话存在，但处规则分界模糊处，编排者无从断定 | ❌ 否（退出 blocker 集；按**该规则原级别**落节，原为 blocker 才降 `major`） |

> 换句话说：只有「**原报 blocker 且核实为确认**」的条目才驱动循环；major/minor 即便被确认为真，也只是记进报告（它们本来就不触发复审）。

- **驳回**须写明理由 + **所据原话**（「计划实际写的是……」）；**改挂**须写明改挂到哪条，并**按改挂后规则的级别**定级。
- **待定**不是第三种缺陷级别，而是**举证状态**：编排者拿不准即说明该缺陷**未达可确证的 blocker 门槛**，于是**退出 blocker 集**（不驱动循环）。落哪一节**取该规则的原级别**：原为 blocker 的降为 `major`；原为 `major/minor` 的**维持原级**。**不得把拿不准的项一律塞进 major**——那会把本该 minor 的模糊项拔高，与「拿不准从宽」相反。这份拿不准本身也是复审的输入，见第 4 步。
- **改挂 ≠ 驳回**：改挂（本条规则不成立、相邻规则成立）后的**级别可能仍是 blocker**（如 `FEAS-006` → `FEAS-001`），那仍进入循环；只有**改挂后级别降为 major/minor** 或**原话根本不存在**时，才落到「驳回」。
- **目标契合性**（第 3 点）**仅对 `SCP-005` / `FEAS-005` / `COMP-003` / `DEP-002` 生效**（范围蔓延类 / 过度设计类 / 偏离既定目标类）。**其余条目不适用该标准**（「必错」「无法落地」「范围边界缺失」「验收不可判定」不因「目标本身该不该这样」而豁免）——否则会以「这不是我们的目标」否掉真 blocker，正是「不要直接采信」要防的反面。第 1、2 点无此例外，对 blocker 与 major **一律**执行。

> 编排者**只核实清单，不复审计划**——不追加子 agent 未报的 blocker、**不改判规则级别的归属**。发现清单外的问题只写进报告，**不驱动循环**；判断仍以子 agent 为准。

### 4. 判定 blocker 与复审循环

- **无「确认」的 blocker** → 跳过复审，直接进入终审。
- **有「确认」的 blocker** → **修订由编排者（主对话）执行**：主对话读取核实后的清单，**自己修订计划**（**默认产出新文本块**；若需覆盖原文件，须先经用户确认），再将「上一轮清单（**逐条标注：采纳（按改编后的原文）/ 驳回（理由）/ 未采纳（未列入理由）**）+ 修订说明 + 修订后计划全文」写入 agent B 的 prompt；**驳回与待定项的原文与理由一并附上**，供 B 反查。用户也可选择「暂停并提示用户改完再触发复审」。
  > 修订须**逐条响应「确认」项**、并避免引入新的 major；每条「确认」项的改动与未改动情况须在**修订说明**中列明，供复审 B 核对。
- **复审 agent B** 核对：blocker 是否真解决、修订是否引入新问题；**并对清单中标记「驳回 / 未采纳」的条目给出裁定**——「**驳回有据**」或「**有保留地驳回**」。
  > **复审中新发现的 blocker 视同未解决，计入循环**。
  > **裁定路径**：B 判「驳回有据」→ 按已驳回处理，不追问；B 判「**有保留地驳回**」→ **编排者再核实一次**：仍认定驳回 → 保留意见、不恢复该 blocker（**避免编排者与 B 互相僵持死循环**）；否则恢复，计入循环。**该路径不新增派发次数**——裁定是 B 复审内的一个步骤，编排者重核是主对话内的一步，均不派新 agent。
  > **返工成本边界**：原 blocker 被驳回、后续实际成真的，由**用户重新触发技能**处理，本技能不为「可能成真」预留轮次。
  > **驳回的影响必须可见**：报告的小结中须给出统计——「初审 blocker N 条 → 确认 N_a + 驳回 N_r + 待定 N_d（N = N_a + N_r + N_d） → 后续实际成真 N_t」，**N_t 与 N_r 的比值就是本技能防假阳性的成绩单**；`N_t > 0` 时须逐条写明「驳回判断错在哪」。不得静默抹去驳回项。
  > B 拿到上一轮清单后倾向重点核对已列项，漏网的新问题由独立终审 C 兜底。
- **循环口径**：**上限 3 轮**，仍存在 blocker → 直接判「不通过」，不死循环——**该情形不派终审 C**（最坏 4 次派发：1 初审 + 3 复审）。
  > **逐轮滚动**：第 N 轮（N ≥ 2）复审的输入清单是**第 N−1 轮复审输出的清单**（含「驳回 / 未采纳」项），修订说明同样逐轮重写。否则上一轮新发现、但本轮修订未解决的 blocker 会从核对清单中消失，复审会误判「已无 blocker」而提前跳出循环。**滚动的是「待核对项」，不是「结论」**——复审 agent 只把上一轮清单当作须逐条独立复核的待办，**不视为已验证**。
  > **B 新报的 blocker 先在主对话核实，再入下一轮清单**：照第 3 步口径执行（回原文按坐标检索），核实为「确认」才成为下一轮的规约项；驳回 / 待定者**滚入下一轮清单的「驳回 / 未采纳」栏**，由下一轮 B 裁定（第 4 步「复审中新发现的 blocker 视同未解决」不再是「不经核实即驱动循环」）。
  > **完整性的硬判据**：B 须以「**本应核对数**」（= 上一轮清单条数（含驳回 / 未采纳项） + 本轮修订新增的条目）为分母，在输出中报告「清单核对数 vs 本应核对数」。**两者不等即核对不完整，该轮结论不得用作跳出循环的依据**——编排者据此要求 B 补齐，仍不齐则按「子 agent 失败兜底」处理。

### 5. 终审

派发**全新**只读 agent C，**不带前几轮结论**，审查**当前（经复审修订后的）计划全文**，独立给三态结论。

**反向设计对抗（终审必做，一次性、不触发回退）**：C 在分级之前，先做一步对抗性检查——

1. 只读计划的**需求部分**（要解决什么问题、为谁解决），**暂时不看**计划提出的方案；
   > 计划**无独立需求小节**时，以「目标 + 背景」段重建需求表述，并在比对中**显式写出该重建**；若目标本身即为唯一需求来源，本步骤退化为「方案对目标的可达性核对」，**不得据此判结构性分歧**。
2. 据此**独立导出**一份它自己认为的最小可行方案；
3. 再读计划方案，与自己的导出**逐项比对**，看差异。

差异按性质归位，**不得新开规则**：

| 差异性质 | 归入 | 典型信号 |
| --- | --- | --- |
| 计划**缺少**达成需求所必需的步骤 | COMP-001（blocker）/ COMP-003（major） | 反推出的必要环节在计划里根本没有 |
| 计划**多出**需求不要求的步骤 | SCP-005 / FEAS-005 | 独立导出里不存在的环节（范围蔓延 / 过度设计） |
| 计划方向与需求对不上 | SCP-005 | 达成目标后，需求所述问题依然存在 |

> **差异归入上表规则 ID 后即按常规分级**（上表括号内已是该规则的级别）：`SCP-005` 为 major，单独出现时为「有条件通过」；**唯有该差异同时构成 `SCP-001`（方向性错误）或 `COMP-001`（关键步骤缺失）时才判「不通过」**——此时不通过的依据是那条 blocker，不是「分歧本身」。

> **该步骤只影响三态判定，不产出替代方案、不触发修订**——C 导出的方案是它自己的比对参照物，**不写入报告给用户**，避免越过「审查者」边界（**终审 C 不改计划**；修订由编排者按第 4 步执行）。
> **该步骤须在同一轮内完成；未完成时就地补做，不因此重新派发 C**。任何情况下不进入回退循环（本节结论仲裁仍然适用）。

三态判据（**C 给出初判，编排者按「核实终审结论」小节复核后的清单定稿**）：

- **通过** = 无 blocker 且无 major
- **有条件通过** = 无 blocker，但存在 major（列出待处理项）
- **不通过** = 存在未解决 blocker

> 三态判据中的 blocker / major **均以「豁免」小节调整后的口径为准**。例如纯调研计划，不因「无交付物」本身计作 SCP-001；若其目标与范围明确，不应因该维度被判「不通过」。

**结论仲裁**：终审是**终止节点**，不触发再修订。终审 C 发现新 blocker → 直接判「**不通过**」并列出该 blocker；如需重审，由**用户重新触发整个技能**。C 与前几轮结论冲突 → **以 C 为准**并说明分歧。

### 6. 核实终审结论（编排者执行，不触发回退）

C 的结论**同样是意见**，对 C 报出的每条 blocker / major 按第 3 步同一口径再核一遍：**确认** → 维持原判；**驳回 / 待定** → 按降级处理并**按降级后的清单定稿三态**（如剩下无 blocker 且有 major，则落「有条件通过」）。

> **单向收紧**：编排者的核实**只降不升**——不得把 C 判的「通过 / 有条件通过」升级为「不通过」。编排者只核实清单、**不复审计划**，无权新增 C 未报的 blocker。此处**核实范围含 blocker 与 major**：C 把某条报成 blocker、实则无原文依据，或报成 major、无原文依据的，**均**按降级处理（原为 blocker 的落 `major` 并注明「原报 blocker，无据降级」；原为 major 的并入 minor）。
> **不新增派发、不触发回退**：核实是主对话内的一步，不派新 agent、不重派 C。C 与编排者各持己见时，报告里**两种意见都写**并说明分歧，结论按本节口径给出。

### 7. 子 agent 失败兜底

任一子 agent 返回空/失败（超时、内容过长、权限）→ **显式报错并重试一次**；仍失败则终止并报告，不静默产出空结论。

## 硬性指令（派发子 agent 时必须遵守）

1. **每轮都用 Agent 工具派发独立子 agent**，子 agent 新建上下文，不继承主对话。
2. **子 agent 类型用只读型（`Explore`）**，禁用 Edit/Write/Agent 工具——审查者不得修改文件或递归派发孙 agent。
3. **派发 prompt 内必须包含「计划全文」与「两个 references 文件的绝对路径」**，并指令子 agent 用 Read 加载 `review-dimensions.md`（审查维度）与 `blocking-criteria.md`（分级标准）。子 agent 新建上下文、不继承主对话，故计划全文必须显式写入 prompt，否则审查对象为空。绝对路径以**本 SKILL.md 所在目录**为基准拼接（`<本技能根目录>/references/...`），编排者派发时须填入实际安装路径。
   > **计划引用了代码库文件时，把被引用文件的绝对路径一并写入 prompt，并指令子 agent 去 Read**。子 agent 新建上下文，拿不到主对话里已有的代码上下文；而 `FEAS`（可行性 / 反例）与 `COMP`（关键步骤缺失）的判断高度依赖计划所引用的真实代码与环境。缺这一步，这两类审查只能凭计划文本自述，深度受限。
   > **派发终审 C 时，还须把「终审」小节的「反向设计对抗」三步与三态判据逐字写入 prompt**——C 是新建上下文的只读 agent，**读不到本 SKILL.md**，只给 reference 路径它不会知道要做这步对抗。
4. **复审 agent 必须拿到「上一轮清单（**逐条标注采纳情况**）+ 修订说明 + 修订后计划全文」**，三者缺一不可（第 1 轮复审对应初审 A 的清单与首次修订说明；后续轮次逐轮滚动，见「循环口径」）——**「驳回 / 未采纳」项的原文与理由也必须附上**，B 要对其反查并裁定（否则 B 会**只核对总条数**，把"漏登"误判成"已确认"）。
   > **上一轮清单是「待核对项」，不是「已验证结论」**：复审 agent 须独立复核每一项，不得因清单已列出即视为确认。
   > **复审必须报告「清单核对数 vs 本应核对数」**：两项相等才算核对完整（见「循环口径」）。
5. **每轮复审、终审都派全新 agent**，不带前几轮结论——复审 B₁ / B₂ / B₃ 各自独立、**不复用同一 agent**，避免自我锚定；终审 C 亦然。
   > **唯一例外**：降级路径（见「豁免」小节的极短计划规则）中终审兼任复核，需携带上一轮 blocker 清单与修订说明以便核对——**仅限降级路径**；正常路径的终审严格适用本条。降级路径下 C 须**先完成反向设计对抗、再读**携带的清单，避免被锚定。
   > **终审额外要求**：必须执行「反向设计对抗」步骤（见「终审」小节），否则终审无效。**该步骤不增加派发次数**——它是同一个 C agent 内的一个步骤，未完成时就地补做，**不重新派发**，也不新增回退循环。
6. **仅 blocker 触发复审循环**；major/minor 只记录。
7. **成本边界**：最坏 5 次正常派发（1 初审 + 3 复审 + 1 终审），每次失败可重试一次，故实际最多 10 次 agent 调用。**「反向设计对抗」是终审内的步骤、主对话内的核实均不额外派发**，故不改变此数。**计划极短（< 3 步）时降级**，并说明降级原因——降级**只跳过复审循环，不跳过修订**；完整降级路径见「豁免」小节。

## 审查维度

7 个维度，完整规则清单见 `references/review-dimensions.md`：

| 维度 | 前缀 | 审查什么 |
|------|------|---------|
| 目标与范围 | SCP | 目标清晰、边界明确、成功标准可判定 |
| 正确性与可行性 | FEAS | 方案是否正确、是否已知不可行、有无反例 |
| 完整性 | COMP | 是否遗漏关键步骤、边界/异常/回滚路径 |
| 风险与缓解 | RISK | 是否识别主要风险并给出缓解措施 |
| 依赖与顺序 | DEP | 任务依赖/顺序是否合理、外部依赖是否识别 |
| 可验证性 | VERIF | 每阶段是否有可验证产出/验收标准 |
| 工作量与资源 | RES | 估算是否合理、有无明显低估/高估 |

## 审查输出格式

> 初审/复审子 agent 只输出分级清单（blocker/major/minor 三节），**不填终审结论**；下方完整格式由编排者在终审后聚合输出。
> **「采纳」栏由编排者填写，子 agent 输出里不出现**（子 agent 只给「规则 ID / 问题 / 原话 / 坐标」四项）。
> **blocker / major 一律要「所据原话」+ 可定位坐标**——原话必须能在计划里**检索到**（子串匹配），**检索不到**的条目由编排者按「无原文依据」驳回并降级。核实正是"按坐标检索该原话"，不是"通读后觉得有"。**写不出原话的条目本身就落在核实口径的「无原文依据」，不会因为标成 major 就免检。**
> **采纳（「已采 / 驳回 / 待定」）是编排者填写**——它是**驳回项的公示位**：核实为「驳回 / 待定」的条目按**自己核实后的级别**落到对应小节（被驳回的 blocker 通常是 major/minor），并在该栏注明驳回理由——**不得因为「不属于 blocker」就整条抹掉**。

```
## 计划审查报告

**审查对象**：<标题/路径>
**审查轮次**：初审 → 复审 ×N → 终审
**初审 blocker 统计**：报出 N 条 → 确认 N_a + 驳回 N_r + 待定 N_d（N = N_a + N_r + N_d） → 后续实际成真 N_t

### 阻塞问题（blocker）
- [ ] <规则ID>：<问题> —— 原话「<逐字引用>」@ <坐标：行号 / 小节名>；采纳：已采（按原话改写为…）

### 重大问题（major）
- [ ] <规则ID>：<问题> —— 原话「<逐字引用>」@ <坐标>；采纳：已采 / 驳回（<理由>） / 待定（按原规则级别保留）
  > 若某项原为 blocker 但被核实降级，其规则 ID 仍保留**声明所依据**的那条；必要时注明「（原报 blocker，无据降级）」。

### 优化建议（minor）
- [ ] <规则ID>：<问题> —— <位置>；采纳：…

### 终审结论
- [x] 通过 / 有条件通过（待处理项见 major） / 不通过（未解决 blocker 见下）
```

> 无问题的小节写「- [x] 无」。
> **驳回项必须留痕**：小结中须附「驳回项复盘」——`N_t = 0` 时写明「驳回 0 条成真」；`N_t > 0` 时逐条写明该驳回判断错在哪。不得静默抹去驳回项。

## 与其他技能协同

- 计划涉及 **C++ 实现**时，`FEAS` 维度引用 `cpp-rules`（编码规范可行性）、`cpp-arch-review`（架构方案可行性）作依据，级别按 `references/severity-mapping.md` 换算。
- 计划涉及**测试策略**时，`COMP`/`VERIF` 维度引用 `cpp-test-author` 的覆盖设计思路。
- 与 `deep-research` 区分：本技能审**计划内部逻辑**，不做外部资料事实核查。

## 豁免

- 计划为纯探索性/调研性质（无明确交付物）时，`VERIF` 维度整个放宽——仅要求「调研结论是否可复现」，不强求验收标准。
  > 同时，**不因「无交付物」本身判 `SCP-001`（blocker）**：纯调研计划的交付物就是结论，不能用「有可交付的产物」去要求它。
  > 但**目标与范围仍须明确**——「调研什么、不调研什么」必须写清；目标含混（如只说「调研一下 X」而无任何范围界定）仍判 `SCP-001` / `SCP-002`。
- 计划极短（< 3 步）时降级——**只跳过复审循环，不跳过修订**：初审**无**「确认」的 blocker → 初审 + 终审（2 次派发）；初审**有**「确认」的 blocker → 编排者**修订一次**后直接终审（终审兼任复核，**此处豁免硬性指令 5**：终审 C 携带上一轮 blocker 清单与修订说明，以便核对是否已解决），不进入多轮复审（2 次派发）。
  > 终审 C 若判定该 blocker **仍未解决** → 直接判「**不通过**」，不再触发二次修订（与正常路径的终止性一致）。
- 其余规则无一例外。
