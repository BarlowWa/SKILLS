# 通用计划审查

对技术方案 / 实施计划做**多轮独立 agent 审查**，判定阻塞问题（blocker），驱动修订与复审，最终给出三态结论（通过 / 有条件通过 / 不通过）。

本技能是**编排型**技能：自身不做审查，而是派发独立子 agent 审查、复审与终审；「判定是否存在 blocker」由编排者（主对话）依据子 agent 的分级清单执行。

## 适用范围

- **审查对象**：技术方案、实施计划、设计文档、步骤清单（领域无关，不绑定语言/技术栈）
- **使用时机**：计划刚产出、计划修订后、提交/实施前把关
- **调用前提**：本技能是编排型技能，**仅适用于主对话直接调用**（`/plan-review`）。被其它编排者当作子 agent 调用时整体不适用——只读子 agent 无法派发孙 agent，多轮审查模型塌缩
- **不适用**：生产代码规范审查（由 `cpp-rules` 负责）、模块架构审查（由 `cpp-arch-review` 负责）、测试代码审查（由 `cpp-test-review` 负责）、外部资料事实核查（由 `deep-research` 负责）
- **能力边界**：审查子 agent 是**只读**的，输入为**计划全文、计划所引用的代码/资料文件**（见硬性指令 3）与两个 references。因此本技能只做**计划内部一致性**审查——「需求与目标是否对得上」（`SCP-005`）、「事实前提是否标注了核验方式」（`FEAS-006`）。**「这个需求本身是否真实」超出本技能能力**（需要工单、用户反馈、线上数据等计划外证据），该判断须明说「需外部核验」并转 `deep-research`，不得凭计划文本臆断

## 严重级别

| 级别    | 含义                                              | 是否触发复审 |
| ------- | ------------------------------------------------- | ------------ |
| blocker | 照此执行无法完成或必错（方向错误 / 不可行 / 关键步骤缺失或矛盾 / 验收不可判定 / 依赖倒置 / 范围缺失 / 不可接受风险无缓解） | 强制修订后复核（正常路径派复审 B；降级路径由终审兼任） |
| major   | 会导致返工或重大风险的缺陷，应修复                  | 仅记录       |
| minor   | 优化建议，可逐步改进                               | 仅记录       |

**级别映射（跨 skill 协同时用）**：

- **blocker** ≈ 各 skill 的**最高级**：`cpp-rules` blocker、`cpp-arch-review` critical、`cpp-test-review` blocker、`cpp-test-author` blocker、`db-rules` blocker
- **major** ≈ `cpp-arch-review` major（其余 skill 为两级，无对应级）
- **minor** ≈ `cpp-arch-review` minor、各两级 skill（`cpp-rules` / `cpp-test-review` / `cpp-test-author` / `db-rules`）的 `warning`

> 现有 skill 的严重级别并不统一（两级与三级并存），引用时以本表为准换算。注意两级 skill 的 `warning` 只能落到本技能 `minor`——两级 skill 中「不阻塞提交」的建议，在本技能里没有 `major` 的对应级，不要为了对齐而拔高或压低其级别。

## 工作流程

```
解析输入 → 输入合法性预检 → 得到「计划」
   ↓
[初审] 派只读 agent A 全面审查 → 分级问题清单
   ↓
判定：是否存在 blocker？
   ├─ 无 blocker ────────────────────────────┐
   │                                          │
   ├─ 有 blocker → 【修订由编排者(主对话)执行】→ │
   │   [复审] 派只读 agent B（prompt 含：       │
   │          上一轮问题清单 + 修订说明 +        │
   │          修订后计划全文 + 两 references 路径）│
   │      核对 blocker 是否解决、是否引入新问题      │
   │      新 blocker 视同未解决，计入循环           │
   │      仍有 blocker → 再修订 → 再复审           │
   │      （「轮」= 一次复审，上限 3 轮）           │
   │      超限 → 编排者直接判「不通过」并终止        │
   │             （不派终审 C）                    │
   │                                          │
   ▼                                          ▼
[终审] 派全新只读 agent C 独立给结论：通过 / 有条件通过 / 不通过
```

### 1. 获取审查对象（三种输入形态，按优先级解析）

1. **显式文件路径**：用户给出 `PLAN.md` / `docs/plan.md` 等 → 用 Read 读取。**文件不存在或读不到 → 报错并提示用户检查路径**，不猜测内容。
2. **粘贴文本**：用户直接附上方案文本 → 以该文本为审查对象。
3. **当前会话方案（默认，使用最多）**：用户仅输入 `/plan-review` 无参数 → 取当前会话中**最近一处**具备「目标 + 步骤」结构的方案/计划输出块。

> **前提声明**：形态 3 依赖主对话上下文，**仅在主对话直接调用本技能时生效**；当本技能被其它编排者当作子 agent 调用时拿不到父会话，此时**强制回退到形态 1/2**（显式路径或文本），找不到则提示调用方提供。

**输入合法性预检**（形态 1/2/3 均执行）：
- 内容为空、或**无「目标 + 步骤」结构**（是代码、提问、随机文本）→ 判定为「非计划输入」，输出提示并**终止**，不硬审。
  > 「极短但具备结构」**不在此列**——见「豁免」小节的降级规则（只跳过复审循环，不跳过修订）。

### 2. 初审

派发独立只读 agent A，按 `references/review-dimensions.md` 全面审查，输出按 `references/blocking-criteria.md` 分级的问题清单。

### 3. 判定 blocker 与复审循环

- **无 blocker** → 跳过复审，直接进入终审。
- **有 blocker** → **修订由编排者（主对话）执行**：主对话读取**最近一轮的问题清单**后**自己修订计划**（**默认产出新文本块**；若需覆盖原文件，须先经用户确认），再将「上一轮问题清单 + 修订说明 + 修订后计划全文」写入 agent B 的 prompt。用户也可选择「暂停并提示用户改完再触发复审」。
  > 修订须**逐条响应 blocker**、并避免引入新的 major；每条 blocker 的改动与未改动情况须在**修订说明**中列明，供复审 B 核对。
- **复审 agent B** 核对：blocker 是否真解决、修订是否引入新问题。**复审中新发现的 blocker 视同未解决，计入循环**。
  > B 拿到上一轮清单后倾向重点核对已列项，漏网的新问题由独立终审 C 兜底。
- **循环口径**：「轮」= 一次复审；**上限 3 轮**，仍存在 blocker → 直接判「不通过」，不死循环。
  > **清单逐轮滚动**：第 N 轮（N ≥ 2）复审的输入清单是**第 N−1 轮复审输出的清单**，而非初审 A 的清单；修订说明同样逐轮重写。否则上一轮新发现、但本轮修订未解决的 blocker 会从核对清单中消失，复审会误判「已无 blocker」而提前跳出循环。
  > **滚动的是「待核对项」，不是「结论」**：复审 agent 只把上一轮清单当作须逐条独立复核的待办，**不视为已验证**；且每轮复审**派全新 agent**（B₁、B₂、B₃ 各自独立），不复用同一 agent，避免自我锚定。

### 4. 终审

派发**全新**只读 agent C，**不带前几轮结论**，审查**当前（经复审修订后的）计划全文**，独立给三态结论。

**反向设计对抗（终审必做，一次性、不触发回退）**：C 在分级之前，先做一步对抗性检查——

1. 只读计划的**需求部分**（要解决什么问题、为谁解决），**暂时不看**计划提出的方案；
   > 计划**无独立需求小节**时，以「目标 + 背景」段重建需求表述，并在比对中**显式写出该重建**；若目标本身即为唯一需求来源，本步骤退化为「方案对目标的可达性核对」，**不得据此判结构性分歧**。
2. 据此**独立导出**一份它自己认为的最小可行方案；
3. 再读计划方案，与自己的导出**逐项比对**，看差异。

差异按性质归位，**不得新开规则**：

| 差异性质 | 归入 | 典型信号 |
| --- | --- | --- |
| 计划**缺少**达成需求所必需的步骤 | COMP-001（blocker）/ COMP-003（major） | 反推出的必要环节在计划里根本没有 |
| 计划**多出**需求不要求的步骤 | SCP-005 / FEAS-005 | 独立导出里不存在的环节（范围蔓延 / 过度设计） |
| 计划方向与需求对不上 | SCP-005 | 达成目标后，需求所述问题依然存在 |

> **该步骤只影响三态判定，不产出替代方案、不触发修订**——C 导出的方案是它自己的比对参照物，**不写入报告给用户**，避免越过「审查者」边界（本技能不改计划）。
> **差异按上表归入既有规则 ID 后，一律回归下方的三态判据**：「方向与需求对不上」记为 `SCP-005`（major）→ 无 blocker 时为「有条件通过」。**唯有该差异同时构成 `SCP-001`（方向性错误）或 `COMP-001`（关键步骤缺失）时，才判「不通过」**——此时不通过的依据是那条 blocker，不是「分歧本身」。
> **该步骤须在同一轮内完成；未完成时就地补做，不因此重新派发 C**。任何情况下不进入回退循环（本节结论仲裁仍然适用）。

三态判据：

- **通过** = 无 blocker 且无 major
- **有条件通过** = 无 blocker，但存在 major（列出待处理项）
- **不通过** = 存在未解决 blocker

> 三态判据中的 blocker / major **均以「豁免」小节调整后的口径为准**。例如纯调研计划，不因「无交付物」本身计作 SCP-001；若其目标与范围明确，不应因该维度被判「不通过」。

**结论仲裁**：终审是**终止节点**，不触发再修订。终审 C 发现新 blocker → 直接判「**不通过**」并列出该 blocker；如需重审，由**用户重新触发整个技能**。C 与前几轮结论冲突 → **以 C 为准**并说明分歧。

### 5. 子 agent 失败兜底

任一子 agent 返回空/失败（超时、内容过长、权限）→ **显式报错并重试一次**；仍失败则终止并报告，不静默产出空结论。

## 硬性指令（派发子 agent 时必须遵守）

1. **每轮都用 Agent 工具派发独立子 agent**，子 agent 新建上下文，不继承主对话。
2. **子 agent 类型用只读型（`Explore`）**，禁用 Edit/Write/Agent 工具——审查者不得修改文件或递归派发孙 agent。
3. **派发 prompt 内必须包含「计划全文」与「两个 references 文件的绝对路径」**，并指令子 agent 用 Read 加载 `review-dimensions.md`（审查维度）与 `blocking-criteria.md`（分级标准）。子 agent 新建上下文、不继承主对话，故计划全文必须显式写入 prompt，否则审查对象为空。绝对路径以**本 SKILL.md 所在目录**为基准拼接（`<本技能根目录>/references/...`），编排者派发时须填入实际安装路径。
   > **计划引用了代码库文件时，把被引用文件的绝对路径一并写入 prompt，并指令子 agent 去 Read**。子 agent 新建上下文，拿不到主对话里已有的代码上下文；而 `FEAS`（可行性 / 反例）与 `COMP`（关键步骤缺失）的判断高度依赖计划所引用的真实代码与环境。缺这一步，这两类审查只能凭计划文本自述，深度受限。
   > **派发终审 C 时，还须把「终审」小节的「反向设计对抗」三步与三态判据逐字写入 prompt**——C 是新建上下文的只读 agent，**读不到本 SKILL.md**，只给 reference 路径它不会知道要做这步对抗。
4. **复审 agent 必须拿到「上一轮问题清单 + 修订说明 + 修订后计划全文」**，三者缺一不可（第 1 轮复审对应初审 A 的清单与首次修订说明；后续轮次逐轮滚动，见「循环口径」）。
   > **上一轮清单是「待核对项」，不是「已验证结论」**：复审 agent 须独立复核每一项，不得因清单已列出即视为确认。**每轮复审仍派全新 agent**（B₁、B₂、B₃ 各自独立），不复用同一个 agent，避免自我锚定。
5. **终审 agent 全新派发，不带前几轮结论**。
   > **唯一例外**：降级路径（见硬性指令 7）中终审兼任复核，需携带上一轮 blocker 清单与修订说明以便核对——**仅限降级路径**；正常路径的终审严格适用本条。降级路径下 C 须**先完成反向设计对抗、再读**携带的清单，避免被锚定。
   > **终审额外要求**：必须执行「反向设计对抗」步骤（见「终审」小节），否则终审无效。**该步骤不增加派发次数**——它是同一个 C agent 内的一个步骤，未完成时就地补做，**不重新派发**，也不新增回退循环。
6. **仅 blocker 触发复审循环**；major/minor 只记录。
7. **成本边界**：最坏 5 次正常派发（1 初审 + 3 复审 + 1 终审），每次失败可重试一次，故实际最多 10 次 agent 调用。**「反向设计对抗」是终审内的步骤，不额外派发**。**计划极短（< 3 步）时降级**，并说明降级原因——降级**只跳过复审循环，不跳过修订**：
   - 初审**无** blocker → 初审 + 终审（2 次派发）；
   - 初审**有** blocker → 编排者**修订一次**后直接终审（终审兼任复核，**此处豁免硬性指令 5**：终审 C 携带上一轮 blocker 清单与修订说明，以便核对是否已解决），不进入多轮复审（2 次派发）。
     > 终审 C 若判定该 blocker **仍未解决** → 直接判「**不通过**」，不再触发二次修订（与正常路径的终止性一致）。

   复审超 3 轮仍存在 blocker → 由编排者**直接判「不通过」**，不再派终审 C（该场景最坏 4 次派发：1 初审 + 3 复审）。

## 审查维度

7 个维度，完整规则清单见 `references/review-dimensions.md`：

| 维度 | 前缀 | 审查什么 |
|------|------|---------|
| 目标与范围 | SCP | 目标清晰、边界明确、成功标准可判定 |
| 正确性与可行性 | FEAS | 方案是否正确、是否已知不可行、有无反例 |
| 完整性 | COMP | 是否遗漏关键步骤、边界/异常/回滚路径 |
| 风险与缓解 | RISK | 是否识别主要风险并给出缓解措施 |
| 依赖与顺序 | DEP | 任务依赖/顺序是否合理、外部依赖是否识别 |
| 可验证性 | VERIF | 每阶段是否有可验证产出/验收标准 |
| 工作量与资源 | RES | 估算是否合理、有无明显低估/高估 |

## 审查输出格式

> 初审/复审子 agent 只输出分级清单（blocker/major/minor 三节），**不填终审结论**；下方完整格式由编排者在终审后聚合输出。

```
## 计划审查报告

**审查对象**：<标题/路径>
**审查轮次**：初审 → 复审 ×N → 终审

### 阻塞问题（blocker）
- [ ] <规则ID>：<问题> —— <位置/依据>

### 重大问题（major）
- [ ] <规则ID>：<问题> —— <位置/依据>

### 优化建议（minor）
- [ ] <规则ID>：<问题> —— <位置/依据>

### 终审结论
- [x] 通过 / 有条件通过（待处理项见 major） / 不通过（未解决 blocker 见下）
```

> 无问题的小节写「- [x] 无」。

## 与其他技能协同

- 计划涉及 **C++ 实现**时，`FEAS` 维度引用 `cpp-rules`（编码规范可行性）、`cpp-arch-review`（架构方案可行性）作依据，按「严重级别」小节的映射表换算级别。
- 计划涉及**测试策略**时，`COMP`/`VERIF` 维度引用 `cpp-test-author` 的覆盖设计思路。
- 与 `deep-research` 区分：本技能审**计划内部逻辑**，不做外部资料事实核查。

## 豁免

- 计划为纯探索性/调研性质（无明确交付物）时，`VERIF` 维度整个放宽——仅要求「调研结论是否可复现」，不强求验收标准。
  > 同时，**不因「无交付物」本身判 `SCP-001`（blocker）**：纯调研计划的交付物就是结论，不能用「有可交付的产物」去要求它。
  > 但**目标与范围仍须明确**——「调研什么、不调研什么」必须写清；目标含混（如只说「调研一下 X」而无任何范围界定）仍判 `SCP-001` / `SCP-002`。
- 计划极短（< 3 步）时按「硬性指令 7」降级——**只跳过复审循环，不跳过修订**（初审无 blocker → 初审 + 终审；初审有 blocker → 修订一次后直接终审）。
- 其余规则无一例外。
