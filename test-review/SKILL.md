# 测试代码审查

对测试代码进行质量审查，确保测试可靠、可维护、有效。判据分两层：**形态可核对**的规则全部在本文且语言中立；**执行证据的获取方式**与语言专有形态在 `references/<lang>.md`。

## 适用范围

- **测试路径**：`tests/`、`test/`、`unittest/`、`src/test/`、`test_*.py`、`*_test.*`、`*Test.java`、`*IT.java`、`*_unittest.*`（按路由判定）
- **审查依据不限于测试源码**：EXEC 组还必须读**构建配置**与**运行产物**（注册清单、测试报告、CI 结果）。仅凭测试源码**无法**判断测试是否真被构建、注册、执行——这三类恰是"缺席类"缺陷，在源码里表现为"看起来没问题"。
- **不适用**：生产代码编码规范（`code-rules`）、测试用例设计（`test-author`）、模块架构（`arch-review`）

## 语言路由

| 语言 | 参考文件 | 状态 |
| ---- | -------- | ---- |
| C++ | `references/cpp.md`（gtest/Catch2/doctest、Death Test、CMake/CTest 证据、假阳性陷阱） | ✅ |
| Rust | `references/rust.md`（cargo metadata/libtest `--list`/doctest 执行证据、`#[ignore]`/cfg/guard 形态、`should_panic`/`debug_assert` 陷阱） | ✅ 已就绪（待真实项目验收） |
| Java | `references/java.md` | ⏳ |
| Python | `references/python.md` | ⏳ |

> **路由优先级**：先按扩展名/构建文件判定语言，再看是否属于测试路径。扩展名能唯一确定语言、但目录不在上表时（如仓库外置的 `add_test.rs`），仍按该语言处理，并在输出中注明判定依据——不得因路径未命中而静默降级或跳过。


**降级**：语言已识别但参考文件不存在 → 只应用本文规则，并在报告顶部标注 `⚠️ 未加载语言专属执行证据：<lang>`，EXEC 组相应记为「未能判定（缺语言证据获取方式）」。

## 工作流程

0. **收集执行证据**（EXEC 组的前提）：定位构建配置中的测试目标、测试运行器的注册清单、最近的运行日志/报告。**运行产物是活文件**——先记时间戳，确认审查期间未被其它构建或 CI 改写，否则同一份报告的数据可能来自不同次运行。
1. **寻找设计清单**：`test-author` 产出的「契约表 + 用例矩阵 + 断言区分度表 + 未覆盖项 + 待确认契约项」是核对基准，`推测` 项与 `未覆盖项` 须**优先核对**。
   按序查找：测试文件顶部的设计依据注释块 → `docs/test-design/` 等固定路径 → 同会话上下文中 author 的输出。
   **⚠️ 三处都找不到不得静默跳过**：报告中显式标注「未找到设计清单——上述 9 项无法核对」并按 warning 计入。**"没查"不是"没问题"**；原因通常是清单未落盘。
2. **识别测试文件**：按路由扫描测试目录与命名模式。
3. **逐文件审查**：对照下方 checklist 逐条检查。
4. **输出报告**：按底部格式。

## 严重级别

| 级别    | 含义                                              |
| ------- | ------------------------------------------------- |
| blocker | 必须修复，违规测试可能产生假阳性/假阴性，削弱测试可信度 |
| warning | 优化建议，应处理但不阻塞提交                       |

## ⚠️ 判定的证据来源：哪些能机械核对，哪些只能核对"依据"

| 类型 | 判据 | 怎么判 |
|---|---|---|
| **形态可核对** | ORG · MOCK · DET · ASRT · EXEC · 语言死亡/崩溃测试组 · TPERF · COV-001/COV-003 | **直接读测试代码/构建配置/运行产物**，不依赖自述，判定具体到 `文件:行` |
| **需要设计依据** | COV-002 · CONTRACT · EXPECT · DIST · BVA · ECP · BRP · FLT · CONC · RLC | 只能判定**是否落地**，不能判定**设计是否正确** |

- **第二类的判定输入是 `test-author` 的设计清单；没有清单 = 无法判定，不是"通过"。**
- **清单本身是自述**：依据列、期望值依据、能捕获的错误都由设计者自填，本技能没有机制验证其为真（唯一证伪手段是变异测试）。核对到的是"清单与测试是否一致"，不是"契约是否正确、边界是否取对"。
- 清单缺失或明显补写时，**降低该组结论的置信度并注明**；测试与清单措辞雷同时，警惕是同一份自述的两次誊抄。
- `TPERF-001` 依赖运行时测量，静态审查时只作参考建议，不能判定到 `文件:行`。

## Blocker 检查清单

### ORG：文件组织

- **ORG-001**：测试文件必须与源文件有明确对应关系，命名遵循该语言惯例（C++ `<source>_test.cpp`；Python `test_<module>.py`；Java `<Class>Test.java`；Rust 集成测试按被测模块命名）；禁止无关联的随机测试文件名。
- **ORG-002**：测试目录结构应镜像源代码目录结构（如 `src/foo/bar.cpp` ↔ `tests/foo/bar_test.cpp` 或语言等价路径）。
  > 「镜像」指**目录结构**，与 ASRT-005 禁止的「镜像实现」（测试内重写被测逻辑）无关。
- **ORG-003**：新建测试文件须声明**测试层级**（unit / integration / e2e），且与**实际范围**相符。默认取能覆盖目标的最低层级——仅验证单个函数/类，不得引入完整集成环境或真实外部依赖。
  > 层级失当同时造成：运行时间数量级上升（与 TPERF-001 冲突）、非确定性上升（与 DET 组冲突）、失败定位成本上升。
  > **边界**：被测单元**本身就是**文件系统/网络/数据库适配层时，用真实资源测试属正当层级；禁止的是为验证纯内存逻辑而读写真实外部资源。
  > 一行 `// Test level: unit` 注释不构成通过条件——须核对依赖与实际触碰的资源是否与声明相符。

### MOCK：Mock 与 Fake 策略

- **MOCK-001**：禁止 mock 不拥有的类型——只能 mock/fake 自己代码中的接口，禁止 mock 第三方库、标准库或系统 API 的具象类。
  > mock 第三方类型会在库升级时无声失效（接口变化但 mock 不报错，测试继续通过）。
- **MOCK-002**：禁止对值类型和标准容器（`std::vector`、`std::string`、`List`、`dict` 等）使用 mock——直接构造真实实例。

### DET：测试确定性

- **DET-001**：禁止在测试断言中使用非确定性随机源（C++ `std::rand()`/`random_device`；Java `new Random()` 无种子；Python `random` 无种子；Rust 未播种的 `rand::thread_rng` 等）。需要随机数据时用确定性种子并在测试中显式注入。
- **DET-002**：禁止在测试断言中直接使用实时时钟（`system_clock::now()`、`System.currentTimeMillis()`、`time.time()`、`Instant::now()` 等）。使用可注入的假时钟配合时间源抽象。
  > 单调整时钟（`steady_clock` / `nanoTime`）只免墙钟回拨，**不能**让测试确定性——真实时间仍在流逝。
- **DET-003**：用例之间禁止通过全局/静态/单例状态共享可变数据；每个测试独立，运行顺序不影响结果。
  > SetUp/TearDown 必须重置所有全局/静态状态；测试框架通常不保证用例顺序（并行执行时更甚）。
- **DET-004**：异步/并发测试必须确定性——异步操作显式等待完成、测试内创建的线程/任务必须 join/await、竞态敏感点用确定性同步手段，禁止依赖调度时序或 sleep 猜测。

### ASRT：断言质量

- **ASRT-001**：每个用例必须包含至少一个有效断言；禁止空测试或无断言测试——无断言的测试默认通过，给出"已覆盖"的虚假安全感。
- **ASRT-002**：断言须验证关键语义。禁止平凡断言（`assertTrue(true)`、只断言非空后不验证具体行为）；相等比较用专用的相等断言（`EXPECT_EQ` / `assertEquals` / `assertEqual`）而非布尔真值断言，失败信息差异巨大。
  > 「平凡断言」指形式正确但内容空洞；「测试内重写被测逻辑」是另一类缺陷，见 ASRT-005。
- **ASRT-003**：浮点比较禁止直接相等断言，使用带显式容差的近似断言。
- **ASRT-004**：正确选用非致命断言（失败后继续）与致命断言（失败即终止当前用例）；依赖后续语句安全时（如解引用指针前）用致命断言提前拦截。
- **ASRT-005**：禁止**镜像实现**——测试代码中不得重写一遍被测逻辑再与被测实现对比。典型形态：测试内重写算法、复制同源实现作参照、先运行被测实现再把输出固化成字面量当期望值。期望值必须来自契约、规格或独立算例。
  > **为何是 blocker**：镜像实现只验证「两处实现一致」，两处犯同一个错时测试照样通过。它无法通过覆盖率、断言数量等任何统计指标发现。**字面量**形态最隐蔽：断言写法上是常量、形似独立算例，但期望值实为照抄实现输出；审查时对**边界与错误用例的期望值**须重点追问来源。
- **ASRT-006**：断言只依据**公开可观测**的返回值、副作用与状态。禁止后门访问私有成员——解除私有可见性、测试专用 friend、反射读写私有字段、直接读内部缓存值。
  > **为何是 blocker**：后门把实现细节固化成契约，内部重构会连带破坏一批本应无关的测试，使测试成为重构阻力。
  > **边界**：仅为测试可见性、不改语义的 friend/包级可见声明属既有约定时可分期整改；**断言私有成员取值**与「宏展开解除私有」不在豁免之列。

### EXEC：执行链（测试是否真的在跑）

> **本组必须读构建配置与运行产物，不能只看测试源码。** 前几组审"测试写得对不对"，本组审"这些测试算不算数"——断言写得再好，若从未被构建或调用，价值为零，且**在源码里完全看不出来**。

- **EXEC-001**：每个测试源文件必须**被某个构建配置引用**且能被真正编译。
  > 判据是「有没有被**任何**构建文件引用」，不是「有没有被某个子目录机制引入」。可靠做法是查**构建产物/目标清单**并与测试源做双向差集；不要用文本搜 `add_subdirectory` 类指令（写法各异，实测误报 3–4 条）。
  > **未编译的测试不会报错、不会告警、不出现在任何报告里**——纯粹的缺席，只能反查。两条独立路径：构建配置的 target 清单 / 构建产物反查。
- **EXEC-002**：测试可执行目标必须**注册给测试运行器**（如 CTest `add_test`、JUnit/Maven Surefire、pytest 收集、cargo test），否则构建出来也从不执行。
  > 判定必须用**构建后的注册清单**，不得用构建文件的字面文本做差集——注册常由变量/循环生成，字面 grep 会得出大量假阳性。
  > **范围限定**：只针对**测试**目标；其他可执行目标（工具、驱动、示例）不计入"未注册"。
- **EXEC-003**：测试不得被**无条件跳过**。逐条确认跳过有无正当理由（为何跳过、何时恢复、关联工单），无理由者按 blocker。
  > 形态包括（按语言展开见参考文件）：框架跳过 API、disabled 前缀/标签、编译期排除整块、空壳用例体、**前置 guard + 提早 return**——最后一种**无任何标记、运行时报通过**，与真跑过完全不可区分，是最易漏检的形态。
  > **判定**：依赖外部资源的 guard 本身可能是合理防御，但必须能与"真的测过了"区分（显式跳过标记或至少 `[SKIP]` 输出并计数）；只在运行时显示"通过"而不留痕迹的，按 blocker，至少记 warning 要求补标记。
  > **「静默」的判据是「有无解释」，不是「有无条件编译」**：带说明、有技术理由（平台 API 无法构造前置条件）、且该逻辑在另一环境已覆盖的，属正当差异，记 warning 即可。
- **EXEC-004**：断言必须**真的会被执行**。禁止致命断言之后的普通断言承载关键验证——致命断言失败即终止当前用例，其后语句永不执行。
  > **先读框架实现确认宏/方法的真实语义，不要按字面推断**：同名写法在不同框架/自定义封装下致命性可能不同，必须一路读到最底层（`throw`/`abort`/`return`）才能定性。
- **EXEC-005**：套件不得包含**已知失败但被隔离**的用例而不做机器可识别的标记。
  > 把已知缺陷的复现用例拆成独立 target/标签以保证套件退出码为绿时，**"CI 绿灯"不再等价于"无已知失败"**。必须落实可操作的标记（标签并验证过滤真能排除、期望失败机制、或项目自己的期望失败清单）；光靠命名约定不算——命名没有机器效力。
  > **必须先区分三种状态**：①红灯仍在 → 未标记 blocker；②红灯已修、已转绿 **且** 提交顺序证明测试早于修复、断言写的是「应该怎样」→ 绿灯正确，缺标记只是记账债，**不报 blocker**；③用例被改坏（绿但断言写"现在怎样"）→ blocker（见 ASRT-005）。
- **EXEC-006**：**按名字**逐条对账后，声明与执行不得有差异。
  > **计数先要数对**：裸搜索声明关键字会把注释里提到的也算进去；须用锚定行首的写法。名字可能含转义字符或多字节字符，自动比对前须归一化。
  > **不要用「声明总数 − 执行总数」直接判红。** 差额的唯一可接受来源是**环境条件编译的一对一替换**（总数守恒、名字互换）。正确做法是按名字做双向差集，对每处差异回读源码定位，而不是拿两个总数相减。
  > 「静默」的判据同 EXEC-003——有无解释、逻辑在另一环境是否覆盖。

## Warning 检查清单

### COV-W：路径覆盖

- **COV-001**：每个被测公开接口的测试集应覆盖正常路径和至少一个边界条件或错误路径；禁止仅有 happy-path 的完整接口测试集。
- **COV-002**：对照 `test-author` 的设计清单逐项核对实际测试是否落地。**消费清单须完整**：契约表、用例矩阵（含「期望值依据」列）、区分度表（含「能捕获的实现错误」列）、待确认契约项。缺失的 CONTRACT/EXPECT/DIST/BVA/ECP/BRP/FLT/CONC/RLC 覆盖须显式列出。
  > 重点核对四处：`推测` 项是否被当作既定事实；「期望值依据」所述来源与实际断言是否相符（写"规格条目"而测试里照抄实现输出 = ASRT-005）；「待确认」项是否未确认就固化进断言；「能捕获的实现错误」是否言过其实（可对照实际断言判断）。
- **COV-003**：套件冗余——同一文件内多条用例验证同一行为、断言几乎重复时，应合并为参数化用例，或在文件中写明差异点。差异点仅是输入取值不同而断言语义完全相同时，仍应合并。

### MOCK-W：Mock 深入建议

- **MOCK-003**：单个用例中 mock 对象数量宜控制在 3 个以内；超出通常是被测类型职责过重的信号，建议重构而非堆砌 mock（启发式，不阻塞）。
- **MOCK-004**：优先 Fake（轻量内存实现）而非 Mock（期望验证）。Mock 适用于需验证交互协议的场景（回调次数、调用顺序）。
  > 过度使用交互期望会使测试脆弱——被测类型的内部重构不应破坏测试。
- **MOCK-005**：区分 Stub（固定返回值）/ Fake（轻量实现）/ Mock（期望验证）三概念；为简单固定返回值引入完整 Mock 框架属过度设计。

### THR-W：覆盖率阈值

- **THR-W001**：建议语句/分支覆盖率 ≥ 80%，核心模块 ≥ 90%。可配置的目标声明（需运行时工具测量），仅作参考建议。

### TPERF-W：测试执行效率

- **TPERF-001**：单个用例平均执行时间宜在 100ms 以内；超过 500ms 的应标记为慢速测试并确认必要性（依赖运行时测量，静态审查时作参考建议）。
- **TPERF-002**：禁止在测试中使用固定 `sleep` 类主动等待——用条件变量、假时钟或带超时的轮询替代。

```
## 测试审查报告
```

## 豁免

- 用例设计由 `test-author` 主动规划，本技能专注落地后的质量审查。
- 与大型遗留测试集集成时，ORG-001/002 的目录结构改造可分期实施，新建测试必须遵守。
- 性能基准测试：豁免本技能**全部**规则，**唯一保留 EXEC-001/EXEC-002 的工程性判据**——基准必须真的被构建并注册；"写了但没接进构建"仍是 blocker。
- 语言专有豁免（如 C++ 实时时钟在时间相关 integration test 中的例外、friend 可见性的分期整改）见参考文件。
- **EXEC 组证据依赖**：纯源码审查场景下无法判定 EXEC-001/002/005/006，须记为「未能判定（缺构建/运行证据）」，**不得记为通过**；EXEC-003/004 可从源码独立判定，不因缺证据跳过。
- **「形态成立但根因正当」不是缺陷**——平台差异、红灯已修复、显式跳过契约三类须判为正当。**判据只负责"发现形态"，定性必须结合根因**；把"形态吻合"直接输出成 blocker，是本技能最容易造成伤害的地方（实测会在一份健康仓库上误报两位数 blocker）。
- **环境问题不等于测试缺陷**：并行运行改写日志、产物目录与工作目录不同盘、多配置生成器缺参数——识别到时报告「未能判定」并说明所需环境。
- 通用规则与语言参考冲突时**取更严者**；其余规则无一例外。
