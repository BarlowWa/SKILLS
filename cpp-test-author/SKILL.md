# C++ 测试用例设计

对被测 C++ 单元做**主动的用例设计**。设计用例之前先厘清契约（CONTRACT），设计之中系统性覆盖边界条件、等价类与分支路径（BVA/ECP/BRP），设计之后确认期望值有来源（EXPECT）、断言有区分度（DIST）。与 `cpp-test-review`（编写完成后的质量审查）互补，形成「先设计、后审查」的闭环。

## 适用范围

- **被测对象**：C++ 类、函数、模板、状态机等单元（被测源码为 `.h`/`.hpp`/`.cpp`/`.cc`）
- **使用时机**：新增测试文件、为已有测试补充用例、重构后重估覆盖、需求变更引入新边界时
- **测试框架**：gtest、Catch2、doctest、Boost.Test 等（本技能聚焦用例设计，框架无关）
- **不适用**：生产代码编码规范（由 `cpp-rules` 负责）；测试代码质量审查（由 `cpp-test-review` 负责）；模块架构审查（由 `cpp-arch-review` 负责）

## 工作流程

1. **契约分析**：产出被测单元的契约表并标注每项依据来源，识别「推测项」（CONTRACT-001/002）。契约自相矛盾时先停下向用户确认（CONTRACT-003）
2. **识别被测单元**：确定被测函数/类，列出全部输入维度（参数、全局状态、环境）与输出空间
3. **输入空间分析**：对每个输入维度划分有效/无效范围，标记边界点（BVA）与等价类（ECP）
4. **设计用例**：按 BVA/ECP/BRP 生成用例清单，**每条标注期望值依据**（EXPECT-001）与覆盖的规则编号
5. **区分度自查**：逐条核对断言是否具区分度（DIST-001）、是否混入镜像实现（DIST-002）
6. **结构化组织**：用参数化集中管理边界用例、规范命名（OGN）
7. **输出**：按输出格式给出契约表、用例矩阵、未覆盖项与待确认契约项，作为 `cpp-test-review` 审查时的核对输入

## 严重级别

| 级别    | 含义                                                          |
| ------- | ------------------------------------------------------------- |
| blocker | 必须设计到位，缺失将导致测试无法判定真伪——契约不明（CONTRACT）、期望值无依据（EXPECT）、断言无区分度（DIST），或边界/覆盖盲区（BVA/ECP/BRP/FLT/CONC/RLC） |
| warning | 建议项，改善可维护性与可读性，不阻塞                          |

## Blocker 检查清单

### CONTRACT：契约与前置分析

- **CONTRACT-001**：设计用例前必须产出被测单元的契约表，逐项列明：**前置条件**、**后置条件**、**不变量**（含跨多次调用的序列不变量）、**副作用**（特别是可观测副作用）、**错误契约**（哪些输入会失败、以何种方式失败——错误码 / 异常类型 / 断言中止）。缺少错误契约时，边界用例无法判定「该接受还是该拒绝」。
  > 契约不明确的单元，其「正确」本身就是未知数——此时任何用例都只是把猜测固化成断言。契约表的**依据**列中，至少一项必须来自被测代码之外（规格文档、协议标准、既有调用点），不得全部落在「接口声明」这一项上：仅凭头文件签名推出的契约，等于把头文件没说的部分交给猜测。
- **CONTRACT-002**：契约表的每一项必须标注依据来源，取值集合：`规格文档` / `接口声明（头文件、Doxygen、契约注释）` / `调用方约定（既有调用点）` / `协议或业界标准` / `推测`。标记为 `推测` 的契约项必须在输出中**集中单列**，不得混同在确认项中。
  > 这条是把「我看到什么」与「我猜什么」分开的关键——推测项正是最可能产出错误期望值的地方。若依据列被整列填成 `接口声明`，需回头确认：该行为真的是声明中写明的，还是从实现反推的？
- **CONTRACT-003**：契约不明或自相矛盾（同一输入按规格该接受、按调用方用法该拒绝）时，必须先向用户提出并确认，禁止默默选一种继续设计。确需推进的，把该项标为 `推测` 并列入「待确认契约项」小节。
- **CONTRACT-004**：契约表只列**可观测**的前置/后置/副作用。测试不得依赖不可观测的内部中间状态（与 `cpp-test-review` ASRT-006 衔接）。

### EXPECT：期望值可追溯

- **EXPECT-001**：每条用例的期望值必须标注依据，取值集合：`规格条目` / `契约表·<项名>`（指向本技能输出的契约表中某一项，如 `契约表·错误契约`） / `手工计算算例（须写明算法）` / `协议或业界标准` / `异源参考实现`。
  > **禁止**把「被测实现的当前行为」当作期望值依据——那是复述实现，不是验证需求。把实现跑一遍、把输出抄成字面量，同样属于此列：断言的书写形式是字面量还是表达式，都不改变「期望值来自实现」这一事实。标为 `异源参考实现` 的，须写明它来自何处、为何与本次改动不同源；同源参考实现不得作为依据（见 DIST-002）。
- **EXPECT-002**：每条用例至少有一条依据**不得来自本仓库**（规格条目、协议/业界标准、独立手工算例、或异源参考实现四者之一），以保证可追溯链存在外部锚点。
  > 全部依据都落在「契约表」或「接口声明」上时，可追溯性退化为自环——契约表本身也是设计者产出的，没有外部基准可供核对。本条的强制项是为了让审查者至少有一个可独立复核的支点。

### DIST：断言区分度

- **DIST-001**：每条用例的**关键断言**须由设计者逐条给出「何种符合契约的实现错误会被它捕获」的具体理由。至少要有一个可被实现错误证伪的断言；只断言「与自身期望值相等」不构成该状态。
  > 示例：「`b == 0` 时返回 `kErrDivZero`」的断言，在实现把守卫写成 `b < 0` 时会失败，成立；「`add(2,3)` 返回 5」若期望值来自实现、且实现恰好也就是唯一被测对象，则不成立。
- **DIST-002**：设计用例时须确认期望值不是第二份算法的产物。**具体禁用形态与判定细则见 `cpp-test-review` ASRT-005**，设计阶段只需排除这一点：所填的「期望值依据」若是把测得的实现输出固化成常量，就不算独立依据。
  > 示例：断言 `EXPECT_EQ(sut.add(2, 3), 5)` 形似手工算例，但若 5 是跑一遍实现抄来的，则依据实为「实现输出」，不成立；`EXPECT_EQ(sut.add(2, 3), 2 + 3)` 更糟——那是把被测算法抄进了测试。
- **DIST-003**：断言只依据**公开可观测**的返回值、副作用与状态（与 CONTRACT-004 同源）。不得在测试内开后门访问私有成员。
  > 本条只管**设计视角**：设计阶段就应选择可观测的断言点。审查侧的具体禁用形态（`friend` 夹具、`#define private public`、断言私有成员）见 `cpp-test-review` ASRT-006。

### BVA：边界值分析

- **BVA-001**：每个数值型参数/返回值必须覆盖边界两侧邻域。以接口文档的合法边界 B 为基准，对**下界与上界各取三点**：下界 `min-1`、`min`、`min+1`，上界 `max-1`、`max`、`max+1`（无符号类型取 `0` 与最大值邻域）；边界的包含/排斥语义以接口声明为准。禁止仅用典型中间值测试
  > 例：`int bytesToMbps(int bytes)` → 以领域边界（如业务规定的最大文件尺寸 `maxBytes`）两侧取值：测 `maxBytes-1`、`maxBytes`、`maxBytes+1`；`int div(int a, int b)` 额外测 `b = ±1`、结果恰好不溢出/恰好溢出的组合。缓冲区上限 `maxSize` → 测 `maxSize-1`、`maxSize`、`maxSize+1`，确认「等于上限可用、超上限拒绝」。注意：若内部涉及乘法（如 `bytes*8`），用类型上界（如 `INT_MAX`）测试的是溢出路径而非领域边界，领域边界应取业务语义下的真实极值。
- **BVA-002**：容器/序列边界——空、单元素、满容量、恰好容量上限、超容量输入各需独立用例，禁止只测「若干一般元素」
  > 如 `std::vector` 从 0→1、`capacity()` 恰好分配上限、`pop_back` 至空后再访问、扩容翻倍处的拷贝/移动语义。
- **BVA-003**：字符串边界——空串、单字符、恰好等于缓冲上限（注意 NUL 终止符占位）、超出上限、含内嵌 `\0`、多字节 UTF-8 截断处。`snprintf`/`strncpy` 类接口必须测「长度等于缓冲区大小」与「大小-1」两侧
- **BVA-004**：浮点边界——`0.0`、`-0.0`、±∞、NaN、最小正规格化数/次正规数、`epsilon` 邻域；整数恰在浮点精确表示边界内外的值（如大 `int64` 转 `double` 的精度损失）
- **BVA-005**：索引/迭代边界——`0`、`size()-1`、`size()`（越界首个）、负数（有符号索引越界）、迭代器首/末/末+1。与 `cpp-rules` 的 SEC-A002（越界）与 SEC-B001（符号混合）约束相呼应
- **BVA-006**：时间/计数边界——0 时间片、恰在超时阈值两侧（T 与 T±1ms 级）、重试上限 N 与 N+1、节流计数 0/1/N。测试侧用 fake clock 推进，见 `cpp-test-review` 的 DET-002
- **BVA-007**：状态转移边界——状态机每个状态的首/末合法动作、每条迁移的两端状态、未注册迁移（非法转移）必须确认被拒绝；状态与迁移以契约表（CONTRACT-001）所列或状态机源码为准，无显式迁移表时按「迁移是否发生」与「发生后是否可观测」两点描述，不要求先产出格式化的迁移表

### ECP：等价类划分

- **ECP-001**：每个输入维度必须划分「有效等价类」；**若存在语义非法值，必须至少一个无效等价类**，每个等价类至少一个用例。禁止用例只覆盖正常一类
  > 无效等价类：类型合法但语义非法——空、越界、负值、已关闭句柄、重复注册、并发写入等。注意：bool、全合法封闭枚举、全置位位掩码等维度不存在语义非法值，不要求划分无效类。无效等价类是边界之外的第二大覆盖盲区。
- **ECP-002**：每个有效等价类必须覆盖类内极值（最小值与最大值），不能只挑「中间舒服值」；与 BVA-001 的 B±1 互补
- **ECP-003**：枚举/离散类型——每个枚举值至少一个用例（含 sentinel：`kInvalid`、`kUnknown`、`kMax`）；位掩码/flag 组合覆盖 `0`、单个 flag、多个 flag 组合、全置位
- **ECP-004**：多个独立输入维度必须做交叉组合——每个无效等价类 × 至少一个有效等价类同时出现。禁止只单独测各维度
  > 多数 bug 藏在「两个维度单独合法、组合后非法」的交叉处；组合爆炸时可用 pairwise 缩减，但每个非法维度必须与一个合法维度组合出现。另：当两个维度存在**非平凡交互**（一个维度的合法取值集合依赖于另一维度的取值，如「编码方式」决定「长度上限」）时，必须至少含一个**有效 × 有效**组合——各维度单独合法、组合后仍非法的情形不限于「一维无效」。
- **ECP-005**：有序范围参数（百分比 0–100、角度 0–360、buffer size 1–MAX）必须测「范围外一个值」（负/超上界），确认拒绝行为及错误码/异常与越界方式匹配
- **ECP-006**：**回归覆盖**——被测单元若带有 issue 编号、历史修复记录、或源码中的 `FIXME`/`HACK`/「见 BUG-xxx」注释，必须为每个已知缺陷点设计一条用例，并在用例 ID 后缀标注关联编号（如 `TC-014 (BUG-4471)`）。
  > 回归用例是信息量最高的一类测试：它对应的是**真实发生过的**错误，而非设计者假想的边界，因此其期望值天然有外部依据（缺陷报告），也天然具区分度（修复被回退时必然变红）。有此类记录而不设计回归用例，是最不划算的覆盖缺口。

### BRP：分支/路径覆盖

- **BRP-001**：被测函数每个分支——`if/else`、`switch` 每个 case 与 `default`、三元运算符 `?:`、`&&`/`||` 短路两侧——都必须有至少一个用例分别命中真/假两翼
- **BRP-002**：循环覆盖 `0` 次（不进入）、`1` 次、`N` 次（N>1）、恰好到循环条件翻转的退出点；禁止只测「正常跑完 N 次」
- **BRP-003**：异常路径——覆盖触发异常的输入组合、异常抛出后的资源释放（RAII 析构顺序）、异常安全保证等级（basic/strong/nothrow）断言；`cpp-rules` ERR-002 声明为 `noexcept` 的函数路径用 `EXPECT_NO_THROW` 显式验证
  > 三个保证等级是 basic / strong / **nothrow**（`noexcept` 是 C++ 关键字/说明符，不是保证等级名）。strong 保证断言的是异常抛出后对象状态回滚到可观测的等价状态，需多条断言或拷贝比对，而非单条断言能直接验证。
- **BRP-004**：空值路径——`nullptr`、`std::nullopt`、空 `span`、空 `string_view`、空容器作为输入必须独立用例。空输入与非空内容是两条不同路径
- **BRP-005**：early-return / guard clause（`if (!valid) return;`）每个提前返回分支都要有对应用例；守卫子句难以覆盖时通常是 `cpp-rules` CPLX-W004 所述的重构信号

### FLT：故障注入

- **FLT-001**：依赖故障注入——被测单元依赖的外部资源（文件、网络、数据库、内存分配）必须设计故障路径用例：注入依赖返回错误码/抛异常、`std::bad_alloc`、磁盘满、连接断开、用 mock 注入超时/延迟，验证被测单元的传播、回滚与清理行为
  > 仅覆盖"输入触发"的异常（BRP-003）不够，依赖级故障注入覆盖的是"下游失败"这一独立盲区。

### CONC：并发与线程安全

- **CONC-001**：并发/线程安全用例设计——被测单元涉及共享状态时，必须设计竞态、死锁、多线程交错（interleaving）、`std::atomic` 内存序、共享状态同步的用例。以 `cpp-rules` THREAD-003/004/005（锁/条件变量/原子）与 THREAD-W008（内存序）为设计导向，验证锁、条件变量、原子操作的正确性

### RLC：资源生命周期

- **RLC-001**：资源生命周期——被测单元持有资源（文件、句柄、连接、内存）时，必须覆盖 open/close、double-close（重复释放）、use-after-close（关闭后使用）、move-from 后复用、拷贝 vs 移动语义、析构幂等性。已释放与未释放是不同路径

## Warning 检查清单

### OGN：用例组织（warning）

- **OGN-001**：边界/覆盖用例用参数化集中管理——gtest `INSTANTIATE_TEST_SUITE_P`、Catch2 `GENERATE`、doctest 子用例——避免复制粘贴 N 个几乎相同的 `TEST`；参数化使覆盖矩阵可读、可增删
- **OGN-002**：测试命名表达「场景-边界」语义（`ReturnsZero_WhenQueueEmpty`、`DivByZero_Throws`、`ExactCapacity_Ok`），使覆盖矩阵在测试列表即可审查
- **OGN-003**：设计完每个被测单元后回填「未覆盖项」，在测试中显式留 `TODO` 或注释说明原因，不建议悄悄放弃边界用例（放弃前须显式声明）

## 输出格式

> **产物落点**：本清单必须**随测试代码一起落盘**，否则 `cpp-test-review` 在事后审查（跨会话、或由独立 agent 审查）时读不到它，其设计覆盖核对会静默退化为"跳过"。
> 推荐任一形式：
> - **测试文件顶部注释块**（最可靠，与代码同生共死）：在被测单元的测试文件开头写一段 `// ===== 测试设计依据 =====`，含契约表的关键项与期望值依据；
> - 或 `docs/test-design/<单元名>.md` 等可被 review 发现的固定路径。
>
> **契约表本身也遵循此规则**——它是 review 核对 CONTRACT/EXPECT 的依据，只留在对话里等于不存在。

### 断言区分度（DIST-001）

| 用例ID | 关键断言 | 能捕获的实现错误 |

## 与其他技能协同

- `cpp-rules`：生产代码规范。测试代码不适用其规则；本技能引用的 SEC-A002（越界）、SEC-B001（符号混合）、CPLX-W004（重构信号）、ERR-002（noexcept）仅作为设计导向
- `cpp-test-review`：本技能产出的「契约表 + 用例矩阵（含期望值依据）+ 待确认契约项」是其审查时的核对输入，重点核对 CONTRACT（契约表是否含外部依据）、EXPECT（期望值依据是否属实）、DIST（断言是否具区分度）三类规则，以及 BVA/ECP/BRP 是否真实落地。契约表中的 `推测` 项是本技能主动标出的不确定处，审查时优先核对
- 设计中发现被测单元边界过多（有效等价类 >15 个）通常是接口职责过重，优先建议重构而非堆砌用例
  > **⚠️ 本条与 ECP-004 的优先级**：两者冲突时（如某单元有 16 个无效等价类，ECP-004 要求逐个交叉、本条建议重构），**以本条为设计缺陷信号，但不豁免 ECP-004**。正确做法是**两条都报**：把"维度过多"作为**接口设计缺陷**上报并建议拆分，同时仍按 ECP-004 为**拆分后的每个单元**设计交叉用例。**不得**用"建议重构"当作跳过 ECP-004 的理由——那会让高维度单元的交叉覆盖**永久缺失**，而它恰恰是最容易藏 bug 的地方。

## 豁免

- 集成测试（跨模块/端到端）：**CONTRACT/EXPECT/DIST 照常适用**（契约、期望值依据、区分度不因测试层级而放宽）；BVA/ECP 聚焦模块接口处，模块内部细节不重复覆盖；须按 `cpp-test-review` ORG-003 声明层级必要性
- 性能基准测试（`*_bench.cpp`）：不适用本技能
- 模糊测试（fuzzing）与属性测试（property-based）：不在本技能范围（BVA/ECP/BRP 聚焦手写确定性用例，fuzz/property 交由专项工具或技能）
- 与大型遗留测试集集成时，OGN-001/OGN-002（参数化/命名）可分期实施，新建用例必须遵守
- 其余规则无一例外
