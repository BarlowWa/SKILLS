# Git 提交技能

对每次提交请求，自动完成变更分析、提交信息生成、代码 / 构建配置脚本 / 文档审查、提交操作。此 skill 按以下流程执行。

代码审查、构建配置脚本审查与文档审查是三条**独立**路径：代码审查是**规则合规审查**，关注实现是否符合编码/测试/架构规则，
不替代功能测试、设计评审和人工 PR 审查；构建配置脚本审查关注 shell/CI/构建文件的可执行行为与安全风险；
文档审查关注本次文档变更是否改全、有无矛盾、是否准确。
三者都不是文风评审。

**与 `code-review` 的边界**：本技能的代码审查是**规则合规审查**——只判断代码是否符合 `code-rules` /
`test-review` / `test-author` / `arch-review` / `db-rules` 的条文，以及本次 diff 内的局部问题。它**不替代**：

- `code-review` 技能 / 内置 `/code-review`（正确性与缺陷审查、复用/简化/效率问题）；
- 功能测试与运行验证（由步骤 2 的测试/构建入口执行，不在审查 agent 内运行）；
- 设计评审（架构方案取舍）与人工 PR 审查。

本技能没有对应规则条文的缺陷，不要硬套规则 ID 上报；需要正确性审查时，提示用户另行运行 `code-review`。

## 工作流程

1. **检查状态**：运行 `git status`、`git diff --stat`、`git diff HEAD --check`（无 HEAD 时用 `git diff --cached --check`），了解变更概览并检查空白错误
2. **分析差异**：先确定提交范围与模式（三选一），后续分析、审查、提交使用**同一范围**：

   | 模式 | 范围 | 审查命令 |
   |---|---|---|
   | 全量（默认） | 工作区全部改动 + 未跟踪新文件 | `git diff HEAD` + `git ls-files --others --exclude-standard` |
   | 仅暂存区 | 索引中的内容 | `git diff --cached`（不含未暂存改动与未跟踪文件） |
   | 指定文件 | 指定路径的工作区内容 + 这些路径的未跟踪文件 | `git diff HEAD -- <路径...>` + `git ls-files --others --exclude-standard -- <路径...>` |

   - 「仅暂存区」与「指定文件」不组合；用户若要“只提交暂存区中的某几个文件”，先让其取消其它文件的暂存，
     或明确改用「指定文件」并接受工作区语义。
   - 「指定文件」提交的是这些路径的工作区内容；本模式不支持只提交索引中的部分内容。若某个指定文件存在
     分块暂存（index 与工作区不一致），必须先询问用户：接受工作区版本，或中止并先整理索引
     （例如取消其它文件的暂存后改用「仅暂存区」模式）。不得在未确认时默认工作区版本。
   - 初始提交（`git rev-parse --verify HEAD` 失败）没有 `HEAD` 基线：改用 `git diff --cached` 查看已暂存文件，
     未跟踪文件按上表列表命令处理；不带 pathspec 的 `git commit` 前确认索引中只有目标文件；
     指定文件模式可直接 `git commit -m "<提交信息>" -- <路径...>`，不会带入索引中的其它文件
     （未跟踪文件需先 `git add -- <路径...>`）。
   - 对选定范围检查空白错误：全量 `git diff HEAD --check`；仅暂存区 `git diff --cached --check`；
     指定文件 `git diff HEAD --check -- <路径...>`；初始提交用 `git diff --cached --check`。
     未跟踪文件没有 diff，需在 Read 时一并检查。
   - 再读取差异，理解变更内容。
   - 代码变更：归纳逻辑意图与影响面；检查项目测试/构建入口（README、Makefile、package.json、
     Cargo.toml、pom.xml、pyproject.toml 等）。若检测到入口，默认至少运行一次快速测试/构建并记录退出码；
     用户明确要求不运行或环境无法运行时，记录原因和风险，由用户确认。无入口写「无测试可挂」，
     并提议一个最小可运行的验证手段（临时驱动脚本 / main() 探针 / 调试器复现），同样先展示失败证据；
     纯文档变更可豁免。不要在审查 agent 内运行测试。
   - 文档变更：写出**语义增量**（改名 / 删除 / 新增规则 / 改流程 / 改路径 / 改默认值等）
     和一句话**变更意图**，供文档审查 agent 使用。
   - 构建 / 配置 / 脚本变更：归纳**变更意图**与**影响面**（哪个构建目标、部署流水线或运行环境），
     并标注是否涉及部署 / 凭证，供构建 / 配置 / 脚本审查 agent 使用。
3. **生成提交信息**：基于变更内容，按 Conventional Commits 规范生成中文摘要
4. **分类派发审查**：识别变更类别，仅对存在的类别派发独立 agent。类别**全覆盖**——每个变更文件必须落入下列三类之一，或明确落入「显式豁免」类并写明原因，不允许出现「既不是代码也不是文档」的静默落空：
   - **代码文件**（按 `code-rules` 语言路由表判定扩展名：C++ `.h/.hpp/.cpp/.cc/.cxx/.hh/.hxx/.ipp/.inl/.tpp/.cppm`、Rust `.rs`、Java `.java`、Python `.py/.pyi`；测试与基准文件；数据库脚本 `.sql`；以及**其它编程语言的源码文件**——Go `.go`、JavaScript/TypeScript `.js/.jsx/.ts/.tsx/.mjs/.cjs`、Ruby `.rb`、Kotlin `.kt/.kts`、C# `.cs`、Swift `.swift`、C `.c`、PHP `.php`、Scala `.scala`、Lua `.lua` 等，判据是「该扩展名是某种编程语言的源码」）→ 代码审查 agent。对 `code-rules` 语言路由表**无专属规则文件**的语言，代码审查 agent 仅应用 G-xxx 基线，并在报告中标注「未加载语言专属规则：<lang>」（与 `code-rules` 的既有降级口径一致）
   - **构建 / 配置 / 脚本文件**（shell/PowerShell/Batch 脚本 `.sh/.bash/.zsh/.ps1/.bat/.cmd`；CI 配置 `.github/workflows/*`、`.gitlab-ci.yml`、`Jenkinsfile`、`.circleci/*`、`azure-pipelines.yml`；构建文件 `Makefile`/`*.mk`、`Dockerfile`/`Containerfile`、`CMakeLists.txt`/`*.cmake`、`Cargo.toml`、`pom.xml`/`*.xml`、`build.gradle*`、`package.json`、`pyproject.toml`、`setup.py`、`go.mod`；配置 `.gitignore`/`.gitattributes`/`.dockerignore`、`.yml/.yaml/.toml/.ini/.conf/.properties/.json/.jsonc`、`.env.example`）→ 构建 / 配置 / 脚本审查 agent（审查要点见 `references/doc-review.md` §9；**不走代码审查**，因为 code-rules 的语言规则不覆盖这些格式，也不走文档审查，因为其约束是可执行行为而非自然语言陈述）
   > **本类只收**上述 shell / CI / 构建 / 配置 格式，**不再兜底任意文本文件**：编程语言源码一律归代码类（含路由表无规则文件的 Go/JS/TS/Ruby/Kotlin 等）；lockfile 归下方「显式豁免」类；未识别的非源码文本（如无扩展名说明文件、数据样本）按文档类或显式豁免处理并写明原因，不得静默落空
   - **文档文件**（.md/.mdx/.rst/.adoc/.txt 等自然语言文档；生成物、二进制等边界按 `references/doc-review.md` §1 处理）→ 文档审查 agent
   - **不做专项审查的类别（显式豁免，非静默落空）**：lockfile（`package-lock.json`、`yarn.lock`、`pnpm-lock.yaml`、`Cargo.lock`、`poetry.lock`、`uv.lock`、`go.sum` 等，**优先于上面的 `.json` 匹配**）与生成物——原因：由包管理器或生成器产出，逐行审阅无意义且会淹没真正变更；风险由「lockfile 变更缺少对应声明变更」与「生成物源文件未改却被改动」两条 warning 信号兜底（见 `references/doc-review.md` §9.3）。`vendor/`、`build/`、`node_modules/` 等被忽略目录不进入提交范围，同样不审。
   - 多个类别都有时，**在同一条消息中并行派发**，agent 之间互不等待；主 agent 等全部返回（或失败降级）后，再进入步骤 5
   - 均无时跳过专项审查，并在确认页注明「本次变更无代码 / 构建配置 / 文档文件，未做专项审查」
   - 审查范围必须与最终提交范围一致；若用户限定只提交部分文件，只审这些文件
   - 派发时传入实际的 `<差异命令>`、提交模式、提交范围（指定文件模式还需传入实际路径列表，即 prompt 中的「路径列表」）、`<技能根目录>`（含 code-rules 等技能的目录）与 `<本 skill 目录>`（git-commit 自身目录）的绝对路径；子 agent 看不到主对话
   - 派发文档审查 agent 时，把步骤 2 得到的**变更意图与语义增量**原样写入 prompt；派发代码审查 agent 时写入**变更意图、影响面与提交范围**；派发构建 / 配置 / 脚本审查 agent 时写入**变更意图、影响面、提交范围与是否涉及部署/凭证**
   - 审查 agent 一律只读：除报告文件外不得修改任何被 Git 跟踪的文件；不得执行 diff 中的代码；不得运行会改变状态的命令
   - 优先使用 `general-purpose`（需要运行 git 命令并写报告）；不要用 `Explore` / `Plan` 派发需要落盘报告的任务
   - 若运行环境的全局约定要求 subagent 产出落盘、只回摘要，在 prompt 末尾**原样附上全局交付模板**：
     完整报告写入 `.tmp_research/<slug>.md`，最终回复只给摘要与文件路径
   - 派发前检查目标仓库是否忽略 `.tmp_research/`（用实际报告路径：`git check-ignore -q .tmp_research/<slug>.md`；
     目录不存在时也能检查路径规则）；未忽略时把报告写到仓库外的临时目录，避免被后续 `git add` 纳入

   **代码审查 agent 指令**：
   ```
   你是一个代码审查 agent。你的任务仅限于审查即将提交的代码变更，只做规则合规与 diff 局部问题审查，
   不替代功能测试、设计评审和人工 PR 审查。只读审查：除报告文件外不得修改任何被 Git 跟踪的文件；
   不得执行 diff 中的代码；不得运行会改变状态的命令。

   步骤：
   1. 运行主 agent 指定的 `<差异命令>` 获取待提交的变更。再取未跟踪（untracked）新文件**列表**：全量模式用 `git ls-files --others --exclude-standard`，指定文件模式加 `-- <路径...>`；仅暂存区模式不取。此时只取列表，不要先读全文。不得自行改用其他 diff 命令
      提交模式：<全量 / 仅暂存区 / 指定文件>
      路径列表：<指定文件模式的实际路径；其他模式写「不适用」>
      变更意图：<一句话；未提供则写「未提供」>
      影响面：<受影响模块/调用方；未提供则写「未提供」>
      提交范围：<文件列表；全量则写「全部变更」>
   2. 仅筛选代码文件：按 `<技能根目录>/code-rules/SKILL.md` 的语言路由表识别（C++ `.h/.hpp/.cpp/.cc/.cxx/.hh/.hxx/.ipp/.inl/.tpp/.cppm`、Rust `.rs`、Java `.java`、Python `.py/.pyi`）、数据库脚本（.sql）、**其它编程语言源码**（Go `.go`、JavaScript/TypeScript `.js/.jsx/.ts/.tsx/.mjs/.cjs`、Ruby `.rb`、Kotlin `.kt/.kts`、C# `.cs`、Swift `.swift`、C `.c`、PHP `.php`、Scala `.scala`、Lua `.lua` 等；判据是「该扩展名是某种编程语言的源码」），以及各语言测试/基准路径（tests/、test/、src/test/、src/testFixtures/、benches/、test_*.py、*_test.py、*Test.java、*Tests.java、*IT.java、*_bench.*）。若主 agent 指定了提交范围，只审查该范围内的文件；筛选出的未跟踪文件需 Read 全文后再审查。可为核对调用方/接口定义读取范围外文件，但只对范围内文件出结论
   3. 如果没有代码文件变更，直接报告「无代码变更，跳过审查」后结束
   4. 读取规则文件，从 `<技能根目录>`（通常为 `~/.claude/skills/` 或项目的 `.claude/skills/`；派发时替换为实际绝对路径）加载：
      - 通用编码规则：<技能根目录>/code-rules/SKILL.md（G 基线 + 语言路由表 + 豁免）
      - C++ 规则：<技能根目录>/code-rules/references/cpp.md（存在才加载）
      - Rust 规则：<技能根目录>/code-rules/references/rust.md（存在才加载）
      - 其他语言规则：<技能根目录>/code-rules/references/<lang>.md（按路由表，存在才加载）
      - 数据库规则：<技能根目录>/db-rules/SKILL.md
      - 架构规则：<技能根目录>/arch-review/SKILL.md（仅涉及模块依赖/分层时加载）
      - 测试规则：<技能根目录>/test-review/SKILL.md（审查测试质量时一律加载）与
        <技能根目录>/test-author/SKILL.md（本次新增/修改用例时加载），另按语言加载各自 references/<lang>.md（C++ / Rust 已就绪）
   5. 对代码变更内容进行审查：
      - 生产代码：对照 code-rules 与该语言规则文件逐条检查 blocker 和 warning；语言已识别但无对应规则文件时，只应用 G-xxx 并在报告中标注「未加载语言专属规则：<lang>」
      - 测试代码：一律对照 test-review 逐条检查测试质量；本次新增/修改用例时再对照 test-author 检查用例设计（测试/基准文件不应用 code-rules 的生产代码规则）；对应语言无测试参考文件时，按 test-author/test-review 的降级路径标注「未加载语言专属细化/执行证据：<lang>」
      - 基准测试：code-rules 豁免；test-review 保留执行链判据
      - 数据库脚本：对照 db-rules 检查
      - 涉及模块依赖/分层/目录结构变更：对照 arch-review 检查
      - 注释/docstring：本次涉及变更时，核对注释描述的约束、行为与实现一致；不做文风评审
   6. 输出审查报告。每条 blocker 必须附：`文件:行`、规则 ID、违规片段原文、反证（规则条文/调用方/命令输出）；
      给不出证据的降为 warning 或标「未能判定」。warning 至少给 `文件:行` + 一句可核对的事实；修法可选
   7. 仅对 blocker 给出是否阻塞提交的结论；warning 只列建议。**报告每条结论时一并给出其来源技能、原名 ID 与原级别**
      （跨技能合并口径见主 SKILL.md「跨技能级别换算与去重」；同一问题多技能命中只报一次，取更严者）
   ```

   ```

   1. 运行主 agent 指定的 `<差异命令>` 获取待提交的变更。再取未跟踪（untracked）新文件**列表**：全量模式用
      `git ls-files --others --exclude-standard`，指定文件模式加 `-- <路径...>`；仅暂存区模式不取。

      变更意图：<一句话；未提供则写「未提供」>
      影响面：<受影响构建目标/部署流水线/运行环境；未提供则写「未提供」>

      提交范围：<文件列表；全量则写「全部变更」>
   2. 筛选本类文件（清单见主 skill 步骤 4 的「构建 / 配置 / 脚本文件」一行）。若主 agent 指定了提交范围，
      只审查该范围内的文件；筛选出的未跟踪文件需 Read 全文后再审查
   3. 读取审查指南：`<本 skill 目录>/references/doc-review.md` §9，按 §9.1 检查清单**逐行逐项**核对

   4. 如果没有本类文件变更，直接报告「无构建 / 配置 / 脚本变更，跳过审查」后结束

      筛选出的未跟踪文件需 Read 全文后再审查；可为核对引用/矛盾读取范围外文件，但只对范围内文件出结论
   4. 如果没有文档文件变更，直接报告「无文档变更，跳过审查」后结束
   5. 按指南的「完整性 / 一致性 / 准确性」三个维度逐项审查，严格遵守其证据要求与分级口径。
      主 agent 提供的变更意图、语义增量与提交范围如下，可作参考，但不得替代你自己的核对：
      变更意图：<一句话；未提供则写「未提供」>
      语义增量：<改名 / 删除 / 新增规则 / 改流程 / 改路径 / 改默认值等；未提供则写「未提供」>
      路径列表：<指定文件模式的实际路径；其他模式写「不适用」>
      提交范围：<文件列表；全量则写「全部变更」>
   6. 输出报告：每条 blocker 必须附 `文件:行`、原文引用、反证位置或命令输出；
      无法验证的声明标注「未能判定」，不得据此判 blocker
   7. 仅对 blocker 给出是否阻塞提交的结论；warning 只列建议
   ```
5. **核实审查结论**：审查 agent 的结论是意见，不是证据。合并报告前，主 agent 必须：
   - 对每条 blocker 回到 diff / 原文 / 权威来源核实：原文引用与反证是否都成立；
   - 无法核实的 blocker 降为 warning 或剔除，并在「已驳回 / 降级」段注明「未核实」及理由，不得留在 blocker 段；
   - 不静默删除有合理依据的结论；被驳回的条目保留一行说明，避免下轮重复提出
   - 「未核实」（主 agent 未复核）与「未能判定」（证据不可得）是两种状态，不得混用
   - 多个审查 agent 报同一问题时，按「跨技能级别换算与去重」合并为一条，取更严者，并保留来源技能与原名 ID
   - 审查结束后重新核对提交信息与最终 diff：type/scope/breaking 是否仍准确；审查导致代码变化时重新生成
6. **blocker 处理与复审边界**：
   - 存在**已核实 blocker** 时默认不进入提交：先修复；发生修复后，**最多复审 1 轮**（只审修复涉及的文件与受影响结论，不重跑全量审查）
   - 复审后**仍存在已核实 blocker**：**不再自动复审**，直接停在确认页，要求用户在「再次显式豁免（记录理由）」与「中止提交」之间选择；没有第三轮，也不得循环修复直到自动通过
   - 只有用户在确认页明确豁免后才可继续；每次豁免都要在下一次复审/确认页记录理由，避免同一 blocker 被反复默认豁免
   - 用户选择修改提交信息、只调整审查范围等**不涉及代码修复**的操作，**不触发复审**（也不消耗复审轮次），但须按步骤 5 重新核对受影响的结论
   - **成本边界**：复审只对「发生过修复的审查类别」各派 1 次，最坏额外派发数 = 代码 1 + 构建配置脚本 1 + 文档 1 = 3 次；之后一律停在确认页，不再派 agent
7. **用户确认**：展示提交信息 + 审查报告（含核实状态）+ 运行验证结果 + 提交顺序核对结果，请用户确认后执行；仍有已核实 blocker 时，确认页必须标注「需豁免才可提交」；已达复审上限仍不通过时，确认页明确写出「复审已达上限，需用户决定：再次豁免 / 中止」
8. **执行提交**：按用户确认的提交模式执行（见「提交执行」）

> **安全边界**：本技能只执行**本地** `git commit`，**绝不执行 `git push`**。任何推送/同步到远程的操作均需用户显式另行指示。

## 跨技能级别换算与去重

代码审查 agent 会同时加载 `code-rules`、`test-review`、`test-author`、`arch-review`、`db-rules`，这些技能的
严重级别口径并不统一（`arch-review` 三级、其余两级），**不能直接混排**。换算口径与
`plan-review/references/blocking-criteria.md` 的「与其他 skill 的级别换算」一节一致（`plan-review` 的
`plan-review/references/severity-mapping.md` 仅保留为独立核检工具，映射表已内联进 blocking-criteria），并结合本技能
「blocker = 不得提交」的语义做如下规定：

| 来源技能 | 原级别 | 本技能级别 | 理由 |
|---|---|---|---|
| `arch-review` | critical | **blocker** | 两边的最高级语义一致（结构性缺陷 / 不得提交） |
| `arch-review` | major | **warning** | **`major` 是「应修复」而不阻塞**，本技能 `blocker` 是「不得提交」，两者语义不同——不得因数值上的「最高一级」而对齐为 blocker |
| `arch-review` | minor | warning | 优化建议，仅记录 |
| `code-rules` / `test-review` / `test-author` / `db-rules` | blocker | **blocker** | 两边均为「违规内容不得提交」 |
| `code-rules` / `test-review` / `test-author` / `db-rules` | warning | warning | 两边均为不阻塞建议 |

- 本技能不设置 `minor` 级：上述所有 warning 统一按本技能 `warning` 处理，只在报告中注明原级别，不另行细分。
- **同一问题被两个及以上技能报出时只报一次**：合并为一条，**取更严者**（blocker > warning），并在报告中
  注明「来源技能 / 原名 ID / 原级别」，例如 `来源：arch-review ARCH-001 (critical) + code-rules G-RELEASE (blocker)`。
  合并后的条目按**输出级别**进入 blocker / warning 段，不再重复列出。
- 级别换算只做**降为「来源技能原级别」的映射**，不新增来源技能未报的结论；主 agent 在步骤 5 的核实可继续降级
  （只降不升）。本表与 `arch-review` 存在一处有意差异：`arch-review` 的 `major` 在本技能落 **warning**（而非 `minor`），
  因为本技能没有 `minor` 级，且其唯一「仅记录」级就是 warning；去重时仍**取更严者**，不会因这一差异放过真 blocker。
- 他技能级别口径变更时，本表须同步 `plan-review/references/severity-mapping.md` 的附录核对命令（本技能只读引用，不改该文件）。

## 提交信息规范

### 格式

```
<type>(<scope>): <中文简短描述>
```

**优先使用单行提交信息。** 详细说明仅在你明确要求时提供；footer 仅在 COMMIT-004 / COMMIT-010 / COMMIT-011 要求时提供。

**破坏性变更（breaking change）**：当变更破坏既有 API/行为时，在 type/scope 后加 `!`，并在 footer 用 `BREAKING CHANGE:` 描述：
```
<type>(<scope>)!: <描述>

BREAKING CHANGE: <破坏性说明>
```
（footer 与标题之间空一行；有正文时 footer 与正文之间空一行。仅在确属破坏性变更时使用，普通变更不加。）

### Type 类型

| Type       | 说明                         |
| ---------- | ---------------------------- |
| `feat`     | 新功能                       |
| `fix`      | 修复 bug                     |
| `docs`     | 文档/注释变更                |
| `style`    | 代码格式（不影响逻辑的空格、缩进等） |
| `refactor` | 重构（非功能、非 bug 修复）  |
| `perf`     | 性能优化                     |
| `test`     | 添加或修改测试               |
| `chore`    | 构建、工具、依赖等杂项       |
| `ci`       | CI/CD 配置变更               |
| `revert`   | 回滚之前的提交               |

### 规则

- **COMMIT-001**：标题行不超过 72 字符，使用中文描述，末尾不加句号
- **COMMIT-002**：默认仅生成单行标题，不加正文和 footer——除非用户明确要求详细说明，或 COMMIT-004 / COMMIT-010 / COMMIT-011 要求 footer
- **COMMIT-003**：若确需正文，正文每行不超过 72 字符，与标题之间空一行
- **COMMIT-004**：若变更为新功能且有相关的 issue/ticket 编号，且用户要求引用时，在 footer 引用（如 `Closes #123` / `Refs #456`，footer 与标题之间空一行；有正文时则与正文之间空一行）
- **COMMIT-005**：一次提交应围绕单一逻辑意图，避免把不相关的变更混入同一提交。检测到变更文件/内容服务于多个不相关逻辑意图时，应主动建议拆分为多个 commit 并分别生成提交信息；若同一批变更同时包含「新增/修改测试」与「修复生产代码」，必须拆成两个提交且测试提交在前（项目或运行环境有更具体约定时，以项目约定为准）。测试提交允许预期的红灯（红灯用例先提交），修复提交完成后必须全绿；确认页应区分「预期红」与「失败」。
  - **顺序必须可核对**：测试提交在前不能只靠自述，须在修复提交完成后用下列命令证明「测试文件的首次提交是修复提交的祖先」：

    ```bash
    TEST_FILE=<测试文件>               # 本次提交涉及、对应源文件修复的测试文件
    SRC_FILE=<源文件>                  # 被该测试覆盖、发生修复的源文件
    FIX_COMMIT=<修复提交>              # 用户确认的修复组提交；只提交测试组、修复尚未提交时留空
    TEST_FIRST=$(git log --diff-filter=A --format=%H -- "$TEST_FILE" | tail -1)   # 测试文件首次加入的提交

    # 证据留存：先于任何分支打印，保证每条路径都能看到两者的提交顺序与时间
    echo "--- 证据：$TEST_FILE / $SRC_FILE 的提交历史（测试文件在前）---"
    git log --format='%h %ad %s' --date=short -- "$TEST_FILE" "$SRC_FILE"
    echo "TEST_FIRST=${TEST_FIRST:-<空>}  FIX_COMMIT=${FIX_COMMIT:-<空>}"

    if [ -z "$TEST_FIRST" ]; then
      echo "不适用：测试文件不在本次提交范围"
      exit 0
    fi
    if [ -z "$FIX_COMMIT" ]; then
      echo "尚未闭合：修复提交待完成"
      exit 0
    fi
    if [ -z "$(git show --format= --name-only "$FIX_COMMIT" -- "$SRC_FILE")" ]; then
      echo "输入错误：FIX_COMMIT 未改动指定源文件，未产出顺序结论"
      exit 2
    fi
    if [ -n "$(git show --format= --name-only "$FIX_COMMIT" -- "$TEST_FILE")" ]; then
      echo "顺序未证明：测试与修复在同一提交"
      exit 2
    elif git merge-base --is-ancestor "$TEST_FIRST" "$FIX_COMMIT"; then
      echo "顺序正确"
      exit 0
    else
      echo "顺序错误：测试提交不在修复之前"
      exit 1
    fi
    ```

    判定规则（与脚本输出的五条分支一一对应，退出码 `0` 不阻断、`1` 顺序错误须阻止、`2` 需用户处理：顺序未证明或输入错误）：
    - `TEST_FIRST` 为空（测试文件不在本次提交范围）→ 「不适用：测试文件不在本次提交范围」，退出码 0，**不阻断**；
    - `FIX_COMMIT` 为空（只提交测试组，修复尚未提交）→ 「尚未闭合：修复提交待完成」，退出码 0，**不阻断**；记录「顺序核对尚未闭合」，不得宣称已通过，修复组提交后再跑一次；
    - **输入错误**（`git show --format= --name-only "$FIX_COMMIT" -- "$SRC_FILE"` 为空，即 `FIX_COMMIT` 未改动指定源文件——传入了无关提交或 `SRC_FILE` 写错）→ 「输入错误：FIX_COMMIT 未改动指定源文件，未产出顺序结论」，退出码 2，**不产出顺序结论**，由用户核对 `FIX_COMMIT` / `SRC_FILE` 后重跑；
    - **修复提交本身改动了测试文件**（`git show --format= --name-only "$FIX_COMMIT" -- "$TEST_FILE"` 非空）→ 「顺序未证明：测试与修复在同一提交」，退出码 2，覆盖「新增测试与修复同一提交」与「已有测试与修复同批修改」两种形态；要求用户拆开提交或显式接受（记录理由）；
    - 否则以 `git merge-base --is-ancestor` 退出码判定，0 为「顺序正确」（退出码 0），非 0 为「顺序错误」（退出码 1）；检出「顺序错误」时阻止继续。

    为什么 `FIX_COMMIT` 要显式传入、而不从源文件历史推导：源文件在基线中已存在时，`git log -1 -- "$SRC_FILE"` 返回的是基线提交而非空，脚本便无法区分「修复尚未提交」与「修复早于测试」——这两种情形（场景 d / c）的源文件历史从哈希上看完全一样，只能靠「当前轮是否已产出修复组提交」来分辨。故 `FIX_COMMIT` 取修复组提交的哈希，只提交测试组时留空。**脚本内置输入守卫**：在 `FIX_COMMIT` 非空判断之后、同提交判断之前，先用 `git show --format= --name-only "$FIX_COMMIT" -- "$SRC_FILE"` 确认该提交确实改动了源文件；输出为空说明传入的不是修复提交（或 `SRC_FILE` 写错），脚本输出「输入错误」并以退出码 2 结束，**不产出顺序结论**，由用户核对输入后重跑。顺序要求只关心「测试的首次加入早于修复提交」，故不把修复跨多个提交的情形纳入本脚本。确认页须留「提交顺序核对」一行，写明命令与结论。
- **COMMIT-006**：禁止生成含 `fix bug`、`update code`、`修改了一下` 等无信息量的模糊描述
- **COMMIT-007**：type 选择要准确——若变更属于多个 type，选择最主要的那一个
- **COMMIT-008**：scope 可选但推荐填写，标注影响的模块/目录/文件
- **COMMIT-009**：描述应直击核心变更，不堆砌细节；能 10 个字说清就不用 30 个字
- **COMMIT-010**：禁止在提交信息中附加 `Co-Authored-By` 等作者注脚（包括运行环境/工具自动追加的）。仅以 conventional commit 行作为提交信息，不添加任何作者行；发现自动追加时必须删除。项目 CONTRIBUTING 明确要求 `Signed-off-by` / DCO 时，仅添加该 trailer，不添加 `Co-Authored-By`。
- **COMMIT-011**：破坏性变更必须显式标注——type/scope 后加 `!`，并在 footer 用 `BREAKING CHANGE:` 描述破坏内容（有正文时与正文空一行，否则与标题空一行）
- **COMMIT-012**：文档类变更按意图选 type——纯文档新增/修订用 `docs`；文档与代码变更描述同一行为时，随代码一起提交并使用代码变更的 type；与代码无关的文档整理、润色单独提交

## 分析要点

在分析 git diff 时，关注以下信息以生成准确的提交信息，并界定代码 / 构建配置脚本 / 文档审查的范围：

- **新增内容**：新文件、新函数、新类、新功能模块
- **修改内容**：逻辑变更、bug 修复、重构、性能优化
- **删除内容**：废弃代码、无用文件、冗余逻辑
- **文档语义增量**：改名、删除、新增规则、改流程、改路径、改默认值、改示例/清单
- **文档性质**：描述当前行为 / 方案规划 / 决策记录 / 变更记录——决定准确性按什么核对
- **文档是否被机器执行**：CLAUDE.md、AGENTS.md、skills、rules 的每句话都是行为约束，
  其矛盾与失效引用的严重度高于普通说明文档
- **引用关系**：新增/改名/删除的文档是否被索引、路由表、其他文档引用
- **跨文件关联**：多个文件的变更是否服务于同一逻辑意图
- **风险判断**：变更是否涉及 API 变更、数据库变更、安全相关等，若重要可在标题中点到

## 用户确认

提交前必须展示以下内容请用户确认：

1. **变更摘要**：列出变更文件与每个文件的核心变更，并标明各文件落入的审查类别（代码 / 构建配置脚本 / 文档 / 显式豁免的 lockfile·生成物）
2. **提交信息**：完整提交信息预览
3. **审查报告**：代码、构建 / 配置 / 脚本与文档审查结果，标注每条 blocker 已核实，以及被驳回/降级的条目；多技能合并的条目注明来源技能与原名 ID
4. **运行验证**：本次是否运行测试/构建；命令与结果（通过 / 失败 / 预期红 / 未运行及原因）。
   代码变更且存在入口时默认必须运行；仅当用户明确要求或环境无法运行时才可「未运行」，并标注风险由用户确认；
   纯文档变更可豁免。测试先提交允许「预期红」，修复提交后必须全绿
5. **提交顺序核对**：涉及「测试 + 修复」拆分时，展示 COMMIT-005 的命令、两个 commit hash 与结论（顺序正确 / 顺序错误 / 顺序未证明 / 输入错误 / 尚未闭合（修复待提交））；否则写「不适用」
6. **确认提示**：询问用户是否确认提交；仍有已核实 blocker 时，确认页必须标注「需豁免才可提交」，并要求用户选择「修复」或「显式豁免」；复审已达 1 轮上限仍不通过时，标注「复审已达上限」，要求用户在「再次豁免」与「中止」之间选择

## 提交执行

用户确认后，按确认的提交模式执行：

```bash
# 全量
git add -A
git commit -m "<提交信息>"

# 仅暂存区：不再 git add
git commit -m "<提交信息>"

# 指定文件（<路径...> 为确认范围内的文件）
git add -- <路径...>
git commit -m "<提交信息>" -- <路径...>
```

- 指定文件模式下 `git commit -- <路径...>` 只提交这些路径的工作区内容，范围外已暂存的文件会保留在暂存区。
- 提交后运行 `git show --stat --oneline HEAD`，核对实际提交的文件与用户确认范围一致；不一致时立即报告。
- 再运行 `git log -1 --format=%B` 核对完整提交信息：若出现 `Co-Authored-By` 等作者注脚，必须删除后重新提交。
  `git show --stat` 不显示 footer，不能替代这一步。指定文件模式下若索引中仍有范围外暂存内容，
  清理信息必须用 `git commit --amend --only -m "<清理后的提交信息>"`，不要用裸 `--amend -m`
  （它会把整个索引带入）；重新提交后再次核对 `git show --stat --oneline HEAD` 与 `git log -1 --format=%B`。
  若环境反复自动追加且无法删除，停止并报告冲突。
- `git commit` 非零退出（hook 失败、nothing to commit、pre-commit 改写文件等）时，不得报告成功；
  说明退出码与输出，保留现场并询问用户。提交 hook 改写了文件时，重新核对 diff 与提交信息。

提交完成后报告结果（commit hash、分支名、提交信息摘要）。

## 特殊情况处理

### 工作区无变更

用 `git status --porcelain` 判断；输出为空才提示工作区干净。只有未跟踪文件时：若当前模式为全量，
纳入审查；若为仅暂存区，提示「暂存区无内容」，不要擅自切换模式；指定文件模式按指定路径处理。

### 部分提交

若用户只想提交部分文件，在步骤 1 之后询问需要提交的文件范围，然后使用「指定文件」模式；
分析、审查、提交都只针对该范围。

### 拆分提交

检测到需要拆分（多个不相关意图，或测试与修复同批）时：

1. 列出建议的提交分组（每组文件、意图、type/scope），**测试组排在修复组之前**，请用户确认；
2. 按顺序对每组执行本流程：以「指定文件」模式确认该组范围 → 审查 → 用户确认 → 提交；
3. 组间范围不得重叠；已提交的组不再改动，除非用户明确要求 amend。
4. 各组提交后，按 COMMIT-005 的脚本核对顺序（`FIX_COMMIT` 传入修复组提交哈希），结论与脚本的五条分支一一对应：
   - 只提交测试组（修复尚未提交，`FIX_COMMIT` 留空）→ 脚本输出「尚未闭合：修复提交待完成」（退出码 0，不阻断），记录该结论，不得宣称已通过；修复组提交后带上其哈希再跑一次闭合核对；
   - 测试文件不在本次提交范围 → 脚本输出「不适用：测试文件不在本次提交范围」（退出码 0）；仅提交修复组且无对应测试时属此情形；
   - `FIX_COMMIT` 未改动指定源文件（传入无关提交或 `SRC_FILE` 写错）→ 脚本输出「输入错误：FIX_COMMIT 未改动指定源文件，未产出顺序结论」（退出码 2），由用户核对输入后重跑，不产出顺序结论；
   - 修复组本身改动了测试文件（新增测试与修复同一提交，或既有测试与修复同批修改）→ 脚本输出「顺序未证明：测试与修复在同一提交」（退出码 2），要求拆开或让用户显式接受并记录理由；
   - 否则按 `git merge-base --is-ancestor <测试首提交> <修复提交>` 判定：退出码 0 为「顺序正确」，非 0 为「顺序错误」（退出码 1）并阻止继续；
   - 核对结果写入确认页/报告的「提交顺序核对」一行：命令、两个 commit hash 与结论。
5. 拆分后的每组提交信息各自生成，不复用同一标题。

### 初始提交

若 `git rev-parse --verify HEAD` 失败（仓库尚无提交），`git diff HEAD` 不可用：
按步骤 2 的初始提交说明，用 `git diff --cached` + 未跟踪列表确定范围。

### 回滚/撤销

若用户要求撤销或回滚：
- **撤销上一次提交但保留变更**：`git reset --soft HEAD~1`（变更保留在暂存区）
- **回滚已提交的变更**：`git revert <commit>`（生成反向提交，保留历史）
- 均需先展示将受影响的范围并请用户确认，不自动执行。

### 合并冲突/未完成操作

若检测到 `git status` 显示合并冲突、cherry-pick 进行中等异常状态，先提示用户处理异常状态，暂停提交流程。

### 审查 agent 失败

派发失败或 agent 未返回有效报告时，**不得视为「无问题」通过**。应说明失败原因，由主 agent 按对应指南自查：
代码侧按本次实际涉及的范围加载 code-rules + 对应语言 references + test-author/test-review + arch-review/db-rules，
`code-rules` 路由表无专属规则文件的编程语言（Go / JS / TS / Ruby / Kotlin 等）仅应用 G-xxx 基线并标注「未加载语言专属规则：<lang>」；
构建 / 配置 / 脚本侧按 `references/doc-review.md` §9 的检查清单；文档侧按 `references/doc-review.md`。
并在报告中标注「审查降级：主 agent 自查」。多类别同时降级时，各自按对应指南核对，不得只查其中一类。

### 暂存区已有内容

若 `git status` 显示暂存区已有暂存内容，询问用户：
- 提交暂存区内容（仅 `git commit`，不 `git add`）
- 只提交暂存区中的部分文件：先取消其它文件的暂存（`git reset -- <其它文件>`，需用户确认；
  该命令在初始提交/无 HEAD 时也可用），再选「提交暂存区内容」；或改用「指定文件」模式并接受工作区语义
- 包含工作区所有变更（`git add -A` + `git commit`）
- 取消操作

选择「仅提交暂存区」时，审查必须使用 `git diff --cached`，不得用 `git diff HEAD`
（后者会混入未暂存改动）；未跟踪文件也不属于此次提交范围。

### 大文件/二进制文件

若检测到变更包含大文件（>1MB）或二进制文件，在摘要中特别标注，提醒用户确认是否应提交。

### 敏感文件

若变更包含敏感文件（`.env*`、`*.pem`、`*.key`、证书、密钥、私钥、`secrets.*`、`.gitignore` 中已忽略项等），在摘要中**红色标注**并阻止直接提交，提示用户确认该文件不应进入版本控制，建议移除或加入 `.gitignore`。

### Amend 提交

若用户要求 amend（修正上一次提交），使用 `git commit --amend`。此时：
- 先展示上一次提交信息
- 展示本次新的变更
- 审查范围应覆盖「上一次提交的内容 + 本次新增变更」，而不是只审本次 diff。`git commit --amend`
  只提交索引，因此用 `git diff HEAD~1 --cached` 查看将进入 amend 的内容；无 `HEAD~1`（root 提交）时
  用 `git diff --cached $(git hash-object -t tree /dev/null)`（或 `git show HEAD` + `git diff --cached`）。
  工作区未暂存改动不会被 amend 纳入，不要混入审查范围。若上一次提交不在本会话内且无法完整获取，先向用户确认范围
- 生成修正后的提交信息供用户确认
- 提示：**不得 amend 已 push 的提交**
- 只加内容、保留原提交信息：`git commit --amend --no-edit`（会提交整个索引；若只想加入指定路径，
  用 `git commit --amend --only --no-edit -- <路径...>` 或先整理索引）
- 只改提交信息：优先 `git commit --amend --only -m "<新提交信息>"`（不改索引中的其它暂存内容）；
  若索引与 HEAD 一致，也可用普通 `git commit --amend -m "<新提交信息>"`（执行前可用 `git diff --cached --quiet` 判断）
- 两者都有：`git commit --amend --only -m "<新提交信息>" -- <路径...>`（只纳入指定路径，保留其它暂存内容）；
  若索引中只有目标内容，也可用普通 `git commit --amend -m "<新提交信息>"`
- 注意：裸 `--amend -m` 会提交整个索引；索引与 HEAD 不一致时，已暂存改动会一同进入 amend，优先用 `--only`
- **所有选项必须写在 `--` 之前**：`--` 之后一律按 pathspec 解析，`git commit --amend --only -- <路径...> --no-edit`
  会把 `--no-edit` 当成文件名并报 `error: pathspec '--no-edit' did not match any file(s) known to git`（退出码 1）。
  正确形态：`git commit --amend --only --no-edit -- <路径...>`、`git commit --amend --only -m "<信息>" -- <路径...>`
