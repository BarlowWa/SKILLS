# Git 代码提交技能

对每次代码提交请求，自动完成变更分析、提交信息生成、代码审查、提交操作。此 skill 按以下流程执行。

## 工作流程

1. **检查状态**：运行 `git status` 和 `git diff --stat` 了解变更概览
2. **分析差异**：对每个变更文件，读取关键差异（`git diff`），理解变更内容
3. **生成提交信息**：基于变更内容，按 Conventional Commits 规范生成中文摘要
4. **代码审查**：启动独立 agent 审查代码变更。仅审查代码文件（.h/.hpp/.cpp/.cc/.sql 等），对照对应技能规则检查。非代码文件跳过。

   审查 agent 指令：
   ```
   你是一个代码审查 agent。你的任务仅限于审查即将提交的代码变更。

   步骤：
   1. 运行 `git diff HEAD` 获取待提交的变更（包含暂存+未暂存）
   2. 仅筛选代码文件：C++（.h/.hpp/.cpp/.cc/.cxx/.hxx）、数据库脚本（.sql）
   3. 如果没有代码文件变更，直接报告「无代码变更，跳过审查」后结束
   4. 读取规则文件，从技能目录（通常为 .claude/skills/）加载：
      - C++ 规则：.claude/skills/cpp-rules/SKILL.md
      - 数据库规则：.claude/skills/db-rules/SKILL.md
      - 架构规则：.claude/skills/cpp-arch-review/SKILL.md（仅涉及模块依赖/分层时加载）
   5. 对代码变更内容进行审查：
      - C++ 代码：对照 cpp-rules 逐条检查 blocker 和 warning
      - 数据库脚本：对照 db-rules 检查
      - 涉及模块依赖/分层/目录结构变更：对照 cpp-arch-review 检查
   6. 输出审查报告，列出违规项及修复建议
   7. 仅对 blocker 违规给出明确结论（是否阻塞提交），warning 仅列建议
   ```
5. **用户确认**：展示提交信息 + 审查报告，请用户确认后执行
6. **执行提交**：`git add` + `git commit` 提交所有变更

## 提交信息规范

### 格式

```
<type>(<scope>): <中文简短描述>
```

**优先使用单行提交信息。** 详细说明和 footer 仅在你明确要求时提供。

### Type 类型

| Type       | 说明                         |
| ---------- | ---------------------------- |
| `feat`     | 新功能                       |
| `fix`      | 修复 bug                     |
| `docs`     | 文档/注释变更                |
| `style`    | 代码格式（不影响逻辑的空格、缩进等） |
| `refactor` | 重构（非功能、非 bug 修复）  |
| `perf`     | 性能优化                     |
| `test`     | 添加或修改测试               |
| `chore`    | 构建、工具、依赖等杂项       |
| `ci`       | CI/CD 配置变更               |
| `revert`   | 回滚之前的提交               |

### 规则

- **COMMIT-001**：标题行不超过 72 字符，使用中文描述，末尾不加句号
- **COMMIT-002**：默认仅生成单行标题，不加正文和 footer——除非用户明确要求详细说明
- **COMMIT-003**：若确需正文，正文每行不超过 72 字符，与标题之间空一行
- **COMMIT-004**：若变更为新功能且有相关的 issue/ticket 编号，且用户要求引用时，在 footer 引用
- **COMMIT-005**：一次提交应围绕单一逻辑意图，避免把不相关的变更混入同一提交
- **COMMIT-006**：禁止生成含 `fix bug`、`update code`、`修改了一下` 等无信息量的模糊描述
- **COMMIT-007**：type 选择要准确——若变更属于多个 type，选择最主要的那一个
- **COMMIT-008**：scope 可选但推荐填写，标注影响的模块/目录/文件
- **COMMIT-009**：描述应直击核心变更，不堆砌细节；能 10 个字说清就不用 30 个字
- **COMMIT-010**：禁止在提交信息中附加 `Co-Authored-By` 等末尾注脚。仅以 conventional commit 行作为提交信息，不添加任何作者行。

### 示例

```
feat(login): 新增短信验证码登录功能
```

```
fix(db): 修复存储过程死锁导致订单超时
```

```
refactor(utils): 将日期工具函数迁移至 DateTime 命名空间
```

```
chore(deps): 升级 jsoncpp 至 1.9.5
```

## 分析要点

在分析 git diff 时，关注以下信息以生成准确的提交信息：

- **新增内容**：新文件、新函数、新类、新功能模块
- **修改内容**：逻辑变更、bug 修复、重构、性能优化
- **删除内容**：废弃代码、无用文件、冗余逻辑
- **跨文件关联**：多个文件的变更是否服务于同一逻辑意图
- **风险判断**：变更是否涉及 API 变更、数据库变更、安全相关等，若重要可在标题中点到

## 用户确认

提交前必须展示以下内容请用户确认：

1. **变更摘要**：列出变更文件列表及每个文件的核心变更
2. **提交信息**：完整提交信息预览
3. **审查报告**：agent 审查结果，标注是否有 blocker（阻塞提交）
4. **确认提示**：询问用户是否确认提交

## 提交执行

用户确认后执行：

```bash
git add <变更文件>
git commit -m "<提交信息>"
```

提交完成后报告结果（commit hash、分支名、提交信息摘要）。

## 特殊情况处理

### 工作区无变更

提示用户当前工作区干净，无内容可提交。

### 部分提交

若用户只想提交部分文件，在步骤 1 之后询问需要提交的文件范围，然后仅分析指定文件。

### 合并冲突/未完成操作

若检测到 `git status` 显示合并冲突、cherry-pick 进行中等异常状态，先提示用户处理异常状态，暂停提交流程。

### 暂存区已有内容

若 `git status` 显示暂存区已有暂存内容，询问用户：
- 提交暂存区内容（仅 `git commit`，不 `git add`）
- 包含工作区所有变更（`git add -A` + `git commit`）
- 取消操作

### 大文件/二进制文件

若检测到变更包含大文件（>1MB）或二进制文件，在摘要中特别标注，提醒用户确认是否应提交。

### Amend 提交

若用户要求 amend（修正上一次提交），使用 `git commit --amend`。此时：
- 先展示上一次提交信息
- 展示本次新的变更
- 生成修正后的提交信息供用户确认
