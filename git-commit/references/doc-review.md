# 文档变更审查指南

供 git-commit 派发的文档审查 agent 使用。审查对象是**本次提交涉及的文档变更**，判断三件事：
改全了吗（完整性）、有没有矛盾（一致性）、说得对吗（准确性）。
不做全库审计，不做文风评审。

本文是文档审查的唯一细则来源；SKILL.md 只负责触发与派发，不重复这里的范围与判据。

## 1. 范围

### 纳入

- Markdown / MDX / RST / AsciiDoc / 纯文本说明等以自然语言为主的文档
- 手工维护的 README、CHANGELOG、ADR、CLAUDE.md / AGENTS.md、skills 与规则文档、`docs/` 下的指南

### 不纳入

- 生成物（自动生成的 API 文档、自动生成的 CHANGELOG、lockfile）、`vendor/` `build/` `node_modules/` 等目录
- 代码文件中的注释与 docstring（随代码审查处理）
- 纯格式重排且无语义变化（diff 仅涉及空白、换行、标点）

> 图片 / PDF 等二进制不纳入文本审查，但仍需核对引用与位置是否有效；Read 能读取时，
> 核对图文内容与文档描述一致。
>
> 手工维护 / 自动生成的判定：文件头含 `generated` / `do not edit` 标记，或由 release 工具产出。
> 「源文件未改而生成物被改动」是独立的 warning 信号（生成物疑似手工修改），不作为分类依据。

### 按读者分流（影响判级）

| 文档类型 | 例子 | 审查侧重 |
|---|---|---|
| 面向 agent 的规范 | CLAUDE.md、AGENTS.md、skills、rules | 每句都是行为约束；矛盾与歧义优先按高严重度处理 |
| 面向人的指南 | README、`docs/guides`、tutorial | 准确性、步骤可执行、前后一致 |
| 决策记录 | ADR、RFC、proposal | 核对历史事实与内部自洽；**不要求与当前代码一致**，除非自称描述当前行为 |
| 变更记录 | 手工维护的 CHANGELOG | 版本、日期、条目与对应提交/版本一致 |

## 2. 输入与准备

1. 按主 agent 指定的 `<差异命令>` 获取变更：全量用 `git diff HEAD`，仅暂存区用
   `git diff --cached`，指定文件使用主 agent 传入的完整命令（路径已包含在 `<差异命令>` 中；
   仅在主 agent 未包含时追加 `-- <路径...>`）。初始提交（无 HEAD）用 `git diff --cached`。
   **不得自行改用其他模式**——仅暂存区却用 `git diff HEAD` 会把不会提交的改动纳入审查。
   未跟踪文件不在 diff 中，需另取列表：全量用 `git ls-files --others --exclude-standard`，
   指定文件再加 `-- <路径...>`；仅暂存区模式不取。先按 §1 筛选，再对命中的文档 Read 全文。
2. 记录主 agent 给出的变更意图与语义增量；未提供时从 diff 归纳，并在报告中注明「意图为推断」。
   主 agent 的归纳只作起点，仍须自行核对
3. 若仓库有文档工具入口（package.json scripts、Makefile、mkdocs.yml、sphinx、vale.ini、
   markdownlint 配置、链接检查脚本），先运行**只读的** lint / build --check / 链接检查目标；
   会改写文件的命令加 `--check` / `--dry-run` 或先询问。失败输出可作为证据，但要区分文档缺陷
   与工具/环境故障——后者标「未能判定」，不计为文档缺陷。没有工具则手工核查

## 3. 维度一：完整性（是否改全了）

先写出**语义增量**：这次到底改了什么（改名 / 删除 / 新增规则 / 改默认值 / 改流程 /
改路径 / 改示例 / 改清单）。

然后：

1. 提取旧标识与新标识：旧/新文件名、路径、规则编号（如 G-xxx、COMMIT-xxx）、
   命令与参数、配置键、API/字段名、skill/模块名、章节标题、URL。
2. 在仓库内检索旧标识与相关术语（`rg`；排除 `.git`、`vendor`、`node_modules`、`build`、生成物）。
3. 逐个判断命中点是否被本次变更弄失效：
   - 未修改文件中仍指向旧名称/旧行为 → **悬挂引用**
   - 索引 / 路由表 / 目录 / 导航 / README 清单未收录新文件 → **孤儿文档**
   - 同一规则在多处镜像陈述，只改了一处 → **不一致副本**
4. 检查对称位置：同一族条目（多语言规则、多个 skill、多个平台/版本）是否都改；
   只改一部分时，判断是刻意（有说明）还是遗漏。
5. 检查数量、版本、支持矩阵、文件清单是否随变更更新。
6. 新增文档是否可达（被索引/路由/父文档引用）；删除或改名文档是否有入链残留。
7. 若本次只提交部分文件：被本次文档引用的文件是否已在 HEAD 或本次提交范围内？
   引用未跟踪/未提交的文件，会让提交后的 HEAD 断链（即使工作区看起来正常）。

结论只能二选一：

- **已覆盖**：列出检索过的旧标识与目录；
- **发现遗漏**：给出 `文件:行` 与命中原文。

「感觉可能还有别处」但无检索证据 → warning「未发现具体遗漏」，不得报 blocker。

## 4. 维度二：一致性（是否矛盾）

1. 抽取变更文档中的**规范性陈述**：必须 / 禁止 / 仅 / 一律 / 优先 / 不得 / 不适用 / 豁免 / 例外 / 默认。
2. 对每个陈述，检索同一主题的其他表述，比较：
   - 触发条件与适用范围
   - 强度（必须 vs 建议）
   - 例外清单
   - 数量、编号、路径、命令
3. 先查同一文件内部（改动段 vs 未改动段），再查跨文件（路由表、豁免表、相邻 skill/规则、README 索引）。
4. 权威顺序：仓库显式规定的优先级 > 代码/配置/测试的实际行为 > 规范性文档 > 教程与示例。
   两份规范性文档冲突时不要替作者选边，并列引用双方原文与位置，交用户裁决。
5. 检查是否把「单一事实来源」变成了副本：新增一段与别处重复的规则（而非指针）时，
   若仓库有单一来源约定，报 warning。

**只有语义冲突才算矛盾**：同义改写、语序调整、拆分段落不算。判断标准是
「按 A 做还是按 B 做，读者会得到不同行为」。
无法确定语义是否冲突时，记 warning 并并列原文，不判 blocker。

## 5. 维度三：准确性（是否说对了）

对每条**可验证的具体声明**逐一核对：

| 声明类型 | 核对手段 |
|---|---|
| 文件 / 目录 / 路径 | Glob / `git ls-files`（注意大小写；Windows 文件系统不敏感，CI 通常敏感） |
| 命令 / 参数 / 脚本 | `--help`、脚本源码、Makefile / package.json 入口；不执行破坏性命令 |
| 规则编号 / 章节锚点 | 全文检索确认存在，且指向内容与引用描述一致 |
| API / 配置键 / 字段 | 代码或 schema 中存在，默认值与描述一致 |
| 版本 / 依赖 | manifest / lockfile / 实际输出 |
| 外部 URL | 优先用环境提供的抓取工具（本环境 WebFetch 被拦截，用 `~/.claude/skills/fetch-page/scripts/fetch.py`）；网络不可用时标「未能判定」，不判错 |
| 内部链接 | 相对路径按文档所在目录解析；锚点按标题 slug 粗查 |

核对规则：

- 每条具体声明都要找到可验证的目标；找不到就标「未能判定」，不得据此判 blocker。
- 代码示例不必完整运行，但其中的 API/参数/输出必须能在代码中核对；可安全执行（只读、无副作用）时优先执行。
- 内部链接的大小写以 `git ls-files` 为准（Windows 文件系统不敏感，CI 通常敏感）。
- 新引入的死链可报 blocker；既有死链只报 warning（仅限本次审查范围内发现的；范围外按 §6 不报）。
- 文档自述为方案/规划/目标，或位于 `decisions/`、`rfcs/`、`proposal/` 等路径时，
  不用当前代码否定它；只查它与自身或既有规范的矛盾。

三类错误：

- **错误**：与权威来源直接冲突，能给出反证；
- **过时**：来源已变更而文档未跟随（本次变更暴露的尤其要查）；
- **不精确**：方向对但条件/边界缺失 → 通常 warning。

## 6. 分级

### Blocker（阻塞提交）

每条 blocker 必须同时具备：`文件:行`、原文引用、反证位置或命令输出。

| 编号 | 判据 |
|---|---|
| DOC-B1 | 本次新增/修改的规范性陈述与权威来源矛盾，照做会出错 |
| DOC-B2 | 本次变更使其他文档/路由/索引中的引用失效，且已定位到具体位置 |
| DOC-B3 | 本次新增/修改的路径、命令、规则编号、API、配置键确认不存在或与描述不符 |
| DOC-B4 | 删除关键内容且未在别处补齐，造成自相矛盾或步骤不可执行 |
| DOC-B5 | 违反仓库中明确标注为强制的文档规范 |

### Warning（不阻塞）

- 可能有遗漏，但无检索证据；
- 无法验证的声明（外部服务、环境相关、无法读取的图片/附件）；
- 术语 / 格式 / 锚点 / 标题层级问题；
- 检索时偶然发现的既有漂移：仅当本次变更使其失效时才报 warning；否则不报（本审查不做全库审计）；
- 影响理解的文风问题（纯偏好不报）。

## 7. 误报抑制与已知边界

1. **无证据不报 blocker**；缺任一项证据 → 降 warning 或标「未能判定」。
2. 不审查未触及内容，除非本次变更使其失效；out-of-scope 改进只作建议。
3. 不把文风当缺陷；不要求翻译/镜像文档同步，除非仓库有明确约定。
4. 不臆测意图：无法判断遗漏还是刻意省略时，提问或记 warning。
5. **无法验证 ≠ 错误**。
6. 去重：同一根因合并为一条，列出所有位置。
7. **本审查只能覆盖**可由 diff 与仓库内容证明的问题。
   **不能覆盖**：产品意图、外部系统真实行为、图片/图表的视觉正确性（只能核对可读取的文字与描述）、
   运行时表现、读者理解成本、全库范围内的概念性缺失。这些标注「超出审查范围」，不伪装成结论。
8. 不替代 CI（链接检查、lint、文档构建）与人工评审；发现系统性问题作为建议提出，
   不要求在本次提交解决。
9. 术语：**未核实** = 主 agent 未复核该条结论；**未能判定** = 证据不可得。
   二者不得混用，也不得用「未能判定」掩盖没做的检查。
10. **触发边界**：本审查只在本次提交包含文档文件时启动。若代码改了 API/CLI/配置
    但没有任何文档改动，本审查不会被触发；这类「代码 → 文档」漂移需由项目的 CI 规则、
    文档新鲜度检查或人工评审兜底。

## 8. 输出格式

```
### 文档审查

**审查范围**：<N 个文件>
**变更意图**：<一句话；推断则标注>
**语义增量**：<改名 / 删除 / 新增规则 / 改流程 / 改路径 / 改默认值等>
**完整性检索**：<旧标识列表 + 检索目录>

#### Blocker
- [DOC-B2] `path:line` — <一句话问题>
  原文：「…」
  反证：<文件:行 / 命令输出>
  建议：<修法>

#### Warning
- [warning] `path:line` — <问题>；证据：<…>；建议：<…>

#### 已核对
- 完整性：<做了什么检索>
- 一致性：<核对了哪些规范/文件>
- 准确性：<核对了哪些声明>
```

无 blocker 时写「文档侧无 blocker，可提交」（代码/运行验证由主 agent 合并）。
