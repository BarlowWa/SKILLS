# 项目架构审查

对项目做架构级静态分析，输出结构性问题与改进建议。规则按**证据可得性**分两层：语言无关的依赖/分层/耦合判据在本文；构建系统产物、依赖图提取方式、源码级 ABI 等**依赖语言工具链**的证据与规则在 `references/<lang>.md`。

## 工作流程

1. **识别语言与构建系统**：按扩展名与构建文件（CMake/Makefile、Cargo.toml、pom.xml/build.gradle、pyproject.toml/setup.py）判定。多语言仓库按模块分别判定，并按模块登记所用语言。
2. **加载语言参考**：`Read` 命中的 `references/<lang>.md`（依赖图提取、构建产物路径、语言专属规则）。
   - **语言已识别但无参考文件** → 只应用本文的 ARCH 规则，并在报告顶部标注 `⚠️ 未加载语言专属证据与规则：<lang>`；依赖图需自行从源码推导并说明推导方式。
   - **无法识别语言** → 同上，并注明依据。
   > **路由优先级**：先按构建文件（Cargo.toml/pom.xml/pyproject.toml/CMakeLists.txt）再按扩展名判定；两者冲突时以构建文件为准并注明，不得因扩展名未命中而静默跳过。
3. **扫描结构**：构建目录树与模块清单，**先声明模块定义口径**（见下）。
4. **构建依赖图**：按参考文件给出的方式提取模块间依赖；不可用时从源码推导并明示方法。
5. **按维度检查**：分层 → 循环依赖 → 接口暴露 → 目录结构 → 耦合/内聚 → 依赖方向 → 全局状态 → 构建结构 → API/ABI。
6. **输出报告**：按下方格式，问题表标注证据来源（构建产物 / 源码推导）。

## 模块定义

所有计数阈值（公开类型数量、入度/出度等）均以「模块」为单元。按优先级确定模块边界，并在报告中声明采用的口径：

| 语言 | 首选 | 次选 | 辅助 |
| ---- | ---- | ---- | ---- |
| C++ | CMake target（`add_library` / `add_executable`） | 顶层目录 | 命名空间 |
| Rust | crate（Cargo.toml 内的 lib/bin） | 模块目录 | — |
| Java | Maven/Gradle module | 包（顶层 package） | — |
| Python | 发行包（pyproject 的 packages） | 顶层目录 | — |

## 严重级别

| 级别 | 含义 |
|------|------|
| critical | 架构缺陷，阻碍演进，必须重构 |
| major | 设计问题，增加维护成本，应修复 |
| minor | 优化建议，可逐步改进 |

## 检查维度（语言无关）

### 1. 模块依赖与分层

- **ARCH-001**：上层不得被下层依赖。若 UI 层模块被平台层模块引用，属于 critical 分层倒置。
- **ARCH-002**：单向依赖原则。同一层内模块保持低耦合，跨层依赖统一向下，属于 major。
- **ARCH-003**：第三方库必须通过适配层隔离，业务代码不得直接依赖第三方 API 的具象类型，属于 major。

> 项目未声明分层时按单层处理：跳过 ARCH-001/002，**其余维度照常检查**。

### 2. 循环依赖

- **ARCH-004**：模块间禁止循环引用。任意长度的模块环（A→B→A、A→B→C→A）均判 critical——危害不随环长递减，更长的环更难发现、更难拆解。
- **ARCH-005**：循环依赖落在**声明/接口边界**（如头文件或模块接口互相包含）时，属于 major；用前向声明、接口抽取或分层打破，见语言参考。
- **ARCH-006**：允许同一模块内的类型相互引用；但同一模块内 3 个以上类型形成引用环时，升级为 major。

分析方法：对模块依赖图做强连通分量检测（DFS/Tarjan）；构建系统的 target 级依赖环见语言参考。

### 3. 接口暴露

- **ARCH-007**：public 接口不得暴露实现细节类型（内部类型、第三方类型、仅在实现中需要的依赖），属于 minor。普通私有成员不违规。
- **ARCH-008**：模块对外接口应精简。一个模块暴露超过 15 个公开类型/函数时，考虑拆分为子模块，属于 minor。
- **ARCH-009**：禁止巨型定义文件（>500 行），拆分或引入实现隐藏惯用法，属于 minor。

### 4. 目录结构

- **ARCH-010**：目录结构应反映架构分层，命名一致（如 `platform/`、`business/`、`ui/`），属于 minor。
- **ARCH-011**：同一模块的声明与实现应在同一目录，或采用清晰的 `include/` 与 `src/`（等价分层）分离，属于 minor。
- **ARCH-012**：无主文件不得散布在项目根目录，所有代码归属明确模块，属于 minor。

### 5. 耦合度指标

- **ARCH-013**：God Module——被 8 个以上模块依赖的模块，应拆分为接口 + 实现，属于 major。
- **ARCH-014**：高扇出——依赖超过 10 个其他模块的模块，检查职责是否过重，属于 major。
- **ARCH-015**：孤立模块——无入度也无出度，确认存在必要，属于 minor。

### 5.1 内聚度

- **ARCH-024**：模块职责单一。识别同一模块混合多个不相关职责（数据访问 + 业务计算 + UI 渲染同处一模块），属于 major。
- **ARCH-025**：抽象层次一致。识别高层抽象与底层细节混排（业务逻辑直接操作裸内存/系统调用），属于 major。

### 5.2 依赖方向与接口隔离

- **ARCH-026**：依赖倒置（DIP）——高层模块依赖抽象而非具体实现；无法替换实现的直接依赖属于 major。
- **ARCH-027**：接口隔离（ISP）——接口按客户端需求切分，禁止胖接口，属于 minor。

### 6. 全局状态

- **ARCH-016**：全局单例/静态可变状态跨模块暴露属于 major，优先依赖注入。
- **ARCH-017**：初始化顺序依赖——模块级全局对象的初始化互相依赖且无显式顺序保证，属于 critical。

## 注意事项

- 第三方目录（`third_party/`、`vendor/`、`external/`、`node_modules/`）默认排除审查。
- 测试目录参与依赖分析但规则放宽（允许依赖被测模块）。
- 无测试/生成代码不计入耦合度阈值。
- **判据只负责发现形态，定性必须结合根因**——形态吻合不等于缺陷（如平台适配层反向依赖属正当），证据不足时记「未能判定」，不得记为通过。

## 与其他技能协同

- `code-rules`（编码规范）负责**单文件内**问题（前向声明、平台 API 隔离、全局对象禁止）；本技能负责**模块/依赖/分层/ABI** 级问题。重叠处口径：
  - 循环依赖：`code-rules`（C++：cpp.md）PLAT-004 管文件级"用前向声明减少包含"，本技能 ARCH-004/005/006 管模块级依赖图成环；
  - 全局静态：`code-rules`（C++：cpp.md）INIT-001 管"禁止全局对象"，本技能 ARCH-016/017 管"已存在/必须存在的全局态如何跨模块暴露"；
  - 平台隔离：`code-rules`（C++：cpp.md）PLAT-001 管"OS 专有 API 隔离"，本技能 ARCH-003 管"第三方库适配层隔离"；
  - 第三方封装：`code-rules`（C++：cpp.md）PLAT-003 管"第三方原生句柄/指针必须二次封装"，本技能 ARCH-003 管"模块级适配层与依赖方向"。
- `test-author` / `test-review`：测试目录按『注意事项』放宽；测试设计归 `test-author`、测试质量审查归 `test-review`，本技能不审查测试代码。
