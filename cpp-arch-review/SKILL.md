# C++ 项目架构审查

对 C++ 项目进行架构级静态分析，输出结构性问题与改进建议。

## 工作流程

1. **扫描结构**：遍历头文件和源文件，构建目录树与模块清单
2. **构建依赖图**：分析 `#include` 关系，生成模块间依赖矩阵
3. **分层检查**：识别分层架构（若存在），检测分层违规
4. **耦合分析**：计算模块间耦合度，识别 God Module / 循环依赖
5. **接口审计**：检查头文件暴露范围，识别过度暴露
6. **输出报告**：按下方格式输出结构化审查结果

## 严重级别

| 级别 | 含义 |
|------|------|
| critical | 架构缺陷，阻碍演进，必须重构 |
| major | 设计问题，增加维护成本，应修复 |
| minor | 优化建议，可逐步改进 |

## 检查维度

### 1. 模块依赖与分层

**Q: 是否有显式分层？**
识别项目是否按以下经典分层（或自定义分层）：

```
Application / UI
     ↓
  Business Logic
     ↓
  Core / Service
     ↓
  Platform / HAL
     ↓
  Third-party / External
```

检查要点：
- **ARCH-001**：上层不得被下层依赖。若 UI 层文件被 Platform 层 `#include`，属于 critical 分层倒置
- **ARCH-002**：单向依赖原则。同一层内模块应保持低耦合，跨层依赖统一向下
- **ARCH-003**：第三方库必须通过适配层隔离。业务代码直接 `#include` 第三方头文件属于 major 违规

### 2. 循环依赖

- **ARCH-004**：模块间禁止循环引用。A → B → A 为 critical；A → B → C → A（3 跳及以上）为 major
- **ARCH-005**：头文件与源文件之间不应出现循环 `#include`
- **ARCH-006**：允许同一模块内的类相互引用（如 Manager ↔ Worker），但若同一模块内 3 个以上类形成引用环，升级为 major

分析方法：
- 构建 `#include` 有向图，用 DFS/Tarjan 算法检测强连通分量
- 检查 `CMakeLists.txt` / `Makefile` 中的 target_link_libraries 循环

### 3. 头文件接口暴露

- **ARCH-007**：public 头文件不应暴露实现细节。头文件中出现 `private` 成员、实现类的 `#include`、PIMPL 之外的内部类型，属于 minor
- **ARCH-008**：模块对外接口应精简。一个模块暴露超过 15 个公开类/函数时，考虑拆分为子模块
- **ARCH-009**：禁止巨型头文件（>500 行）。拆分或引入 PIMPL 惯用法

### 4. 目录结构

- **ARCH-010**：目录结构应反映架构分层，命名一致（如 `platform/`、`business/`、`ui/`）
- **ARCH-011**：同一模块的 `.h` 和 `.cpp` 应在同一目录或清楚的 `include/` / `src/` 分离下
- **ARCH-012**：无主文件散布在项目根目录。所有代码应归属明确模块

### 5. 耦合度指标

- **ARCH-013**：God Module 检测——被 8 个以上其他模块依赖的模块，应拆分为接口 + 实现
- **ARCH-014**：高扇出模块——依赖超过 10 个其他模块的模块，应检查是否职责过重
- **ARCH-015**：孤立模块——既无入度也无出度的模块，应确认是否有存在的必要

### 6. 全局状态与静态对象

- **ARCH-016**：全局单例/静态对象跨模块暴露属于 major。优先依赖注入替代全局访问
- **ARCH-017**：静态初始化顺序依赖（SIOF）风险——不同编译单元之间的全局对象互相引用属于 critical

### 7. Build 结构

- **ARCH-018**：检查 CMake / Makefile 中 target_link_libraries 的 PUBLIC / PRIVATE / INTERFACE 使用是否合理
- **ARCH-019**：纯头文件库（header-only lib）应有明确理由；无理由的 header-only 大型库属于 minor

## 注意事项

- 若项目未声明分层架构，默认为单层（扁平结构），此时跳过分层违规检查（ARCH-001），仅检查循环依赖和耦合度
- 第三方库目录（`third_party/`、`vendor/`、`external/`）默认排除审查
- 测试目录（`tests/`、`test/`、`unittest/`）参与依赖分析但规则放宽（如允许依赖被测模块）
- 纯头文件库（如 Catch2、nlohmann/json）默认不审查
