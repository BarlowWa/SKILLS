# C++ 项目架构审查

对 C++ 项目进行架构级静态分析，输出结构性问题与改进建议。

## 工作流程

1. **扫描结构**：遍历头文件和源文件，构建目录树与模块清单
2. **构建依赖图**：分析 `#include` 关系，生成模块间依赖矩阵
3. **分层检查**：识别分层架构（若存在），检测分层违规
4. **耦合分析**：计算模块间耦合度，识别 God Module / 循环依赖
5. **接口审计**：检查头文件暴露范围，识别过度暴露
6. **输出报告**：按下方格式输出结构化审查结果

## 模块定义

本技能所有计数阈值（公开类数量、入度/出度、循环环长等）均以「模块」为单元。默认按以下优先级确定模块边界：

1. **CMake target / 构建目标**（`add_library` / `add_executable`）——首选；
2. **目录**（一个顶层目录 = 一个模块）；
3. **命名空间**（作为目录粒度的辅助划分）。

审查开始时应声明采用的模块定义口径，并在报告中统一使用，确保阈值可复现。

## 严重级别

| 级别 | 含义 |
|------|------|
| critical | 架构缺陷，阻碍演进，必须重构 |
| major | 设计问题，增加维护成本，应修复 |
| minor | 优化建议，可逐步改进 |

## 检查维度

### 1. 模块依赖与分层

**Q: 是否有显式分层？**
识别项目是否按以下经典分层（或自定义分层）：

```
Application / UI
     ↓
  Business Logic
     ↓
  Core / Service
     ↓
  Platform / HAL
     ↓
  Third-party / External
```

检查要点：
- **ARCH-001**：上层不得被下层依赖。若 UI 层文件被 Platform 层 `#include`，属于 critical 分层倒置
- **ARCH-002**：单向依赖原则。同一层内模块应保持低耦合，跨层依赖统一向下，属于 major
- **ARCH-003**：第三方库必须通过适配层隔离。业务代码直接 `#include` 第三方头文件属于 major 违规

### 2. 循环依赖

- **ARCH-004**：模块间禁止循环引用。任意长度的模块环（A → B → A、A → B → C → A 等）均判为 critical——循环依赖的危害不随环长递减，更长的环更难发现、更难拆解
- **ARCH-005**：头文件之间不应出现循环 `#include`（源文件按约定不被 `#include`，循环包含实际发生在头文件之间）；用前向声明打破头文件包含环，属于 major
- **ARCH-006**：允许同一模块内的类相互引用（如 Manager ↔ Worker），但若同一模块内 3 个以上类形成引用环，升级为 major

分析方法：
- 构建 `#include` 有向图，用 DFS/Tarjan 算法检测强连通分量
- 检查 `CMakeLists.txt` / `Makefile` 中的 target_link_libraries 循环

### 3. 头文件接口暴露

- **ARCH-007**：public 头文件不应暴露实现细节。违规对象是**成员暴露了实现细节类型**（private/protected 成员引用了需 include 内部头/第三方头的类型、实现类的 `#include`、PIMPL 之外的内部嵌套类型），属于 minor。普通 private 数据成员不违规（与 cpp-rules OOP-005"成员默认 private"一致）
- **ARCH-008**：模块对外接口应精简。一个模块暴露超过 15 个公开类/函数时，考虑拆分为子模块，属于 minor
- **ARCH-009**：禁止巨型头文件（>500 行）。拆分或引入 PIMPL 惯用法，属于 minor

### 4. 目录结构

- **ARCH-010**：目录结构应反映架构分层，命名一致（如 `platform/`、`business/`、`ui/`），属于 minor
- **ARCH-011**：同一模块的 `.h` 和 `.cpp` 应在同一目录或清楚的 `include/` / `src/` 分离下，属于 minor
- **ARCH-012**：无主文件散布在项目根目录。所有代码应归属明确模块，属于 minor

### 5. 耦合度指标

- **ARCH-013**：God Module 检测——被 8 个以上其他模块依赖的模块，应拆分为接口 + 实现，属于 major
- **ARCH-014**：高扇出模块——依赖超过 10 个其他模块的模块，应检查是否职责过重，属于 major
- **ARCH-015**：孤立模块——既无入度也无出度的模块，应确认是否有存在的必要，属于 minor

### 5.1 内聚度

- **ARCH-024**：模块职责单一——一个模块应围绕单一职责组织。识别同一模块内混合多个不相关职责（如数据访问、业务计算、UI 渲染同处一模块），属于 major
- **ARCH-025**：抽象层次一致——同一模块内代码应处于相近抽象层次。识别高层抽象与底层细节混排（如业务逻辑直接操作裸内存/系统调用），属于 major

### 5.2 依赖方向与接口隔离

- **ARCH-026**：依赖倒置原则（DIP）——高层模块应依赖抽象（接口/抽象基类）而非具体实现。识别高层模块直接依赖具体实现类、无法替换实现的场景，属于 major
- **ARCH-027**：接口隔离原则（ISP）——接口应按客户端需求切分，禁止胖接口（一个接口同时暴露多个客户端只需其中一部分的方法）。识别单一庞大接口应拆分为多个小接口的场景，属于 minor

### 6. 全局状态与静态对象

- **ARCH-016**：全局单例/静态对象跨模块暴露属于 major。优先依赖注入替代全局访问
- **ARCH-017**：静态初始化顺序依赖（SIOF）风险——不同编译单元之间的全局对象互相引用属于 critical

### 7. Build 结构

- **ARCH-018**：检查 CMake / Makefile 中 target_link_libraries 的 PUBLIC / PRIVATE / INTERFACE 使用是否合理，属于 minor
- **ARCH-019**：纯头文件库（header-only lib）应有明确理由；无理由的 header-only 大型库属于 minor

### 8. API/ABI 兼容性

> 本维度主要适用于对外发布共享库（.so / .dll）或公开 API 的项目。纯内部单体应用可跳过本维度所有规则。ABI 精确分析建议搭配 `abidiff`（libabigail）等专用工具，本维度聚焦源码级别的风险识别。

- **ARCH-020**：公开头文件中的函数签名变更（修改返回类型、增删参数、修改默认参数值）必须评估向后兼容性，记录在变更说明中。新增重载 + 保留旧签名是兼容变更的首选方式，属于 major
  > LLM 的语义理解优势：区分"源码级兼容扩展"与"ABI 破坏性修改"。注意：给函数增加默认参数仅**源码级**兼容，对已发布共享库仍是 ABI 破坏（函数 mangled name 改变，旧符号消失），必须与"新增重载"区分对待。
- **ARCH-021**：发布共享库的项目：已发布类中新增虚函数（影响 vtable 布局）、重排成员变量顺序（影响内存布局）、修改内联函数体（可能被调用方内联后不更新）属于 critical
  > 本条为源码级**启发式检查**，精确 ABI 差异验证需搭配 `abidiff`。LLM 可识别风险模式，但不能替代二进制级别的兼容性工具。仅适用于对外发布共享库的项目，纯内部单体应用跳过。
- **ARCH-022**：对外二进制库必须显式控制符号导出——Windows 使用 `__declspec(dllexport/dllimport)` 宏、Linux/macOS 使用 `__attribute__((visibility("default")))`。禁止默认全导出（增大攻击面和 ABI 约束面），属于 major
  > 检查是否有不该导出的内部符号被暴露、是否有该导出的公开 API 被遗漏。
- **ARCH-023**：对外发布的 SDK/框架建议规划版本化接口策略——如 `inline namespace v1`/`v2` 或单独的版本化头文件目录，确保不同版本可并存。本条为 minor 级别，仅适用于有明确长期 API 稳定性需求的项目

## 审查输出格式

```
## 架构审查报告

**项目**：<项目名或路径>
**模块数**：N 个
**总文件数**：N 个（.h N, .cpp N）

### 分层图

> 若项目为扁平结构（无显式分层），跳过此图，改为输出模块拓扑图（按依赖方向排列模块节点及 edges）。
>
> 若项目有分层，按以下格式输出：

<ASCII 分层图，标注当前分层与违规箭头>

### 依赖矩阵

> 方向语义：**行模块依赖列模块（row → col）**，即某行的 ✓ 表示"行模块 #include 列模块"。行和 = 该模块的出度（依赖了多少模块），列和 = 该模块的入度（被多少模块依赖）。

|       | ModA | ModB | ModC | 出度 |
|-------|------|------|------|------|
| ModA  |  -   |  ✓   |      |  1   |
| ModB  |      |  -   |  ✓   |  1   |
| ModC  |  ✓   |      |  -   |  1   |
| 入度  |  1   |  1   |  1   |      |

> 注：上表 ModA → ModB → ModC → ModA 构成 3 模块循环依赖（ARCH-004 critical），此处仅为演示矩阵写法。

### 发现问题

| ID | 级别 | 标题 | 位置 | 说明与建议 |
|----|------|------|------|------------|
| ARCH-001 | critical | 底层依赖上层 | platform/window.h → ui/main_window.h | 移除该 include，将公共类型下沉至 core 层 |
| ARCH-004 | critical | 循环依赖 | business/ ↔ core/ | 提取公共接口到单独模块 |

### 总结

- Critical：N 项 —— 必须重构
- Major：N 项 —— 应修复
- Minor：N 项 —— 可逐步改进

### 重构建议优先级

1. <最高优先级问题>
2. <次高优先级问题>
...
```

## 注意事项

- 若项目未声明分层架构，默认为单层（扁平结构），此时跳过分层违规检查（ARCH-001），仅检查循环依赖和耦合度
- 第三方库目录（`third_party/`、`vendor/`、`external/`）默认排除审查
- 测试目录（`tests/`、`test/`、`unittest/`）参与依赖分析但规则放宽（如允许依赖被测模块）
- 纯头文件库（如 Catch2、nlohmann/json）默认不审查

## 与其他技能协同

- `cpp-rules`（编码规范）负责**单文件内**问题（前向声明打破循环、平台 API 隔离、全局对象禁止），本技能负责**模块/依赖/分层/ABI** 级问题。二者重叠处口径如下：
  - 循环依赖：`cpp-rules PLAT-004` 管文件级"用前向声明减少包含"，本技能 `ARCH-004/005/006` 管模块级依赖图成环；
  - 全局静态/SIOF：`cpp-rules INIT-001` 管"禁止全局对象"，本技能 `ARCH-016/017` 管"已存在/必须存在的全局态如何跨模块暴露（DI 替代）"；
  - 平台隔离：`cpp-rules PLAT-001` 管"OS 专有 API 隔离"，本技能 `ARCH-003` 管"第三方库适配层隔离"；
  - 第三方封装：`cpp-rules PLAT-003` 管"第三方原生句柄/指针必须二次封装"，本技能 `ARCH-003` 管"模块级适配层与依赖方向"（业务代码可否直接 `#include` 第三方头）。
- `cpp-test-author` / `cpp-test-review`：测试目录按本技能"注意事项"放宽处理；测试用例设计归 `cpp-test-author`、测试质量审查归 `cpp-test-review`，本技能不审查测试代码。
