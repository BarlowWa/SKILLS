# 证据与限制

本文说明 `SKILL.md` 中每条结论的来源、强度与已知限制。**引用前核对**：这些材料有时效性，
Anthropic 官方对多 agent 的立场在 2025–2026 年间有明显变化。

## 一、证据等级

| 等级 | 含义 | 可信度 |
|---|---|---|
| 文档 | 官方文档正文 | 高（契约级，但会随版本变） |
| 内置 | 从 `/code-review`、`/deep-research` 实现读到的机制 | 高（官方每天在跑） |
| 论文 | 受控实验 / 失败分类学 | 中高（依赖实验设定） |
| 本地 | 本仓库经审计的 skill 实践 | 中（样本小，但同环境） |
| 校准 | 本技能拟定的默认值 | **低（无外部依据）** |

## 二、结论与来源

### 不该按工作类型拆成多个常驻 agent

- 官方（2026-01）：多 agent 只在三种情况下稳定优于单 agent——上下文污染导致效果下降、任务可并行、
  专业化改善工具选择或聚焦；其余情况协调成本超过收益。
- 官方：按问题类型拆分（写功能 / 写测试 / 审代码）产生持续协调开销，每次交接丢上下文；
  **planner / implementer / tester / reviewer 分工的实验中，子 agent 花在协调上的 token 多于干活**；
  「同一工作的顺序阶段」被列为有问题的分解边界。
- 官方（2026-10）：单 agent + skills 经常在质量上胜过 subagent 设计，成本与延迟更低；按团队/问题类型
  各配一个 subagent 会让 agent 架构变成组织架构图。

### 多 agent 的收益与代价

- 官方：多 agent 通常比单 agent 多用 3–10× token；研究系统约 15×（普通 agent 约 4×）。
- 论文（受控实验，260 配置 / 6 基准 / 5 架构）：相对单 agent 从 +80.8%（可分解金融任务）到
  −70.0%（顺序规划）；顺序任务全面退化 −39%~−70%；单 agent 基线超过 45% 后，增加 agent 为负收益；
  无集中验证的架构错误放大 17.2×，集中式 4.4×；多 agent token 为单 agent 的 1.6–6.2×，工作冗余 41–50%。
- 官方：并行化的主要收益是彻底性，不是速度。

### 为什么验收要独立

- 官方：模型评价自己的产出时「可靠地偏正面」。
- 论文：无外部反馈时，模型的自我纠正无效甚至退化。
- 论文（Who&When，127 个多 agent 系统的失败日志）：识别责任 agent 准确率 53.5%，
  **定位失败步骤仅 14.2%**——所以核对只能核对可验证的产物，不能依赖对过程的叙事性审查。
- 内置 `/code-review` 的评审者与实现者上下文隔离；内置 `/deep-research` 用 3 票对抗验证，
  不确定时默认「refuted=true」。

### 黑盒验证是有效的拆分边界

- 官方：验证者只需跑测试并报告结果，不需要实现上下文；验证子 agent 之所以有效，
  是因为天然只需极少上下文传递。
- 官方（反方，必须一并保留）：更强的 orchestrator 越来越能直接评估子 agent 产出，
  验证子 agent 只在 orchestrator 较弱、需要专用工具、或需要显式检查点时值得。

### 失败分类学

- 论文（MAST，1600+ traces / 7 框架 / κ=0.88）：14 种失败模式，3 类；步骤重复 15.7%、知行不一 13.2%、
  不知何时停 12.4%、违反任务规格 11.8%、错误验证 9.1%、无/不全验证 8.2%、任务漂移 7.4%；
  7 个开源多 agent 系统失败率 41%–86.7%。

### 内置实现的具体机制

- `/code-review`：Scope 先行并嵌入每个 prompt；按角度分 finder；verifier 按 (file, line) 分组；
  三态判定 CONFIRMED / PLAUSIBLE / REFUTED；高投入档加 sweep；综合步只返回索引与合并关系；
  装配时只要有余量就回填，不静默丢。
- `/deep-research`：Scope → 搜索 → 去重 → 抓取提取（声明 2–5 条**可证伪** claim）→ 3 票对抗验证
  （2 票驳倒即杀，不确定默认驳倒）→ 综合；全 verifier 失败时报「基础设施故障，不是研究结论」；
  预算上限（最多抓 15 个来源、最多验 25 条 claim）并记录被丢弃项。

## 三、已知限制（引用时不要省略）

1. **官方「单 agent + skills 常胜」是结论性断言**：原文只说「in our comparisons across several
   enterprise deployments」，未公布对比数据。
2. **成本个例不可外推**：planner/generator/evaluator harness 的 $200/6h vs $9/20min 是单次任务案例。
3. **45% 阈值来自特定基准**（金融 / 规划 / 工作流 / 浏览），不能外推到所有任务。
4. **研究任务的收益不能套到写代码**：官方明确多数编码任务真正可并行的部分少于研究任务。
5. **厂商自述的评审效果无方法论**（如「每个 PR 抓 2 个 bug、58% severe」）。
6. **本技能的组合方式是推断**：每条约数有出处，但「主控 skill + Scope + 四态验收 + 索引回填」
   这一组合没有任何人发表过，属工程判断。
7. **档位阈值与派发预算无依据**：S/M/L 判据、0/4/10 的直接派发上限、800 字摘要上限、汇总门槛 15 条均为校准值。
8. **内置实现是版本快照**：`/code-review`、`/deep-research` 的实现随 CLI 版本变化，
   本机读取版本为 2.1.212；升级后应复核。
9. **子 agent 嵌套与并发是版本相关参数**：默认嵌套 3 层、并发 20（workflow 16、可调 1–256、
   单次 parallel/pipeline 4096、每 run 1000）——数值随版本变化。
10. **fork 模式影响等待语义**：内部版本 2.1.212 默认关闭，较新版本在交互式会话默认开启；
    开启时主 agent 无法等待子 agent。串行阶段必须显式确认等待行为。
11. **`code-review` 与 `deep-research` 是内置能力，不在本仓库**：它们是编译进 Claude Code 的
    skill / workflow，不是 `~/.claude/skills/` 下的目录。本技能引用的是它们的**行为约定**，
    具体参数（票数、上限、档位）随 CLI 版本变化。
12. **`plan-review` 的三态与本技能四态的映射是对齐约定，不是原技能的一部分**：本技能用
    通过→无条件、有条件通过→PARTIAL、不通过→FAIL 的映射并入验收记录；该映射由本技能维护，
    `plan-review` 若改变判据须同步。

## 四、建议的验证

在真实任务上做小规模对照：1 个 S、1 个 M、1 个 L，各记录派发数、token、返工次数、用户干预次数。
外部证据再强，也不如本环境的实测数据。
