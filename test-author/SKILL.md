# 测试用例设计

对被测单元做**主动的用例设计**。设计之前先厘清契约（CONTRACT），设计之中系统性覆盖边界、等价类与分支路径（BVA/ECP/BRP），设计之后确认期望值有来源（EXPECT）、断言有区分度（DIST）。与 `test-review`（落地后的质量审查）互补，形成「先设计、后审查」闭环。

## 适用范围

- **被测对象**：函数、方法、类、状态机等单元（具体语言与扩展名见路由表）
- **使用时机**：新增测试文件、为已有测试补充用例、重构后重估覆盖、需求变更引入新边界时
- **测试框架**：框架无关；各语言常用框架与惯用写法见 `references/<lang>.md`
- **不适用**：生产代码编码规范（由 `code-rules` 负责）；测试代码质量审查（由 `test-review` 负责）；模块架构审查（由 `arch-review` 负责）

> **路由优先级**：先按扩展名/构建文件判定语言，再看是否属于测试路径。扩展名能唯一确定语言、但目录不在上表时（如仓库外置的 `add_test.rs`），仍按该语言处理，并在输出中注明判定依据——不得因路径未命中而静默降级或跳过。

> **加载动作**：路由命中后必须用 `Read` 读取 `references/<lang>.md`——绝对路径以**本 SKILL.md 所在目录**为基准拼接（例：本文件位于 `~/.claude/skills/test-author/SKILL.md` 时，读 `~/.claude/skills/test-author/references/rust.md`）。路由判定与加载是两个动作：命中即加载，不得只判定不读取。输出时在 `语言 / 已加载参考` 字段写明**实际加载**的文件名。


**降级**：语言已识别但参考文件不存在 → 只应用本文规则（全部语言中立），并在输出顶部标注 `⚠️ 未加载语言专属细化：<lang>`；无法识别语言 → 同上并注明。不得静默跳过。

## 工作流程

1. **契约分析**：产出契约表并标注每项依据来源，单列「推测项」（CONTRACT-001/002）；自相矛盾时先确认（CONTRACT-003）
2. **加载语言参考**：按上方路由表用 `Read` 读取 `references/<lang>.md`（绝对路径以本 SKILL.md 所在目录为基准），并在输出 `语言 / 已加载参考` 字段写明实际加载的文件；未加载时按降级段标注 `⚠️ 未加载语言专属细化：<lang>`，不得静默跳过
3. **识别被测单元**：列出全部输入维度（参数、全局状态、环境）与输出空间
4. **输入空间分析**：划分有效/无效范围，标记边界点（BVA）与等价类（ECP）
5. **设计用例**：按 BVA/ECP/BRP 生成清单，每条标注期望值依据（EXPECT-001）与覆盖规则编号
6. **区分度自查**：逐条核对断言是否具区分度（DIST-001）、是否混入镜像实现（DIST-002）
7. **结构化组织**：边界用例参数化集中管理、命名表达场景语义（OGN 的语言写法见参考文件）
8. **输出**：契约表 + 用例矩阵 + 区分度表 + 未覆盖项 + 待确认契约项，作为 `test-review` 的核对输入

## 严重级别

| 级别    | 含义                                                          |
| ------- | ------------------------------------------------------------- |
| blocker | 必须设计到位，缺失将导致测试无法判定真伪——契约不明（CONTRACT）、期望值无依据（EXPECT）、断言无区分度（DIST），或边界/覆盖盲区（BVA/ECP/BRP/FLT/CONC/RLC） |
| warning | 建议项，改善可维护性与可读性，不阻塞                          |

## Blocker 检查清单

### CONTRACT：契约与前置分析

- **CONTRACT-001**：设计用例前必须产出契约表：**前置条件**、**后置条件**、**不变量**（含跨多次调用的序列不变量）、**副作用**（可观测的）、**错误契约**（哪些输入会失败、以何种方式失败——错误码 / 异常类型 / 断言中止）。缺少错误契约时边界用例无法判定「该接受还是该拒绝」。
  > 契约不明确的单元，「正确」本身就是未知数——任何用例都只是把猜测固化成断言。契约表的**依据**列至少一项必须来自被测代码之外（规格文档、协议标准、既有调用点），不得全部落在「接口声明」。
- **CONTRACT-002**：每项契约必须标注依据来源：`规格文档` / `接口声明` / `调用方约定` / `协议或业界标准` / `推测`。标为 `推测` 的项必须**集中单列**，不得混在确认项中。
  > 若依据列被整列填成 `接口声明`，回头确认：该行为真是声明中写明的，还是从实现反推的？
- **CONTRACT-003**：契约不明或自相矛盾时，必须先向用户提出并确认，禁止默默选一种继续。确需推进的，标为 `推测` 并列入「待确认契约项」。
- **CONTRACT-004**：契约表只列**可观测**的前置/后置/副作用；测试不得依赖不可观测的内部中间状态（与 `test-review` ASRT-006 衔接）。

### EXPECT：期望值可追溯

- **EXPECT-001**：每条用例的期望值必须标注依据：`规格条目` / `契约表·<项名>` / `手工计算算例（须写明算法）` / `协议或业界标准` / `异源参考实现`。
  > **禁止**把「被测实现的当前行为」当依据——那是复述实现。跑一遍实现、把输出抄成字面量同样属于此列：断言写成字面量还是表达式，不改变「期望值来自实现」这一事实。标为 `异源参考实现` 的须写明来源与为何不同源；同源实现不得作依据（见 DIST-002）。
- **EXPECT-002**：每条用例至少一条依据**不得来自本仓库**（规格条目、协议/业界标准、独立手工算例、异源参考实现之一）。
  > 全部依据落在「契约表」或「接口声明」上时，可追溯性退化为自环——契约表本身也是设计者产出的。

### DIST：断言区分度

- **DIST-001**：每条用例的**关键断言**须给出「何种符合契约的实现错误会被它捕获」的具体理由；至少要有一个可被实现错误证伪的断言。
  > 例：「`b == 0` 时返回除零错误」的断言，在实现把守卫写成 `b < 0` 时会失败，成立；「`add(2,3)` 返回 5」若期望值来自实现、且实现就是唯一被测对象，则不成立。
- **DIST-002**：期望值不得是第二份算法的产物。**具体禁用形态见 `test-review` ASRT-005**；设计阶段只需排除：所填「期望值依据」若是把测得的实现输出固化成常量，就不算独立依据。
  > `assert(add(2,3)) == 5` 形似手工算例，但若 5 是跑一遍实现抄来的，依据实为「实现输出」；`assert add(2,3) == 2+3` 更糟——把被测算法抄进了测试。
- **DIST-003**：断言只依据**公开可观测**的返回值、副作用与状态（与 CONTRACT-004 同源），不得开后门访问私有成员。
  > 设计视角：设计阶段就应选可观测的断言点。审查侧的禁用形态（friend 夹具、解除私有可见性、断言私有成员）见 `test-review` ASRT-006。

### BVA：边界值分析

- **BVA-001**：每个数值型参数/返回值覆盖边界两侧邻域。以接口文档的合法边界 B 为基准，**下界与上界各取三点**：`min-1`、`min`、`min+1`，`max-1`、`max`、`max+1`（无符号类型取 `0` 与最大值邻域）；包含/排斥语义以接口声明为准。禁止仅测典型中间值。
  > 若内部涉及乘法/累加，用类型上界测的是**溢出路径**而非领域边界；领域边界取业务语义下的真实极值。
- **BVA-002**：容器/序列边界——空、单元素、满容量、恰好容量上限、超容量输入各需独立用例，禁止只测「若干一般元素」（语言细节见参考文件）。
- **BVA-003**：字符串/字节序列边界——空、单元素、恰好等于缓冲上限（注意终止符 / 长度前缀占位）、超出上限、含内嵌零字节、多字节编码在截断边界处的处理（语言细节见参考文件）。
- **BVA-004**：浮点边界——`0.0`、`-0.0`、±∞、NaN、最小正规格化数/次正规数、`epsilon` 邻域；整数恰在浮点精确表示边界内外的值。
- **BVA-005**：索引/迭代边界——首元素、末元素、越界首个、负数（有符号索引）、迭代器首/末/末+1；与 `code-rules` 对应语言的越界/符号混合规则呼应（C++：`references/cpp.md` SEC-A002、SEC-B001）。
- **BVA-006**：时间/计数边界——0 时间片、恰在超时阈值两侧、重试上限 N 与 N+1、节流计数 0/1/N。测试侧用可注入的假时钟，见 `test-review` DET-002。
- **BVA-007**：状态转移边界——状态机每状态的首/末合法动作、每条迁移两端、未注册迁移必须确认被拒绝；无显式迁移表时按「迁移是否发生」与「发生后是否可观测」描述，不强制先产出格式化迁移表。

### ECP：等价类划分

- **ECP-001**：每个输入维度必须划分有效等价类；**存在语义非法值时至少一个无效等价类**，每类至少一个用例。禁止只覆盖正常类。
  > 无效等价类：类型合法但语义非法——空、越界、负值、已关闭句柄、重复注册、并发写入。bool、全合法封闭枚举、全置位位掩码不存在语义非法值，不要求无效类。
- **ECP-002**：每个有效等价类覆盖类内极值（最小与最大），不只挑「中间舒服值」；与 BVA-001 互补。
- **ECP-003**：枚举/离散类型——每个枚举值至少一个用例（含 sentinel：`Invalid`、`Unknown`、`Max`）；位掩码覆盖 `0`、单 flag、多 flag 组合、全置位。
- **ECP-004**：多独立输入维度必须交叉组合——每个无效等价类 × 至少一个有效等价类。禁止只单独测各维度。
  > 多数 bug 藏在「各自合法、组合非法」处；组合爆炸可用 pairwise 缩减，但每个非法维度必须与一个合法维度组合出现。当两维度存在**非平凡交互**（一维合法集合依赖另一维取值）时，必须至少含一个**有效 × 有效**组合。
- **ECP-005**：有序范围参数（百分比 0–100、角度 0–360、buffer size 1–MAX）必须测「范围外一个值」，确认拒绝行为及错误码/异常与越界方式匹配。
- **ECP-006**：**回归覆盖**——被测单元若带 issue 编号、历史修复记录、或源码中 `FIXME`/`HACK`/「见 BUG-xxx」注释，必须为每个已知缺陷点设计一条用例，并在用例 ID 后缀标注关联编号（如 `TC-014 (BUG-4471)`）。
  > 回归用例信息量最高：它对应**真实发生过**的错误，期望值天然有外部依据（缺陷报告），修复被回退时必然变红。

### BRP：分支/路径覆盖

- **BRP-001**：被测函数每个分支——条件语句两翼、`switch`/`match` 每个 case 与 default、三元/条件表达式、逻辑运算短路两侧——都必须有至少一个用例分别命中。
- **BRP-002**：循环覆盖 `0` 次（不进入）、`1` 次、`N` 次（N>1）、恰好到循环条件翻转的退出点；禁止只测「正常跑完 N 次」。
- **BRP-003**：异常/错误路径——覆盖触发异常的输入组合、抛出后的资源释放与对象状态回滚、异常安全/错误传播保证等级断言（语言细节见参考文件）。
  > 三个异常安全保证等级是 basic / strong / nothrow（`noexcept` 是 C++ 关键字，不是等级名）。strong 保证断言的是异常后对象状态回滚到可观测的等价状态，需多条断言或拷贝比对。
- **BRP-004**：空值/缺失路径——空指针、空值（`None`/`null`/`nullopt`）、空集合作为输入必须独立用例；空输入与非空内容是两条不同路径（语言写法见参考文件）。
- **BRP-005**：early-return / guard clause（`if (!valid) return;`）每个提前返回分支都要有对应用例；守卫难覆盖时通常是 `code-rules` 复杂度规则（C++：CPLX-W004）指出的重构信号。

### FLT：故障注入

- **FLT-001**：被测单元依赖的外部资源（文件、网络、数据库、内存分配）必须设计故障路径用例：注入依赖返回错误/抛异常、内存分配失败、磁盘满、连接断开、超时/延迟，验证传播、回滚与清理行为。
  > 仅覆盖"输入触发"的错误（BRP-003）不够；依赖级故障注入覆盖"下游失败"这一独立盲区。

### CONC：并发

- **CONC-001**：被测单元涉及共享状态时，必须设计竞态、死锁、多线程交错（interleaving）、内存序/可见性、共享状态同步的用例；以 `code-rules` 对应语言的共享状态/锁/内存序规则为设计导向（C++：`references/cpp.md` THREAD-003/004/005、THREAD-W008；语言原语见参考文件）。

### RLC：资源生命周期

- **RLC-001**：被测单元持有资源（文件、句柄、连接、内存）时，必须覆盖获取/释放、重复释放、释放后使用、移动/转移后复用、拷贝 vs 移动语义、析构幂等性。已释放与未释放是不同路径。
  > 语言相关：C++ move-from 状态、Rust 所有权转移、Java/Python 的 close/finalizer 语义见参考文件。

## Warning 检查清单

### OGN：用例组织

- **OGN-001**：边界/覆盖用例用参数化集中管理，避免复制粘贴 N 个几乎相同的用例；参数化使覆盖矩阵可读可增删（语言写法见参考文件）。
- **OGN-002**：测试命名表达「场景-边界」语义（`ReturnsZero_WhenQueueEmpty`、`DivByZero_Throws`、`ExactCapacity_Ok`），使覆盖矩阵在测试列表即可审查。
- **OGN-003**：设计完每个被测单元后回填「未覆盖项」，在测试中显式留 `TODO` 或注释说明原因；放弃边界用例前须显式声明。

## 与其他技能协同

- `code-rules`：生产代码规范。测试代码不适用其**语言规则**（`G-SECRET` / `G-CMDINJ` 两条基线仍适用，见 `code-rules/SKILL.md`『豁免』）；文中引用的语言规则 ID（C++ 的 SEC-A002、SEC-B001、CPLX-W004、THREAD-003/004/005 等，Java 的 JAVA-COLL-*/JAVA-NUM-* 等）仅作设计导向，其他语言按其参考文件对应条目。
- `test-review`：本技能产出的「契约表 + 用例矩阵 + 区分度表 + 未覆盖项 + 待确认契约项」是其核对输入，重点核对 CONTRACT/EXPECT/DIST 与 BVA/ECP/BRP 是否落地。`推测` 项与未覆盖项优先核对。
- **接口职责过重信号**：有效等价类/维度 >15 个时优先建议重构，但**不豁免 ECP-004**——应同时把「维度过多」作为接口缺陷上报，并仍为拆分后的每个单元设计交叉用例。不得用"建议重构"跳过交叉覆盖。

## 豁免

- 集成测试（跨模块/端到端）：CONTRACT/EXPECT/DIST 照常适用；BVA/ECP 聚焦模块接口处，内部细节不重复覆盖；须声明层级必要性（见 `test-review` ORG-003）。
- 性能基准测试：不适用本技能。
- 模糊测试（fuzzing）与属性测试（property-based）：不在本技能范围（聚焦手写确定性用例）。
- 与大型遗留测试集集成时，OGN-001/002（参数化/命名）可分期实施，新建用例必须遵守。
- 通用规则与语言参考冲突时**取更严者**；其余规则无一例外。
