# 审查协议：把「审查」做成可判定的事

**横切层**：所有体裁定稿前都走这一份。它与 `wording.md` 同级——`wording.md` 管措辞，
本文件管**审查本身怎么执行、结论怎么分级**。

它不是体裁 reference：体裁专属的「审查对象与证据形态」放在 §9，其余内容跨体裁通用。

## 0. 为什么需要协议

**执行者不验收自己的产物**：同上下文的自我复核只算编辑，不算验收；未独立验收的必须在交付里声明。
验收要有**证据原件**（命令＋输出＋退出码），拿不到证据就记「未能判定」，不能当成通过。

没有协议时，审查会退化成两种东西：**只会挑毛病**（不可用），或**走过场**（更糟，因为它冒充了
「已审查」这个结论）。协议的价值不在于发现率，而在于**每条结论都可被第三方复核**。

> **审查必须在全新上下文中执行。** 做不到时**必须声明「这不是审查」，不得降级冒充**——
> 同上下文自审的判别力显著下降，且审查者会偏向自己刚写的东西。

## 1. 每条问题必须带三样

| 字段 | 说明 |
|---|---|
| **处置** | 必修／建议改／明确不改／待确认。**四类都须显式声明**（该类为空时写「本轮为空」） |
| **证据状态** | **实测**（坐标／命令输出／原始数据）／**线索**（推断、按公式估）／**推测** |
| **protects**（仅必修） | 保护哪条官方条款、验收标准或用户场景 |

**证据状态决定能升到多高**：实测 → 可到必修；**线索 → 最高只能到建议改**；推测 → 只能待确认。

这条堵死一整类错误：**按字数估算列宽**得出的「表格溢出 2.06 in」，天生不可能被判为必修。

**命名为「处置」而非「严重级」**，因为四项里混了两种东西：必修／建议改是**程度**，
明确不改／待确认是**处置动作**。混在一个枚举里再要求「每档都必须出现」，会逼出
「纯口味既要占位又不计入结论」这类自相矛盾。声明的是**类别存在性**，不是结论。

## 2. 必修的判据（须同时满足一条判据＋有 protects）

- **实测复现**：有坐标、原始输出证明照现状交付会错
- **验收不可判定**：交付物无法证明满足自己声明的标准
- **单向门**：撤回成本远高于现在改
- **现场可被当场问倒**：有具体提问人／场景，现答案站不住

**必修必须挂 protects，写不出的降为建议改。** 这样「必修」可判定，不靠审查者语气强弱。

> **证据强约束不是绝对禁令。** 医学领域的 GRADE 体系同样限制「低确定性证据 → 强推荐」，
> 但它列出了五种允许例外的范式情形（危及生命、获益相当但某选项明显更安全等）。
> 证据档位：**文献结论**，但本 skill 未取到 GRADE 原文、仅据二手转述，
> 故此处只作**类比**，不据此改动本协议的硬上限。
> 本协议目前的「线索最高只能到建议改」是**硬上限，没有例外通道**——这是一处已知的结构性
> 取舍：宁可漏掉「后果严重但证据只到线索」的问题，也不让推测混进必修。
> **遇到这类问题时的正确做法**：把它写成「待确认 + 说明后果严重性」，交用户裁决，
> 而不是自作主张升格。

## 3. 明确不改要拆成四类

混在一起会稀释证据价值：

| 子类 | 须给出 |
|---|---|
| **已证伪** | 复测方法（命令／参数／坐标）＋若按原报告改会怎样 |
| **成立但收益不抵成本** | 收益／风险比较 ＋ **Revisit if**（什么条件下应改） |
| **纯口味** | 标明「无判据，不构成审查意见」，**不计入结论** |
| **超出范围** | 指出归属范围 |

**三个补充子类**——问题成立，但不属于上面四类，容易无处安放：

| 子类 | 说明 | 为什么不等于「超出范围」 |
|---|---|---|
| **需产品决策 / 需上级批准** | 审查者无权判定，但问题本身成立 | 就在本次范围内，只是拍板权不在审查者 |
| **上游依赖未就绪** | 等业务方确认口径、等甲方下发模板 | 卡的是**时间**，不是范围 |
| **当前阶段不适用** | 结题要求不能拿来要求立项材料 | 判据随阶段变化，不是范围问题 |

「只会挑毛病的审查不可用」——所以「明确不改」必须分类给出理由，**不能只说「还差什么」**。

> `Revisit if` 是本协议里最有原创性的字段：常见做法里找不到**等价的「触发条件」字段**——
> Bugzilla 的 Resolution 与 ADR 的 Status 只记录**当前**状态（是否解决、是否被取代），
> 技术债的触发条件散见于实践、无标准写法。都能表达「将来条件变了要不要重看」，
> 但没有一个把它做成必填项。`Revisit if` 把「现在不改」变成**将来可自动触发再审的条件**，
> 而不是一句主观判断。照写。
>
> 证据档位：**从业经验**（对上述几套实践的比较归纳，非文献结论）。

## 4. 对抗过度审查

**「没有完美，只有更好」要放在协议顶层，不是放在结尾的注意事项里。**
审查的目的不是把问题数量降到零，而是**让交付物在已知边界内站得住**。

三条硬约束：

1. **补内容必须由 protects 驱动。** 说不出这条补充保护了哪条要求，就不要补。
   「这样更完整」不是理由——完整性不在优先级前列（见 SKILL.md §0）。
2. **每轮结论要给数量分布。** 只报「必修 N 条」会激励多报必修；报「必修 N / 建议改 M /
   明确不改 K / 待确认 J」才能看出审查者是不是在凑数。
3. **审查者的产出是判断，不是工作量。** 一份只写「本轮无必修，三条建议，两条明确不改（附理由）」
   的报告，比一份列了二十条的建议清单更有用。

## 5. 单列「被证伪」表，每条两列必填

| 栏 | 为什么必须 |
|---|---|
| **复测方法** | 命令／参数／坐标，让第三个人能判断证伪本身可不可信 |
| **若按原报告改会怎样** | 没有这一栏，「证伪」只是另一个意见 |

范例：「按字数估算需 14.10 in，实际渲染右缘 12.50 in 未越界；**若按原报告重排列宽，会把
12.04 拉到 14.10，反而真的越界**」。

**这张表解决的是**：防止按错误的上游报告返工、甚至改坏。没有它，下一个接手的人会把同样的
错误再犯一遍。

## 6. 未执行 ≠ 没发现问题

审查者超时、抓不到文件、工具失败，状态记为 **`not run`**，**绝不能算作零发现**。
裁决时报两个数字：

```
surface pass  = 通过 / 已执行
effective pass = 通过 / (已执行 − 受阻)
```

这是 PARTIAL 被悄悄算成 PASS 的唯一入口。**报告结尾固定写「本轮未覆盖什么」**，
开头固定写「本轮不审什么」——两头对称，缺一头就等于默许读者认为覆盖全了。

> **实证背景**：结构化 checklist 的价值不在发现率，而在**可复核性**。
> 有一项针对软件审查的经典研究（Porter et al., IEEE TSE 1995）发现，
> **用 checklist 的审查组并不比临时（Ad hoc）审查组更有效**。这警告的是「加了表格就以为提高了质量」，
> 而不是「不该用协议」——协议保证的是**别人能核你的结论**，这正是它不可替代的地方。
> 证据档位：**【文献结论】**（同行评议的对照研究）；「结构化审查的收益按风险选择性启用
> 而非一律强制」这一推论属**推断**。

## 7. 常见失效方式（照着自查）

| 失效 | 表现 | 防法 |
|---|---|---|
| **打勾走过场** | 表填满了，但没人真的执行 | 每条须带**证据原件**；「已检查」不算证据 |
| **偏好污染** | 审查者按自己的审美判级 | 必修必须挂 protects；纯口味单列且不计入 |
| **多报必修** | 用「必修」的数量证明审查有价值 | 必修有四条判据门槛；写不出 protects 的一律降级 |
| **只挑毛病** | 只说「还差什么」，不给不改的理由 | 明确不改必带四类之一 + 理由 |
| **未执行记零发现** | 超时的部分被当作「没问题」 | `not run` 单列，两个 pass 数分开报 |
| **规则密度过高** | 规则太多、互相冲突，执行者挑最容易的 | 同一件事只留**一个**处置序列，其余全部改指针 |

最后一行是本协议自身最容易犯的错：**同一份文件里出现两套降级顺序，等于没有顺序**。

## 8. 审查姿态

- **技术事实高于个人偏好**
- **没有完美，只有更好**——不为满足审查者而补内容
- **想反驳的愿望本身不是证据**；要反驳须引用审查者读得到的证据（`CONTEST`，即「异议并附反证」），
  证据在其可读范围之外则升级说明（`ESCALATE`，即「上报」）
- **不要偷偷改级别**——认为某条「必修」其实只是「建议改」，就提异议并说明理由

## 9. 体裁专属：审查对象与证据形态

协议（§1–§8）跨体裁通用；**「拿什么去审」和「什么算实测」按体裁不同**：

| 体裁 | 审查对象 | 「实测」长什么样 |
|---|---|---|
| 汇报 PPT / HTML 汇报页 | **渲染后的产物**（PDF、缩略图网格、截图），不是源文件 | 几何测量（坐标、包围盒求交）、渲染目视、对比度取样 |
| 立项申请书 / 结题报告 | 申请书 + 当期的形式审查要求 + 上一期的承诺清单 | 条文对照：逐条指出要求原文与本次材料的落点 |
| 学术论文 | 稿件 + 当届 CFP / checklist | 逐项对照 CFP 原文；数字复算 |
| 专利 | 权利要求书 + 说明书 + 法条与审查指南 | 条号核对（**注意 2023 年细则已重排条号**）、技术特征逐项比对 |
| 软著 | 申请表 + 源代码 + 文档 | 四处口径（名称/版本号/日期/开发方式）逐字比对 |

**通用原则：不复信上游报告。** 每条候选问题都要用本体裁的「实测」手段复测一遍，
再决定它能不能升到必修。
