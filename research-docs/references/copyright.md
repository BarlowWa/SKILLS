# 软件著作权登记材料

登记是**形式核验**，不是实质审查：登记机构不判断软件是否先进，只核对材料是否齐全、
格式是否合规、源代码与文档是否对得上。所以这里的工作量与「写作」关系不大，
主要在**清单核对**与**代码抽取**。

## 1. 关键认知

- 软著保护的是**表达**，不是思想、算法、技术方案。**技术方案要走专利**。
- 登记只看形式一致性，但**材料之间自相矛盾是真实的驳回原因**（软件名称、版本号、
  开发完成日期、开发方式在各表与说明书中不一致）。
- 唯一容易被忽略的成本：**源代码前后各 30 页必须是真实、连续、可编译的源码**，
  不能是空行、注释堆、或从多文件剪贴拼接出的碎片。

## 2. 通常需要准备的材料

以登记机构当期要求为准，常见清单：

| 材料 | 要点 |
|---|---|
| 软件著作权登记申请表 | 名称、版本号、开发完成日期、首次发表日期——**全表一处口径** |
| 源程序 | 前后各 30 页（前 30＋后 30），连续编页；**不足 60 页全交**；程序每页不少于 50 行 |
| 文档 | 前后各 30 页；**文档每页不少于 30 行**（与程序不同，别套错） |
| 身份证明 | 单位营业执照 / 个人身份证 |
| 权属证明 | 委托开发、合作开发、职务作品需附对应协议 |
| 其他 | 代理委托书（如委托代理） |

## 3. 判据

**名称、版本号、日期、开发方式四项必须全篇一致。** 这是驳回的第一大来源。
申请表、源代码页眉、文档封面三处最容易不一致。

**源代码的「前后各 30 页」有讲究：**

- 页码连续，页眉统一写软件名称＋版本号。
- 前 30 页通常是入口与主流程，后 30 页是收尾——**选代码时优先选能体现完整逻辑的段落**，
  不要机械地取文件首尾，那样常常是 import 与 license 头。
- 删掉第三方库代码、生成代码、自动注释块；保留自己的核心实现。
- **代码量与软著价值无关**，但材料要能体现「这是一个能运行的软件」，不是一堆脚本。

**文档要与代码对得上。** 用户手册里出现的功能、界面、菜单项，代码里要有对应实现。
只写「本软件具有强大的知识管理能力」这类内容的文档，与源代码的互证性很差。

**开发完成日期不要晚于或靠近申请日**——留出合理的时间关系，避免与其它材料冲突。

## 4. 与专利的分工

| | 软著 | 专利 |
|---|---|---|
| 保护对象 | 代码表达 | 技术方案、方法 |
| 审查 | 形式核验 | 实质审查 |
| 周期 | 较短 | 长 |
| 常见误区 | 以为能保护算法 | 只见交底书，代码没整理 |

**同一成果可以两者都要**：专利保护「怎么做的」，软著保护「写出来的这份代码」。
若只有算法没有具体实现，软著无从谈起；若只有代码没有可专利的技术方案，专利不成立。

## 5. 交付前自检

- [ ] 申请表、源代码页眉、文档封面的**名称与版本号**是否完全一致？
- [ ] 开发完成日期、首次发表日期是否与其它材料无冲突？
- [ ] 源代码是否连续编页、页眉统一、无第三方库与自动生成代码？
- [ ] 源代码前 30 页是否选在了能体现主流程的位置，而不是 import 与注释头？
- [ ] 文档描述的功能在代码里能否找到对应实现？
- [ ] 权属（职务作品 / 委托 / 合作）是否有对应协议？

> 具体页数要求、表格模板、代理要求以登记机构当期规定为准；本文件只给材料一致性层面的判据。
