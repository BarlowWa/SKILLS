# 汇报 PPT

读者在**现场大屏**上边听边看，只有几秒消化一页。判据是「看完这一页，他能不能带走一句判断」。

## 1. 内容：两条逻辑线，缺一不可

### 横向：标题连起来能不能成故事（幽灵稿）

只写标题、不写正文，标题自上而下连读。讲不完整说明结构错了——**此时改结构，不是改版面**。
先交幽灵稿给用户签字，三分钟能发现「重点搞偏了」；写满二十页再改，成本高十倍。

**标题是假设，不是承诺。** 正文分析出来不支撑标题时，**回头改标题**，不是硬凑正文。

### 纵向：每页正文能不能证明自己的标题

幽灵稿只管横向。一份通过幽灵稿测试的 deck，完全可能**每页正文都证实不了标题**。

**双向遮挡测试**，逐页做：

- 遮住标题看正文——能否自己看出结论？
- 遮住正文看标题——正文是否真的支撑这句话？

### 行动标题的三类失败

「标题写成完整判断句」这一条**判据不够**，下面两类都能通过它：

| 失败 | 例 | 为什么没过 |
|---|---|---|
| **停在观察** | 「流失率上升 4%」 | 是完整句，但只是观察，不是判断 |
| **过度断言** | 「新架构彻底解决了性能问题」 | 完整且是判断，但正文证明不了 |
| 两行啰嗦 | 超过 22 字被折行 | 说明论点还没想清 |

**判据**：标题要说出这件事**意味着什么**，且正文能给得出证据。
「流失率上升 4%」→「客服响应慢是流失的主要来源：上升的 4% 全来自等待超时的用户」。

### 其余内容规则

**每页一个论点，约一分钟。** 二十分钟的汇报约二十页。两个论点就拆页。

**每个元素都要能在讲稿里被指认。** 指认不出来的元素删掉——它的存在只为撑版面。

**结论句在图表上方，用大字。** 图表是证据，不承担论点。一页最多一句结论句。

**关键结果直接标注在图上**（箭头、高亮区域、标注框），不要让读者自己在图里找。

**用对比，不用堆砌。** 过去 vs 现在、做前 vs 做后、能答 vs 拒答。

**主结果要早出现。** 五分钟的 spotlight 内必须出现在第 3–4 页；后面的页是补充证据，
不是铺垫。先主结果后方法细节。

**页间要有口头衔接。** 讲完一页，下一句自然引到下一页——这是排练时要练的，不是写出来的。

**收尾不落「遗留问题」**，落到价值与下一步；但边界怎么写见 SKILL.md §3「边界要如实说」。

> ⚠️ **项目经验法则，非文献结论**：以下两条在实践中有效，但在公开文献里找不到出处，
> 不要当成有依据的通行规则：
> - **先肯定现有能力，再讲天花板**——直接否定读者熟悉的系统会激起辩护
> - **现状页只讲症结，不解释原因**——原因留给后面的原因页

**外部借鉴每条必须带来源**（在图上，不是在页脚）：做参考图的时候就标，别等忘了出处再补。

**反证预案**，预判最可能被问的三个方向：

- **趋势反证**：「活动前 6 个月指标没有上升趋势；变化出现在对策上线后；未实施对策的同类样本没有同等跳变。」
- **口径反证**：「两组数字用同一脚本、同一口径复算；被弃用的旧口径原因已查明。」
- **能力反证**：「能答的给答案和出处；答不了的明确说没有依据并指路——不硬答。」

## 2. 中文答辩场景的本地惯例

英文文献（Naegle 2021、学术会议指南）与中文学位答辩的官方要求**存在直接冲突**，
照搬会踩坑。以本校当期通知为准，下列差异供预判：

| 项 | 英文学术共识 | 中文答辩常见要求 |
|---|---|---|
| 结尾页 | 停在结论页，**不接「Thank You」** | 「恳请各位专家批评指正」是通行做法 |
| 参考文献页 | 必须有 References 页 | 部分高校明确「关键词、参考文献不须在 PPT 中列出」 |
| 动画 | 禁用 | 个别通知反而建议「节奏较快的切换效果」 |
| 章节标题 | 禁止标签式（「研究目标」） | 官方通知常把「研究目标／内容／方法／结论」列为**覆盖清单**——那是**要讲什么**，不是**标题怎么写**。两者可同时满足：章节骨架照官方的，每页标题仍写成判断句 |
| 盲审 | 写单位与致谢 | **要求隐去导师、学号、作者单位** |
| 必备结构页 | 无对应 | **评阅意见修改说明页**是许多学校的强制页 |

**结论**：章节骨架服从校方，标题写法服从可读性。冲突时以校方通知为准，但要保留判断句标题。

## 3. 版式形状

形状规则跨项目成立；**具体数值属项目级**，须按项目模板校准后写入项目规范。

> **数值出处与可信度**：本节数值来自一次 16:9（13.333 × 7.5 in）PPT 的实测审计
> （python-pptx 读几何、PyMuPDF 做包围盒求交、110 dpi 渲染目视），**不是通用标准**。
> 该审计记录未入库，故无法在此复算——**当作校准起点，不要当结论引用**。
> 需要在自己项目上用，就重新测一遍。

### 三带结构

版面切三条横带，全篇一致：**标题带 / 内容带 / 页脚带**。

全篇内容顶边取**一个值**、底边取**一个值**。
实测案例顶边散落 13 个近邻值，翻页时内容上下跳；但把 13 个值归一要改 19 页 × 多个形状，
且差异肉眼不可辨——**这条属于「知道但可以不修」**。

对齐线全篇只留两组：正文左边界／内容右边界，以及卡片内文字相对卡片的缩进。
区块宽度从栅格推导（12 栏 × 固定沟槽），不要每页手调。

### 字号阶梯

- **相邻层级至少差 1.25 倍**。26 → 20 → 18 不成立（差 1.3 和 1.11），26 → 20 → 16 成立。
  实测反例：15pt 小标题配 14pt 正文，只差 7%，层级等于没有。
- **每页至少一个 ≥30pt 的元素**（标题之外的数字或结论），否则投影时找不到落点。
- **正文 ≥18pt**（学术投影场景；商业 deck 可到 14–16pt，场景不同勿混）。
- **全篇字号种数 ≤6**，内容页 ≤5。实测反例：全篇用了 22 种。
- 标题长度上限按模板实测得出（实测案例为 **≤22 个汉字**，中文单行上限约 24 字），
  超了先删修饰词，不要缩字号。**这条含内容成分**（多出的常是修饰词），须在项目规范里定值。

### 密度

- 每页独立信息单元 **≤4**。依据是工作记忆容量研究（文献结论，非本次审计）。
- 单页上屏字数：文献口径约 40 个英文词，换算中文约 60–80 字，但**该换算未实测**，
  按项目实测校准后写入项目规范，不要直接照搬。
- 两套密度指标分开看：**文本块面积**看「是不是文字堆」，**墨迹率**看「视觉是否喘不过气」。
  实测出现过文本块占 59% 但墨迹率仅 15% 的页，单看一个指标会误判。
- 单要点 ≤2 行；单列表 ≤4 项。超过就是该拆页。

### 表格

- **列宽从结论列和数字列倒推**：先给数字列固定宽（`最长数字字符数 × 0.55 × 字号 ÷ 72 + 内边距`），
  剩余均分给文字列。
- **不靠缩字号解决放不下**。9 列表在正文字号下放不下就是放不下——拆成两张，或前几列留正表、
  其余移附录。实测反例：缩到 11.5pt 仍然横向溢出。
- **行列数上限属项目经验值**（常见口径 6×6），公开文献里没有依据，按项目定。
- 超过 2×2 的表格**加网格线**——不加会让视线跳行。
- 行高 ≈ `字号 ÷ 72 × 1.3 + 上下内边距`；文本框高度不足以放两行时，删掉后半句，不要硬塞。

### 卡片

- 卡内纵向顺序：**小标题 → 数字／结论 → 说明**。数字放底部是反的——读者读完两行说明才看到重点。
- 卡片数 **3 或 4**；超过 4 分两行。三栏天然符合扫读动线，优于五栏。
- 卡片间距全篇一个值；卡片宽度从栅格推导。

### 页脚与页码

- **页脚只写四类信息**：来源、口径、日期、脚注标记。**不写论证句**——
  论证句放最后一秒要读者停下来思考，收益为零。
- 页脚文字上限按框宽实测算（11pt 下约每汉字 0.123 in），留 40% 余量便于日后微调。
  实测案例取 **≤45 字**——这是该项目框宽下的值，仍是**篇幅上限，须按项目模板重算**。
- 页码右下，「当前 / 总」格式便于被引用定位；封面、结束页不编号。
- 页码用母版 `slidenum` 字段，不要手写文本框——增删页后要重跑脚本，容易漏。

### 对比度

正文类文字 **≥4.5:1**，小字建议 **6:1**（投影比屏幕苛刻）。
次要灰、状态色最容易不达标。**但不要把次要信息提亮成主信息**——加深颜色会破坏层级，
这类问题常常是「不改更好」。优先保证主文字色达标。

### 技术健壮性

- **动画默认关**（`<p:timing>`）。学术与评审场合动画多半是负分，且易在他人机器上失效；
  项目模板若允许动画，按模板上限用，但**渐次出现以替代拆页是不可接受的**——那只是把一页的过载藏起来。
- **存一份 PDF 备份**，主文件打不开时直接用 PDF。
- 关键结果备一张**视频截图页**，现场演示不可用时顶上。

## 4. 交付前：黑盒审查协议

把渲染后的产物（PDF 或缩略图网格）交给**只看产物**的独立视角。
**不复信上游报告**：每条候选问题都用几何测量、包围盒求交、渲染目视**复测**。

> **审查必须在全新上下文中执行。** 做不到时，**必须声明「这不是审查」，不要降级冒充**。
> 同上下文自审的判别力显著下降，且审查者会偏向自己刚写的东西。

### 每条问题必须带三样

| 字段 | 说明 |
|---|---|
| **严重级** | 必修／建议改／明确不改／待确认 |
| **证据状态** | **实测**（坐标＋原始输出）／**线索**（推断、按公式估）／**推测** |
| **protects**（仅必修） | 保护哪条官方条款、验收标准或用户场景 |

**证据状态决定能升到多高**：实测 → 可到必修；**线索 → 最高只能到建议改**；推测 → 只能待确认。

这条堵死一整类错误：**按字数估算列宽**得出的「表格溢出 2.06 in」，天生不可能被判为必修。

**必修必须挂 protects，写不出的降为建议改。** 这样「必修」可判定，不靠审查者语气强弱。

### 必修的判据（须同时满足一条判据＋有 protects）

- **实测复现**：有坐标、原始输出证明照现状交付会错
- **验收不可判定**：交付物无法证明满足自己声明的标准
- **单向门**：撤回成本远高于现在改
- **现场可被当场问倒**：有具体提问人／场景，现答案站不住

### 明确不改要拆成四类

混在一起会稀释证据价值：

| 子类 | 说明 |
|---|---|
| **已证伪** | 复测后发现原判断不成立 |
| **成立但收益不抵成本** | 须写四要素：Pros／Cons／Rejected because／**Revisit if** |
| **纯口味** | 无判据的审美偏好——标明「不构成审查意见」，**不计入结论** |
| **超出范围** | 不在本次交付范围 |

### 单列「被证伪」表，每条两列必填

| 栏 | 为什么必须 |
|---|---|
| **复测方法** | 命令／参数／坐标，让第三个人能判断证伪本身可不可信 |
| **若按原报告改会怎样** | 没有这一栏，「证伪」只是另一个意见 |

范例：「按字数估算需 14.10 in，实际渲染右缘 12.50 in 未越界；**若按原报告重排列宽，会把
12.04 拉到 14.10，反而真的越界**」。

**这张表解决的是**：防止按错误的上游报告返工、甚至改坏。没有它，下一个接手的人会把同样的
错误再犯一遍。

### 未执行 ≠ 没发现问题

审查者超时、抓不到文件、工具失败，状态记为 **`not run`**，**绝不能算作零发现**。
裁决时报两个数字：

```
surface pass  = 通过 / 已执行
effective pass = 通过 / (已执行 − 受阻)
```

这是 PARTIAL 被悄悄算成 PASS 的唯一入口。**报告结尾固定写「本轮未覆盖什么」。**

### 审查姿态

- **技术事实高于个人偏好**
- **没有完美，只有更好**——不为满足审查者而补内容
- **想反驳的愿望本身不是证据**；要反驳须引用审查者读得到的证据（`CONTEST`，即「异议并附反证」），
  证据在其可读范围之外则升级说明（`ESCALATE`，即「上报」）
- **不要偷偷改级别**——认为某条「必修」其实只是「建议改」，就提异议并说明理由

## 5. 常见失败模式

| 症状 | 根因 | 改法 |
|---|---|---|
| 像规格说明书 | 按准确率验收 | 回到 SKILL.md §0 判据：删细节、提结论 |
| 每页信息量均匀、没有高潮 | 缺少优先级 | 幽灵稿重排结构 |
| 标题都是完整句，但仍不好 | 只在观察，或过度断言 | 做 §1 的三类失败检查 |
| 幽灵稿很顺，翻页却散 | 纵向逻辑缺失 | 做双向遮挡测试 |
| 排版丑但说不出哪丑 | 没看产物 | 渲染回去看，按 §4 审 |
| 字数塞不下就缩字号 | 顺序错了 | 删字→删小字→删卡片行→最后拆页 |
| 通篇同构 | 套版式 | 保留 2–3 种版式变化，别每页「标题＋三行要点」 |
