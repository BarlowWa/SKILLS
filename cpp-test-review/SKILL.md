# C++ 测试代码审查

对 C++ 测试代码进行质量审查，确保测试可靠性、可维护性和有效性。

## 适用范围

- 测试目录：`tests/`、`test/`、`unittest/`、`*_test.*`、`*_unittest.*`
- 测试框架：Google Test（gtest）、Catch2、doctest、Boost.Test 等
- **审查依据不限于测试源码**：对 EXEC 组（执行链）还必须读取**构建配置**（CMakeLists/Makefile/meson 等）与**运行产物**（`ctest` 日志、gtest XML、CI 结果）。仅凭测试源码**无法**判断测试是否真的被构建、注册、执行——这三类恰恰是"缺席类"缺陷，在源码里表现为"看起来没问题"。
- **不适用**：生产代码的编码规范（由 `cpp-rules` 负责）、测试用例设计（由 `cpp-test-author` 负责）、模块架构审查（由 `cpp-arch-review` 负责）

## 工作流程

0. **收集执行证据**（EXEC 组的前提）：定位构建配置中有无测试目标、`ctest -N` 或等价方式的注册清单、最近的运行日志/报告。**注意运行产物是活文件**——先记录其时间戳，确认审查期间未被其它构建或 CI 改写，否则同一次报告内的数据可能来自不同次运行。
1. **寻找用例设计清单**：`cpp-test-author` 产出的「契约表 + 用例矩阵 + 断言区分度表 + 待确认契约项」是核对基准，其中标为 `推测` 的契约项与期望值依据须**优先核对**（它们最可能产出错误期望值）。
   **在以下位置按序查找**：测试文件顶部的 `// ===== 测试设计依据 =====` 注释块 → `docs/test-design/` 等固定路径 → 同会话上下文中 author 的输出。
   **⚠️ 若三处都找不到，不得静默跳过**：本小节在报告中须显式标注 **「未找到设计清单——CONTRACT/EXPECT/DIST/BVA/ECP/BRP 覆盖无法核对」**，并按 warning 计入报告。**这不是"没问题"，是"这一整块没查"**。缺失的原因通常是清单未落盘（见 `cpp-test-author` 输出格式的落盘要求），应在报告里点明。
2. **识别测试文件**：扫描测试目录和命名模式，确定审查范围
3. **逐文件审查**：对照下方 checklist 逐条检查
4. **输出报告**：按底部格式输出审查结果

## 严重级别

| 级别    | 含义                                              |
| ------- | ------------------------------------------------- |
| blocker | 必须修复，违规测试可能产生假阳性/假阴性，削弱测试可信度 |
| warning | 优化建议，应处理但不阻塞提交                       |

## ⚠️ 判定的证据来源：哪些能机械核对，哪些只能核对"依据"

**本技能的判据分两类，判定前必须先分清——否则会把"设计者说什么"当成"实际做了什么"。**

| 类型 | 判据 | 怎么判 |
|---|---|---|
| **形态可核对** | ORG · MOCK · DET · ASRT · EXEC · DEATH · TPERF | **直接读测试代码/构建配置/运行产物**，不依赖任何自述。这类是本技能的主力，判定结果应当具体到 `文件:行` |
| **需要设计依据** | COV-W · CONTRACT · EXPECT · DIST · BVA · ECP · BRP · FLT · CONC · RLC | 只能判定**是否落地**，不能判定**设计是否正确** |

**第二类的关键限制**（务必在报告中如实反映）：

- **它们的判定输入是 `cpp-test-author` 的设计清单**（契约表 / 用例矩阵 / 断言区分度表）。**没有清单 = 无法判定**，不是"通过"。
- **清单本身是自述**：那三列（契约的依据 / 期望值依据 / 能捕获的实现错误）由设计者自填，**本技能没有任何机制验证其是否为真**（唯一能证伪的手段是变异测试——改坏实现看断言是否变红）。
- 因此：**核对到的是"清单与测试是否一致"，不是"契约是否正确、边界是否取对"。** 审查者若发现清单缺失或明显是补写的，应当**降低对该组结论的置信度并在报告中注明**，而不是照单打勾。
- **不要把"清单说覆盖了"当成"确实覆盖了"**——尤其当测试与清单高度吻合、措辞雷同时，可能是同一份自述的两次誊抄。

**设计清单缺失时的正确处理**：见下方「设计覆盖核对」小节的兜底条款——**显式标注"未找到清单，该组无法核对"并计入 warning**，不得静默略过。

## Blocker 检查清单

### ORG：文件组织

- **ORG-001**：测试文件必须与源文件有明确对应关系。命名规范：`<source>_test.cpp` / `<source>_unittest.cpp` / `<module>_test.cpp`；禁止无关联的随机测试文件名
  > 对应关系确保他人能快速定位测试，避免测试成为黑盒。
- **ORG-002**：测试目录结构应镜像源代码目录结构。如 `src/foo/bar.cpp` 对应 `tests/foo/bar_test.cpp` 或其等价路径
  > 此处的「镜像」指**目录结构**，与 ASRT-005 禁止的「镜像实现」（测试内重写被测逻辑）无关，勿混淆。
- **ORG-003**：新建测试文件须声明**测试层级**（unit / integration / e2e），且声明的层级须与测试的**实际范围**相符。默认取**能覆盖目标的最低层级**——仅为验证单个函数/类的行为，不得引入完整集成环境或真实外部依赖（真实网络、真实数据库、启动完整对象图）。
  > 层级选择失当同时造成三害：运行时间数量级上升（与 TPERF-001 冲突）、非确定性风险上升（与 DET 组冲突）、失败定位成本上升。本条约束的是**层级选择**，MOCK/DET 组约束的是选定层级之后的写法。
  > **边界**：本条不禁止测试写入临时目录 —— 当一个单元**本身就是**文件系统适配层（路径拼接、文件句柄 RAII、目录遍历）时，用临时目录做真实文件操作是必要的正确层级，不应判违规；禁止的是为验证纯内存逻辑而读写真实文件。同理，被测单元本身就是网络/数据库适配层时，对真实依赖的测试属正当层级。
  > `// Test level: unit` 一行注释不构成本条的通过条件——审查者须核对 `#include` 与测试实际触碰的资源是否与声明层级相符。

### MOCK：Mock 与 Fake 策略

- **MOCK-001**：禁止 mock 不拥有的类型。只能 mock/fake 自己代码中的接口，禁止 mock 第三方库、STL 或系统 API 的具象类
  > mock 第三方类型会在库升级时无声失效（接口变化但 mock 不报错，测试继续通过），导致虚假安全感。
- **MOCK-002**：禁止对值类型和 STL 容器（`std::vector`、`std::string` 等）使用 mock——直接构造真实实例即可，mock 值类型不增加价值反而增加复杂度

### DET：测试确定性

- **DET-001**：禁止在测试断言中使用 `std::rand()` / `std::random_device` / `std::mt19937` 等非确定性随机源。若需要随机数据，使用确定性的种子生成器并在测试中显式注入
  > 非确定性随机源导致测试偶发性失败（flaky test），极难调试且破坏 CI 可信度。
- **DET-002**：禁止在测试断言中直接使用 `std::chrono::system_clock::now()` / `time()` / `gettimeofday()` 等实时时钟。使用可注入的假时钟（fake clock）配合时间源抽象
  > 实时时钟依赖导致测试在跨时区、夏令时切换、系统时间调整时失败，且运行速度不可控。注意：`std::chrono::steady_clock` 仅保证单调（免墙钟回拨），**不能**让测试确定性——真实时间仍流逝；确定性解法是"时间源抽象 + 注入假时钟"，`steady_clock` 不能替代。
- **DET-003**：测试用例之间禁止通过全局变量、静态变量、单例状态共享可变数据。每个测试必须是独立的（isolated），运行顺序不应影响结果
  > SetUp/TearDown 中必须重置所有全局/静态状态。测试框架通常不保证用例执行顺序。
- **DET-004**：异步/并发测试必须确定性——异步操作须显式等待完成（`future.get()`/`wait()`、事件/条件变量通知），测试内创建的线程必须 join（未 join 的 `std::thread` 析构会 `std::terminate`），竞态敏感点用确定性同步手段，禁止依赖调度时序或 sleep 猜测

### ASRT：断言质量

- **ASRT-001**：每个测试用例必须包含至少一个有效断言（EXPECT/ASSERT）。禁止空测试或无断言测试——一个不含断言的 TEST 默认通过，给出"已覆盖"的虚假安全感
- **ASRT-002**：断言须验证关键语义。禁止平凡断言 / 无意义断言（`EXPECT_TRUE(true)`、`ASSERT_TRUE(ptr != nullptr)` 后不验证具体行为）；比较用 `EXPECT_EQ`/`EXPECT_NE` 而非 `EXPECT_TRUE(a == b)`（失败信息差异巨大）
  > 本条中的「平凡断言」指**形式正确但内容空洞**的断言；「测试内重写被测逻辑」属另一类缺陷，见 ASRT-005。
- **ASRT-003**：浮点比较禁止直接 `EXPECT_EQ`，使用 `EXPECT_NEAR` / `EXPECT_DOUBLE_EQ` 并显式设定容差（EPSILON）
- **ASRT-004**：正确选用 `EXPECT`（非致命，继续执行）与 `ASSERT`（致命，失败即终止当前用例）；依赖后续语句安全时（如解引用指针前）用 `ASSERT` 提前拦截
- **ASRT-005**：禁止**镜像实现**——测试代码中不得重新实现一遍被测逻辑再与被测实现对比。典型形态：在测试内重写算法、复制同源实现作为参照、先运行被测实现再把输出固化成字面量当期望值。测试期望值必须来自契约、规格或独立算例。
  > **为何是 blocker**：镜像实现只验证「两处实现一致」，无法验证正确性——两处犯同一个错时测试照样通过。它给出的「已覆盖」是彻底的假象，且无法通过覆盖率、断言数量等任何统计指标发现。注意「字面量」形态最隐蔽：断言写法上是常量、形似独立算例，但期望值实为照抄实现输出；审查时对**边界与异常用例的期望值**须重点追问来源（边界值恰是照抄实现最不易被察觉处）。
- **ASRT-006**：断言只依据**公开可观测**的返回值、副作用与状态。禁止在测试内通过后门访问私有成员——`#define private public`、`FRIEND_TEST`、测试夹具声明为 `friend`、直接读取私有成员或内部缓存值。
  > **为何是 blocker**：后门把实现细节固化成契约，任何内部重构都会连带破坏一批本应无关的测试，最终使测试成为重构阻力而非安全网。这属于本技能自立的测试可观测性约束。
  > **边界**：仅为测试可见性、不改语义的 `friend` 类声明（如 `class FooTest;` 前置声明）在部分代码库属既有约定，存量可分期整改；**断言私有成员取值**与 `#define private public` 不在豁免之列。

### EXEC：执行链（测试是否真的在跑）

> **本组必须读取构建配置与运行产物，不能只看测试源码。** 前四组审的是"测试写得对不对"，本组审的是"这些测试算不算数"——一个断言写得再好的测试，若从未被构建或从未被调用，其价值为零，且**在源码里完全看不出来**。

- **EXEC-001**：每个测试源文件必须**被某个构建配置引用**，且该引用能真正导致编译。
  > 判据是「有没有被**任何** CMakeLists/Makefile 引用」，**不是**「有没有被 `add_subdirectory` 引入」——后者只是前者的实现方式之一。测试源被**父目录**的 CMakeLists 直接 `add_executable` 属常见且合法的形态；而「目录存在独立 `test/CMakeLists.txt` 但没被上层引入」才是死代码。
  > **⚠️ 不要用"搜 `add_subdirectory` 文本"来判断测试目录是否被引入**：`add_subdirectory()` 取的是**相对当前 CMakeLists 的路径**，同一目录在不同层级写法各异（本技能实测中，先后用"目录名匹配"和"仓库相对路径匹配"两种写法，在同一个正常工作的仓库上**分别误报 3 条和 4 条**）。可靠的做法是查**构建产物**：`bin/<config>/` 下是否有对应的测试可执行文件，并与注册清单做双向差集。
  > **⚠️ 未编译的测试不会报错、不会告警、不出现在任何报告里**——它是纯粹的缺席，只能靠**反查**发现。两条独立路径：
  > 1. **构建配置的 target 清单**（如 `build/CMakeFiles/TargetDirectories.txt`）——不依赖是否构建过
  > 2. **构建产物的反查**——需要产物存在
  > **⚠️ 用产物反查时，选错 config 会大面积假阳性。** 多配置生成器下各配置的产物目录**内容不同且新旧不一**：实测某仓库 `bin/Release/` 有 24 个测试 exe，而 `bin/Debug/` 只有 5 个陈旧残留。拿后者去对账会得出「19 个测试没进构建」的假 blocker。**先确认当前构建使用的是哪个 config**（与生成器、`CMAKE_RUNTIME_OUTPUT_DIRECTORY` 的写法有关），再看对应目录。
  > **⚠️ 查注册清单时，必须在【构建目录】跑，不能在仓库根跑。** 实测某仓库根目录的 `CMakeLists.txt` 含 `enable_testing()`，导致在仓库根跑 `ctest -N` **成功返回 `Total Tests: 0`**——不是报错，是静默给 0。若据此判"全部未注册"，就是一个假 blocker。**先确认 `CTestTestfile.cmake` 在哪个目录，再在该目录执行。**

- **EXEC-002**：测试可执行目标必须**注册给测试运行器**（CTest 的 `add_test`、或项目自身的 runner 入口），否则构建出来也从不执行。
  > 常见形态：`add_executable(XxxTest ...)` 写了，却漏了 `add_test(NAME XxxTest COMMAND XxxTest)`；或注册被包在 `if(NOT SKIP_XXX)` 里而该开关默认关闭。**"构建出测试 exe"不等于"跑了测试"**——若项目手册只写到"构建出 N 个测试可执行产物"为止、找不到运行命令，那是纸面约定而非执行链。
  > **⚠️ 判定必须用构建后的注册清单，不得用 CMakeLists 的字面文本做差集。** 实测某仓库字面比对待出 10 条"未注册"，**全部是假阳性**——因为注册是用**变量/foreach 生成**的：
  > ```cmake
  > foreach(test_target ObjectPoolTest ThreadPoolTest ...)
  >   add_test(NAME ${test_target} COMMAND ${test_target})    # 字面 grep 查不到
  > endforeach()
  > ```
  > 字面差集会把「用了 foreach」误读成「漏了 `add_test`」。**唯一可靠判据是构建后 `ctest -N`（或等价方式）实际列出的注册清单**，与各目标的对应关系在该清单上核对。
  > **⚠️ 范围限定**：本条只针对**测试**可执行目标。`add_executable` 还包含 DLL、驱动、工具等非测试目标（实测某仓库的 24 个里有 `ODBCDriver`/`TDengineDriver`），把它们一律当成"测试未注册"会直接产出假 blocker。先确认哪些 target 是测试。

- **EXEC-003**：测试不得被**无条件跳过**。以下形态必须逐条确认有无正当理由（为何跳过、何时恢复、关联工单），无理由者按 blocker：
  > - `GTEST_SKIP()` / `DISABLED_` 前缀 / `doctest::skip()` / Catch2 的 `[.]` 标签
  > - `#if 0` 包裹测试体
  > - **条件编译包裹整个 `TEST_CASE`**（`#ifdef _WIN32`、`#ifndef NDEBUG`、`SUPPORTS_*`）——平台/配置相关的用例差异
  > **⚠️ 这条要区分两种情形，不可一律当最隐蔽**：「**同名替换**」（`#ifdef` / `#else` 各一条 `TEST_CASE`，总数守恒）运行时**有痕迹**、可核验，属正当平台差异；真正的「**静默消失**」（某平台下**没有任何** `TEST_CASE` 顶替）才是隐蔽形态。判定前先看 `#ifdef` 是否配对。
  > - 用例体只有 `return;`（空壳占位，永远通过）
  > - **前置 guard + 提早 `return`**（最易漏检的形态）：`if (<前置条件不满足>) return;` 位于 `TEST_CASE` 开头，**无任何标记、运行时报 `[PASS]`**，与真跑过**完全不可区分**。实测某仓库有 9 处此形态，源码注释自述为「SKIP 约定」——这是该仓库**最主流的跳过机制**，而 `GTEST_SKIP`/`DISABLED_`/`[.]` 等标准词表**一条都覆盖不到**。
  > ```cpp
  > TEST_CASE("...") {
  >     const std::string& dll = odbcDriverPath();
  >     if (dll.empty()) return;      // ← 无标记的静默跳过，运行时 [PASS]
  >     ...真正的断言...
  > }
  > ```
  > **判定**：这类 guard 若依赖外部资源（驱动文件、数据库、硬件），本身可能是合理的防御；但**必须能与"真的测过了"区分**。合格做法是输出显式跳过标记（框架的 skip API，或至少打印 `[SKIP]` 并计数）；**只在运行时打印 `[PASS]` 而不留任何痕迹的，按 blocker**——它使"测试通过"失去信息量。至少应登记为 warning 并要求补标记。
  > **⚠️「静默」的判据是「有无解释」，不是「有无 `#ifdef`」。** 上面第 3、4 条的形态成立时，**先读注释和技术理由**：带说明、有充分理由（如平台 API 无法构造前置条件）、且该逻辑在另一平台已覆盖的，属**正当平台差异**，记 warning 即可。只有当包裹**无任何说明、且相应逻辑在任何平台都未被覆盖**时，才按 blocker。用 `SKIP_RETURN_CODE <码>` 显式声明跳过且实现侧在缺依赖时主动返回该码（而非静默 `return 0`）的集成测试，属**正当用法**，不报缺陷。
  > **判据来源**：优先用**运行产物**——gtest 的 XML 报告会为每个 testcase 记录运行状态（官方示例中形如 `<testcase name="..." status="run" .../>`；**具体的"未运行/被抑制"取值需以你本地 gtest 版本的实际输出为准，不要凭文档片段推断**），CTest 则会把跳过项写进 `LastTestsDisabled.log`。**测试通常会自报家门，不必只靠读源码猜——但要先确认你用的框架确实产出了这类记录。**
  > **⚠️ 源码扫描的词汇表覆盖不足是常态**：某仓库实测框架跳过宏 0 命中，而 CTest 日志里确实记录了被跳过的测试。**源码扫描 0 命中只能证明"没用这些宏"，不能证明"没有跳过"。**
  > **⚠️ 自研框架没有现成的运行产物**：若项目不用 gtest/Catch2 而是自己的 harness，`--gtest_output=xml` 这条路不存在，`LastTestsDisabled.log` 也可能只记录 **CMake 层的 `SKIP_RETURN_CODE`**、不记录测试内部的自跳过。此时**只能回到源码扫描**，须相应放宽结论并明说"跳过情况未能完整核对"。
  > **⚠️ `LastTestsDisabled.log` 只在有跳过项时更新**：只跑全绿的测试不会刷新它，容易读到几小时前的陈旧残留（实测某条目 mtime 已过期 3 小时，而重跑该测试是 Passed）。读取前**先核对 mtime**，过期的不可作为"本套件有被禁用测试"的证据。

- **EXEC-004**：断言必须**真的会被执行**。禁止致命断言（`ASSERT_*`、`REQUIRE`、`CHECK_FALSE`、`FAIL`）之后的普通断言承载关键验证——致命断言失败即终止当前用例，其后的语句永不执行。
  > **⚠️ 先读框架头确认宏的真实语义，不要按字面形态推断**：同一写法 `#define REQUIRE(expr) CHECK(expr)`，若 `CHECK` 抛异常则 `REQUIRE` **是**致命的，若 `CHECK` 只记日志则**不是**。必须一路读到最底层宏体（看到 `throw`/`abort`/`return`）才能定性。

- **EXEC-005**：套件不得包含**已知失败但被隔离**的用例而不做机器可识别的标记。
  > 若项目把已知缺陷的复现用例拆成独立 target 以保证套件退出码为绿，则 **"CI 绿灯"不再等价于"无已知失败"**，CI 信号失效。必须落实**可操作的**标记：`set_tests_properties(... LABELS <标签>)` 并验证 `ctest -LE <标签>` 真能排除（与不带 `-LE` 的计数对比）、或 `WILL_FAIL`、或项目自己的期望失败清单。
  > **光把 target 命名成 `*ReproTest` 不算**——命名没有任何机制效力，`--print-labels` 报 `No Labels Exist` 时该约定在机器上**不存在**。
  > **⚠️ 必须先区分三种状态，不可一律报缺陷**：
  > | 状态 | 判据 | 处置 |
  > |---|---|---|
  > | **红灯仍在** | 用例为红 | 未标记 → blocker（CI 绿灯确实不等价于无已知失败） |
  > | **红灯已修、已转绿** | 用例全绿 **且** 提交顺序证明测试提交早于修复提交 **且** 断言写的是「应该怎样」 | 绿灯是**正确**结果；缺标记属**记账债**，**不报 blocker**（建议改名/补标记/清理陈旧注释） |
  > | **用例被改坏** | 用例为绿但断言写的是「现在怎样」 | blocker（期望值源自实现，见 ASRT-005） |
  > 实测某仓库 7 个 `*ReproTest` 全绿且无任何标记，但提交顺序证明红灯曾生效（测试提交 `78f1bdb` 早于各修复提交），断言写的全是"应该提供/应该返回正确值"——**属第二态，不该报 blocker**。把它当第一态报，就是冤枉了一个已经修好缺陷的仓库。

- **EXEC-006**：**按名字**逐条对账后，声明与执行不得有差异。
  > **⚠️ 计数先要数对**：裸 `grep -c TEST_CASE` 会把**注释里提到 `TEST_CASE` 的行**也算进去（实测某仓库裸匹配 527、真实声明 516，差 11 全在注释里）。必须用 `^TEST_CASE(` 这类锚定行首的写法。名字里可能含转义引号或多字节字符（实测有 `TEST_CASE("...value(key, \"literal\")...")`），自动比对前须归一化。
  > **⚠️ 不要用「声明总数 − 执行总数」直接判红。** 差额的唯一可接受来源是**平台条件编译的一对一替换**：
  > ```cpp
  > #ifdef _WIN32
  > TEST_CASE("A (not automated on Windows)") { /* 注释说明理由 */ return; }
  > #else
  > TEST_CASE("B (POSIX)") { ...CHECK(...)... }     // 另一平台的真实体
  > #endif
  > ```
  > 此时**总数守恒、名字互换**——源码文本扫到 2 条，Windows 下只注册 1 条，于是"声明数比执行数多 1"。**这不是"用例静默消失"，是同一个测试的两种平台实现。**
  > **⚠️「静默」的判据是「有无解释」，不是「有无 `#ifdef`」**：上述形态若带注释、有技术理由（如平台 API 无法构造前置条件）、且对应逻辑在另一平台**确实存在**，记一笔记账债，**不报 blocker**。只有当缺失的那一支**无任何说明、且相应逻辑在任何平台都未被覆盖**时，才按 blocker。
  > **正确做法**：按名字做双向差集，对每一处差异**读源码定位**（`comm` 出名字后回查 `#ifdef` 结构），而不是拿两个总数相减。

## Warning 检查清单

### COV-W：路径覆盖

- **COV-001**：每个被测公开接口（函数/方法）的测试集应覆盖正常路径和至少一个边界条件或异常/错误路径。禁止仅有 happy-path 的完整接口测试集
  > 仅有正常路径的测试给人以"已测试"的错觉，实际上异常分支完全未验证，是测试覆盖率中最常见的盲区。
- **COV-002**：对照 `cpp-test-author` 的设计清单逐项核对实际测试是否落地。**消费清单须完整**，缺一不可：契约表、用例矩阵（含「期望值依据」列）、**断言区分度表（含「能捕获的实现错误」列）**、待确认契约项。缺失的 CONTRACT/EXPECT/DIST/BVA/ECP/BRP 覆盖需在报告中显式列出。本条衔接 `cpp-test-author`（写时设计 → 写后审查）
  > 重点核对四处：契约表标为 `推测` 的项在测试中是否被当作既定事实；用例矩阵的「期望值依据」列所述来源与实际断言是否相符（写着「规格条目」而测试里是照抄实现输出，即为 ASRT-005 违规）；标为「待确认」的契约项是否在未确认的情况下被固化进断言；**断言区分度表所列「能捕获的实现错误」是否真的能捕获**（该列是设计者的自述，可对照实际断言判断其是否夸大）。
  > THR-W001（覆盖率阈值）见下方「THR-W：覆盖率阈值」小节。
- **COV-003**：套件冗余——同一测试文件内多条用例实际验证同一行为、断言集合几乎重复时，应合并为参数化用例，或**在文件中写明各自的差异点**。冗余用例会随被测行为演进而不同步，制造虚假的覆盖数量。
  > 与 `cpp-test-author` OGN-001（参数化）互补：OGN-001 说「怎么组织」，本条说「何时该组织」。写「差异点」注释不是豁免通道——若差异点仅是输入取值不同而断言语义完全相同，仍应合并。

### MOCK-W：Mock 深入建议

- **MOCK-003**：单个测试用例中 mock 对象数量宜控制在 3 个以内。超出时通常是被测类职责过重的信号，建议重构而非继续堆砌 mock（本条为启发式建议，不阻塞提交）
- **MOCK-004**：优先使用 Fake（轻量内存实现）而非 Mock（期望验证框架）。Fake 更简洁、可复用，且与实现解耦；Mock 适用于需验证交互协议的场景（如回调次数、调用顺序）
  > 过度使用 EXPECT_CALL / ON_CALL 会使测试脆弱——被测类的内部重构不应破坏测试。
- **MOCK-005**：区分 Stub / Fake / Mock 三概念——Stub（固定返回值，无交互验证）、Fake（可用轻量实现）、Mock（期望验证）。优先用 Stub/Fake 表达"桩"语义，避免为简单固定返回值引入完整 Mock 框架

### DEATH-W：Death Test 规范

- **DEATH-001**：Death test（`EXPECT_DEATH` / `ASSERT_DEATH` / `EXPECT_DEATH_IF_SUPPORTED` / `EXPECT_EXIT`）仅用于验证程序的断言/abort/致命崩溃行为及退出码。**禁止**用于验证普通异常抛出——异常用 `EXPECT_THROW` 验证
  > Death test 在独立子进程运行：POSIX（Linux/macOS）下 gtest 默认用 fork 子进程（开销较低）；Windows 无 fork，gtest 回退到 threadsafe 风格（spawn 新进程并重跑整个测试到死亡点，开销可达数百 ms~秒级）。且 death test 运行在独立进程，不继承测试夹具的内存态、其副作用不会回流主进程。滥用会显著拖慢测试套件，Windows 上尤甚。

### THR-W：覆盖率阈值

- **THR-W001**：建议语句/分支覆盖率阈值 ≥ 80%，核心模块建议 ≥ 90%。本条为可配置的目标声明（需运行时工具测量），仅作为审查时的参考建议

### TPERF-W：测试执行效率

- **TPERF-001**：单个测试用例平均执行时间应控制在 100ms 以内。超过 500ms 的测试应标记为慢速测试并确认必要性
  > 本条依赖运行时测量数据，静态审查时作为参考建议。
- **TPERF-002**：禁止在测试中使用 `sleep()` / `std::this_thread::sleep_for()` 等主动等待——用条件变量、fake clock 或轮询超时替代

## 豁免

- 用例设计由 `cpp-test-author` 主动规划（边界值/等价类/分支路径），本技能专注落地后的质量审查；两者协同形成「先设计、后审查」闭环
- 与已有大型遗留测试集集成时，ORG-001/002（文件组织）的目录结构改造可分期实施，新建测试必须遵守
- 性能基准测试（benchmark）使用独立的 `*_bench.cpp` 或 `bench/` 目录，豁免本技能中与正确性相关的规则（DET/COV 类），性能相关规则（TPERF-001/TPERF-002）也不适用
- DET-002（实时时钟）在专门测试时间相关逻辑的 integration test 中可例外，需注释说明原因
- ASRT-006（后门访问私有成员）中「仅为测试可见性的 `friend` 类声明」在既有代码库可分期整改；断言私有成员取值与 `#define private public` 不豁免
- **EXEC 组的证据依赖**：该组需要构建配置与运行产物。**纯源码审查场景下（如只拿到几个测试文件、无构建树）无法判定 EXEC-001/002/005/006**——此时应在报告中记为"未能判定（缺构建/运行证据）"，**不得记为通过**。EXEC-003（跳过形态）与 EXEC-004（断言可达性）可从源码独立判定，不因缺证据而跳过
- **EXEC 组存在第三态：「形态成立但根因正当」**。这是该组最重要的一条边界——**判据描述的技术形态出现，不等于构成缺陷**。以下三类必须判为"形态成立但根因正当"，**不报 blocker**：
  - **平台差异**：`#ifdef` 配对分支、平台 API 限制导致的占位，**有注释、有技术理由**且逻辑在另一平台已覆盖
  - **红灯已修复**：`*ReproTest` 全绿 + 提交顺序证明红灯曾生效 + 断言写的是「应该怎样」→ 结论是"已修好，缺记账"
  - **显式跳过契约**：`SKIP_RETURN_CODE` + 实现侧主动返回该码（而非静默 `return 0`）
  > **⚠️ 这条边界不能省**：实测一个"测试写得相当密、有正规 CTest 接入、红灯已全修"的健康仓库，若机械照搬判据形态，会被报出**两位数**的假 blocker。**判据只负责"发现形态"，定性必须结合根因**——把"形态吻合"直接输出成 blocker，是本技能最容易造成伤害的地方。
- **同一台机器上，测试是否"真的在跑"可能取决于环境而非代码**：多配置生成器缺 `-C` 参数、产物目录与工作目录不在同一盘、并行运行改写日志——这些都属**执行环境**问题。识别到此类现象时，报告为"未能判定"并说明所需环境，不要判为测试代码缺陷
- 其余规则无一例外
